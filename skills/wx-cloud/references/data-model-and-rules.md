# 集合建模与权限规则

> 云开发数据库的字段类型、查询语法与安全规则写法以官方「云开发 / 数据库 / 安全规则」文档为准。本文讲建模决策与越权防护。

## 一、建模的四条原则

1. **一集合一职责**。不要做"大杂烩表"（什么都塞一个集合里，靠 `type` 字段区分）。查询会越来越难写，权限也没法细分。
2. **字段名一旦上线就不要改名**。改名要全量刷数据 + 改所有代码，成本极高。上线前把字段名评审清楚。
3. **软删除优于物理删除**。加 `deleted: false`，查询带条件。物理删除后出问题无法追溯。
4. **时间统一存服务端时间**，不要用客户端时间（客户端可改）。

## 二、一个电商类示例

### 集合：goods（商品）

| 字段 | 类型 | 必填 | 说明 | 索引 |
|---|---|---|---|---|
| `_id` | string | 自动 | 主键 | 默认 |
| `title` | string | 是 | 名称 | |
| `price` | number | 是 | 单价（分） | |
| `cover` | string | 是 | 封面图（云存储 fileID 或 CDN 地址） | |
| `status` | string | 是 | `on` / `off` | 组合索引(status, createdAt) |
| `createdAt` | date | 是 | 服务端时间 | 同上 |
| `deleted` | boolean | 是 | 软删除标记 | |

**权限**：所有人可读（仅 `status == 'on'` 且 `deleted == false` 的部分靠查询过滤），写入仅管理端。因为没有"管理端"身份，实际做法是**商品写操作全走云函数**，集合规则设为"所有人不可写"。

### 集合：orders（订单）

| 字段 | 类型 | 必填 | 说明 | 索引 |
|---|---|---|---|---|
| `_openid` | string | 自动 | 下单用户 | 组合索引(_openid, createdAt) |
| `orderNo` | string | 是 | 业务订单号（唯一） | 唯一索引 |
| `items` | array | 是 | 明细快照（下单时固化价格） | |
| `amount` | number | 是 | 总额（分） | |
| `status` | string | 是 | `created`/`paid`/`shipped`/`done`/`closed` | |
| `paidAt` | date | 否 | 支付时间 | |

**权限**：仅创建者可读；**写入全部走云函数**（下单、改状态、发货）。原因：如果允许前端直接写 `status`，用户就能自己把订单改成已支付。

> 这条是云开发最常见的越权漏洞：为了省事让前端直接 `update` 订单状态。

## 三、安全规则怎么写

云开发的安全规则是 JSON，表达"谁能读、谁能写"。基本形态：

```json
{
  "read": "doc._openid == auth.openid",
  "write": false
}
```

三种典型规则：

| 场景 | 规则 | 含义 |
|---|---|---|
| 用户私有 | `{"read": "doc._openid == auth.openid", "write": "doc._openid == auth.openid"}` | 只能读写自己的 |
| 公开只读 | `{"read": true, "write": false}` | 谁都能读，谁都别写（写走云函数） |
| 完全关闭 | `{"read": false, "write": false}` | 只允许云函数访问（云函数有管理权限） |

**原则：能关就关，能窄就窄。** 规则越简单越不容易写出漏洞；复杂业务判断放云函数里，因为云函数里的逻辑可测试、可 review。

## 四、索引

- 索引不是越多越好：每个索引都占空间并拖慢写入。
- 按**真实查询**建：`where` 的等值字段在前，`orderBy` 的字段在后。
- 列表页典型查询：`where({ status: 'on', deleted: false }).orderBy('createdAt', 'desc')` → 建 `(status, deleted, createdAt)` 组合索引。
- 分页用游标（上一页最后一条的 `createdAt`）比 `skip` 更快，`skip` 在大偏移量时性能很差。

## 五、字段类型上的三个坑

1. **金额用整数分**，不要用浮点。`0.1 + 0.2` 的问题在对账时一定会出现。
2. **日期存 Date 类型**，不要存字符串。字符串排序在跨时区时会错。
3. **数组字段不要无限增长**（比如把评论 ID 都存在商品文档里），会撞单文档大小上限。用独立集合并用关联 ID。

## 六、越权自测（交付前必做三条）

1. 用 A 账号登录，尝试读 B 账号的订单 `_id` → 应失败
2. 用 A 账号尝试直接改自己订单的 `status` 为 `paid` → 应失败（因为写入走云函数）
3. 在前端改请求参数，传别人的 `openid` → 云函数应以**服务端拿到的 openid** 为准，忽略前端传的
