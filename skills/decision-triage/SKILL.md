# G1 分诊：这到底是个什么决策

## 什么时候用

- 任何产品请求的第一道处理
- 有人说"这个要做吗"，但说不清为什么
- 材料零散（几条反馈、一张截图、一句老板的话）
- 你自己不确定该写 PRD 还是该劝退

## 输入

必需（缺了就问，不要猜）：
- 请求的原始表述（用户怎么说的，尽量原话）
- 决策截止时间

可选：
- 任何已有材料：反馈、工单、数据、截图、竞品链接、旧文档
- 涉及的指标与现在的值
- 谁提出的、谁受益、谁出人力

## 第一步：定门型

不是所有决策都值得同样的流程。先判门型，门型决定后面走多重的流程。

| 门型 | 判据 | 回滚成本 | 流程重量 |
|---|---|---|---|
| **R 可逆补丁** | 上线后一周内能改回来，影响单个模块 | 低 | 轻。不写 PRD，写一段说明 + 验收点，限时做完 |
| **O 单向门** | 涉及数据模型、定价、合同条款、公开承诺、账号体系 | 高，改了要迁移或赔钱 | 重。五闸全走 |
| **B 赌注** | 投入超过团队一个季度产能，结果高度不确定 | 高 | 重。五闸全走 + 必须写止损线 |
| **C 合规驱动** | 监管、平台规则、客户合同要求 | 不由你选 | 中。只讨论怎么做和什么时候，不讨论要不要 |
| **F 缺陷修补** | 已上线功能不符合既有预期 | 低 | 轻。不进优先级竞争，走缺陷通道 |

判定要点：

- **门型看回滚成本，不看工作量。** 一个三天的小改动如果改了计费口径，它是 O 不是 R。
- **C 型不要讨论"要不要"。** 用户如果问"C 型要不要做"，把问题改成"什么时候做、做到什么程度、怎么证明做到了"。
- **F 型不要和需求抢排期。** 这是最常见的组织病：修 bug 和做新功能在同一个池子里竞争，结果 bug 永远排不上。分开。

## 第二步：清点材料

列一张清单，不要凭印象。

| 材料 | 类型 | 证据等级 | 能用在哪 | 缺什么 |
|---|---|---|---|---|
| 例：3 条客户群里的抱怨 | 一手原文 | B | 证明痛点是真实的 | 不知道涉及多少客户 |
| 例：销售说"很多客户要" | 转述 | D | 只能作为线索 | 具体客户、具体场景 |

证据等级见 `evidence-ledger` 技能。这一步只要粗标，不必逐条论证。

清点完必须回答一句：**这些材料能支持的最强结论是什么？** 如果最强只能到"有几个客户提过"，就不要写"客户强烈需求"。

## 第三步：四问检验

四个问题，逐个过。答不出来的写"答不出"，不要用漂亮的措辞糊过去。

**问一：谁会因此改变什么行为？**
要具体到动作。"用户会更满意"不算。"仓库管理员不用再手工导表，改成在系统里直接确认"算。

**问二：这个行为变化影响哪个指标，能测吗？**
指标必须是你现在就有埋点或能查到的东西。指不出指标 → 这个需求没有成功标准，做完无法判断对错。

**问三：不做会怎样？代价多大、多久发生一次？**
代价要能说成钱、人力、时间或流失。说不出代价 → 这更接近偏好，不是需求。

**问四：现在做比三个月后做，多得到什么？**
时间价值说不出来 → 它可以排后面，不必占用当前产能。（例外：C 型合规有硬截止日期。）

判定：

- 四问答出三个以上 → 进入 G2 证据闸
- 答出一到两个 → 补材料，给最小取证清单
- 一个都答不出 → 不做，说明什么时候再来

## 第四步：选出口

### 出口一：做

给一句话立项理由，格式：
> 因为 [A/B 级证据] 显示 [具体人群] 在 [具体场景] 上 [具体损失]，做 [范围很小的动作] 可以改变 [可测指标]，所以进入 [门型] 流程。

然后进入 G2。

### 出口二：先补材料

给最小取证清单，三项以内，每项写清成本：

| 要补什么 | 怎么补 | 花多久 | 补到什么程度就够了 |
|---|---|---|---|
| 例：确认有多少客户遇到 | 查工单关键词 + 近 90 天 | 半天 | 拿到涉及客户数和工单原文各 3 条 |

**禁止**把"再调研一下"当出口。必须有具体动作、具体时限、具体停止条件。

### 出口三：不做

分三种不做，说法不一样：

- **不是产品问题**：是流程、人力或销售承诺的问题。指出真正该动的地方。
- **现在判断不了**：信息量不够，且补材料的成本高于先做一个小版本的试错成本。这时给"最小可试版本"而不是"再研究"。
- **不该做**：四问全不过，或者收益明显小于机会成本。要说清被挤掉的是什么。

## 输出：决策简报骨架

分诊阶段的输出要短，一屏以内：

```
【门型】O 单向门
【结论】不做。理由一句话。
【证据状态】最强到 B（3 条工单原文），缺影响范围。
【四问】问一 ✅ 问二 ✅ 问三 ❌ 问四 ❌
【下一步】补影响范围，半天，查工单关键词「导出失败」
【如果一定要做】最小范围：只做 X，不碰 Y，止损线：两周内 N 个客户使用
```

最后一行很关键。**分诊说"不做"时，永远给一个"如果一定要做"的最小版本**——因为很多时候决定权不在用户手里，他需要一个能在会上交出去的东西。

## 异常

| 情况 | 处理 |
|---|---|
| 用户只说"老板要做" | 追问老板的原话和目标。老板的原话通常是真实约束，转述常常失真。 |
| 用户已经写好了 PRD 让你看 | 先不看 PRD，先问四问。四问不过，PRD 越完整越危险。 |
| 用户情绪化（很急、很气） | 先把事实和情绪分开：他要解决的是哪个具体场景，不要回应情绪本身。 |
| 请求里有明显的方案预设（"我们做个 XX 页面"） | 把方案退回到问题上：页面解决的是哪个行为？有没有更便宜的方式达到同一效果？ |
| 涉及多个门型（既改数据模型又要合规） | 按最重的那个走。 |

## 与其他技能的关系

- 上游：无（这是入口）
- 下游：`evidence-ledger`（补证据）、`portfolio-fit`（若是排期问题）、`spec-handoff`（若是 R 型直接做）
- 分诊结论是 C 型合规时，直接跳 `spec-handoff`，压缩 G2–G4
