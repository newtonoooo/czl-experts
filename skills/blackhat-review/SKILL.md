# 评审模拟

## 什么时候用

- 稿子基本成型，想知道"大概能打多少分"
- 时间不够，必须决定先改哪一章
- 想听难听的话：这份标书哪里会让评委犹豫

## 输入

必需：分数地图（评分项与分值）。
必需：每项的预计得分率（0-1）。**这一项必须由人判断，脚本不代填、不猜、不给默认值。**
可选：历史入围线或已知对手分（用于判差距，不做名次预测）。
可选：竞争对手画像。

## 四类评委视角

| 视角 | 关心什么 | 常见扣分点 |
|---|---|---|
| 商务评委 | 资质、业绩、响应完整性 | 漏项、盖章位置错、业绩不匹配 |
| 技术评委 | 方案可行、接口清楚、风险有解 | 只有架构图没有落地步骤 |
| 使用方 | 上线后谁维护、培训够不够 | 承诺的功能实际用不上 |
| 财务 | 报价构成、付款节奏、变更条款 | 总价低但变更条款全是开口 |

## 步骤

1. **逐项打分**。每个评分项给 pess / mid / opt 三个数，每条写一句扣分理由。理由要具体到"第 3.2 节没有说明回滚触发条件"，不写"方案不够细"。
2. **汇总区间**。得到悲观/中性/乐观总分。区间宽说明判断没底，通常意味着评分口径没读透。
3. **对参考线**（有的话）。算差距；再算"全部追到乐观值够不够"。**如果拉满仍不够，就明说这不是改文字能解决的**，需要动报价或换打法。
4. **排追分**。追分 = 乐观值 − 中性值，除以预计工时。报价类不参与排序（那是决策项）。
5. **黑帽**。假想最强对手怎么打我们：价格、案例、交付承诺、关系。每条给出我方的一句话应对，写进稿子里。
6. **复核**。改完重跑一遍，看总分是否真的变了——没变的改动是白改。

## 判断

| 情况 | 处理 |
|---|---|
| 区间下限已低于参考线很多 | 先补硬伤（缺项、废标风险），不要润色 |
| 全部拉满仍不够线 | 明确告知：需要动报价策略、配置分档或联合体，文字改不动结果 |
| 某项区间宽 > 该项分值的 40% | 说明该项评分口径没读透，回原文重读 |
| 用户要求"预测能不能中" | 拒绝给结论。只给区间与假设，说明"分数不是名次" |

## 输出

`评审模拟报告.md`：三档总分、逐项表、最不确定三项、追分 Top5（含每小时追分）、黑帽应对表。
最后必写一节"这份模拟不能证明什么"。

## 脚本

```bash
python scripts/score_sim.py assess.json --md 评审模拟.md
```

`assess.json` 结构见 `templates/assess.schema.json`。缺 rate 时脚本直接报错并列出缺哪几项——这是故意的，防止用默认值糊过去。

## 异常

- 没有历史入围线：只做内部一致性检查，明确说"不做名次判断"。
- 评分项太多（30 项以上）：按分值排序只做前 15 项，其余合并成"其他"，并在报告里注明。
- 用户坚持要一个"中标概率"：给区间 + 假设 + 三项最敏感的变量，不给单一数字。
