# 条目写法细则

## 为什么条目比需求文档更要紧

需求文档写给人看，条目写给"验收"看。小程序最大的浪费不是写错代码，是**做完了发现不是要的东西**，或者**做完了发现验不了**。所以这个技能只认条目，不认"需求大概齐"。

## 一条合格条目的四个字段

| 字段 | 要求 | 反例 |
|---|---|---|
| `id` | `A-01` 起递增，永不重用 | 用"首页二期"这种名字 |
| `title` | 一句话说清做完是什么样，不超过 30 字 | "优化体验" |
| `verify` | 第三人能照做的验收动作 | "看着没问题" |
| `files` | 至少一个文件路径 | 空着（进 done 会被脚本拦） |

## 验证动作的四种合法形态

1. **点击路径型**：`点分类 tab → 进入对应列表页 → 返回后滚动位置保留`
2. **数值型**：`列表 20 条首屏耗时 < 300ms（真机中端机）`、`主包 ≤ 1.7MB`
3. **状态型**：`未登录可浏览；点下单才触发授权；拒绝授权后可继续浏览`
4. **文件型**：`app.json 含 requiredPrivateInfos: ["getLocation"] 且 permission.scope.userLocation.desc 非空`

不在这四类里的，基本就是"感觉型"，一律打回。

## 状态机（只有四态）

```
todo（未开始） → doing（开发中） → done（已完成·待验） → accepted（已验收）
```

规则：
- 只能前进，不能跳级（`todo` 不能直接 `accepted`）
- `done` / `accepted` 必须绑文件，否则 `ledger.py set` 直接报错
- 不做"基本完成""差不多了"——这类说法在交接时一定出事

## 条目怎么拆（拆到多细）

一个经验刻度：**一条 = 一个人半天能做完并自验的量**。

太粗：`做完整个下单流程`（这是 8-10 条）
太细：`把按钮圆角改成 8rpx`（进不了台账，写进代码注释即可）

推荐拆分维度（按这个顺序切）：
1. 页面能进得去（路由、tabBar、分包声明）
2. 页面有数据（接口、字段、空/错/加载三态）
3. 交互能闭环（提交、返回、失败重试）
4. 边界能兜住（未登录、无权限、断网、超时）
5. 体积在预算内（页面资源、图片处理）

## 与预算的联动

页面类条目在 `add` 时就把资源额度写进 `note`，例如：

```
ledger.py add docs/acceptance.json \
  --title "商品详情页" \
  --verify "从列表点进详情，图文正常，返回不丢滚动位置" \
  --files pages/goods/detail/detail.js \
  --gate W2
```

图片超过 200KB 的，在 note 里写 `图片额度 ≤ 120KB，超了先压`。

## 反模式清单

| 反模式 | 为什么不行 |
|---|---|
| 条目里写技术方案（"用云函数实现"） | 验收标准被方案绑死，方案变了条目就废 |
| 条目里写工期 | 工期不是验收标准，且会诱导跳步 |
| 一条里塞三个不相关功能 | 没法判"完成"，也没法定位 bug |
| 用"支持 XX"当条目 | "支持"是能力描述，不是验收动作 |
| 把 bug 修复写成条目但不写复现路径 | 修没修好无法判定 |
