# 验收条目写法

一条好的验收条目，读完之后两个人能得出同一个结论：**过了，还是没过。**

做不到这一点的，都还是愿望，不是条目。

---

## 四要素

| 要素 | 作用 | 不合格的样子 |
|---|---|---|
| 操作 | 谁做了什么 | "系统应该处理订单" —— 谁？怎么处理？ |
| 预期 | 可观察的结果 | "体验流畅" —— 无法观察 |
| 反例 | 出错的路径 | 只写正常流程，等于只验了一半 |
| 证据 | 怎么留证 | "测试过了" —— 谁测的、跑了什么 |

---

## 改写示例

**改前（不可验收）**

> 登录功能要做安全，密码不能明文存。

问题：安全到什么程度算够？谁是攻击者？怎么证明？

**改后（可验收）**

```
A4 密码存储
   操作：注册一个账号，用任意密码
   预期：数据库中该用户记录里查不到明文密码；字段值长度固定且每次注册同一密码结果不同
   反例：用同一密码注册两个账号，两个字段值必须不同
   证据：注册后查库输出的字段片段（截断，不贴完整值）
```

**改前**

> 列表页加载要快。

**改后**

```
A7 列表首屏
   操作：在 1 万条数据的库上打开列表第一页
   预期：响应时间 < 800ms（本地环境，测得 3 次取中位数）
   反例：翻到最后一页、请求不存在的页码，均返回正常空列表而非报错
   证据：三次请求的耗时输出
```

## 三类必须写的反例

大部分线上事故来自这三类，定桩阶段不写，验证阶段一定想不起来。

| 类别 | 典型反例 | 对应的验收写法 |
|---|---|---|
| 越权 | 改 URL 里的 id 访问别人的数据 | 用 A 账号的凭据请求 B 的数据，预期 403/404，而不是 200 |
| 重复 | 连点两次提交、网络超时重试 | 预期只产生一条记录，第二次返回同样结果而不是新建 |
| 空与异常 | 空列表、超长文本、特殊字符、时区 | 预期不崩溃、不返回 500、不把原始堆栈给到前端 |

## 禁止的写法

| 不要写 | 因为 | 改成 |
|---|---|---|
| 支持多种格式 | 多种是哪几种 | 列出接受的 3 种扩展名，其他报错 |
| 权限要合理 | 合理谁来定 | 列出角色 × 动作的允许表 |
| 出错要友好 | 友好无法核对 | 给出具体提示文案与状态码 |
| 性能要达标 | 达标线在哪 | 给数值、给环境、给测量方法 |
| 兼容旧版本 | 旧版本是哪个 | 给出必须兼容的版本号与回归项 |

## 条目与代码的对应

每条条目在实现时要能指出"这条由哪个文件/函数负责"。做不到，说明这条要么太抽象，要么跨了多个切片。

建议在切片时附一行映射：

```
切片 S2（写订单）
  覆盖：A3 下单成功 / A4 重复提交只生效一次
  不覆盖：A6 支付回调（属于 S4）
```

切片做完，只销对应编号，不替别的编号签收。

---

## 条目作废与变更

- 不要删编号。删掉的划掉并注明"作废：<原因>"，编号不复用。
- 需求变更时新增编号接在最后，不插队——编号顺序就是讨论历史。
- 交付时把"未验条目"单独列一节，写清为什么没验（缺环境、缺账号、留到二期）。
