# 闸门：验证与上线

这一段只有一个目的：**在用户发现问题之前，先自己发现问题。**

它不负责让功能变好，只负责回答两个问题：能不能上？上了出事怎么退？

---

## 何时用

- 切片写完，要判断"算不算完成"
- 要上线，尤其是涉及数据迁移、支付、权限变更
- 已上线出问题，要回滚或热修
- 要交给别人维护，需要一份能照着跑的说明

---

## 三层验证

缺一层就不算验证过。三层的关系是**逐层加真实度**，不是三种可选方案。

### L1 · 单元与接口层

**验什么：** 单个函数/接口在边界值下的行为。

必测四类：

| 类别 | 用例 |
|---|---|
| 空 | 空字符串、空数组、null、未传字段 |
| 极端 | 超长文本、超大数值、负数、零 |
| 类型/格式 | 错误类型、非法字符、错位 JSON、错误时间格式 |
| 重复 | 同一请求连发两次、超时后重试 |

**证据：** 测试运行的输出，或一组 `curl` 的返回。

**不算通过的：** 只跑了 linter；只跑了 happy path；测试里全是 mock 的自言自语。

### L2 · 集成层

**验什么：** 和真实依赖一起跑一次。

- 真数据库（不是内存替身），跑一次迁移 + 一次完整读写
- 真第三方（用沙箱环境），走一次成功和一次失败分支
- 真文件系统 / 真队列，确认写入位置和消费行为

**证据：** 真实调用的日志片段（含时间与请求标识），或数据库查询结果。

**不算通过的：** 用 mock 返回固定值就宣布"集成没问题"。mock 通过只证明你的假设自洽。

### L3 · 端到端层

**验什么：** 按验收条目当用户走一遍。

- 从入口开始（页面登录 / 接口首次调用），不跳过中间步骤
- 每条验收条目走一次，附截图或命令输出
- 反例也走：越权访问、重复提交、中途退出

**证据：** 截图 / 录屏 / 命令输出，与条目编号一一对应。

**不算通过的：** "我自己点过一遍" —— 没有证据等于没有记录。

## 上线闸门

六项，缺一项就不该上。做不到的必须**在上线前明说**并给临时兜底。

| # | 项 | 合格线 | 做不到时 |
|---|---|---|---|
| 1 | 迁移可回退 | 有 down 脚本，或在接近生产数据量上试过 | 上线前手动全量备份，写明恢复步骤 |
| 2 | 备份可恢复 | 至少演练过一次恢复 | 上线前导出一份并核对条数 |
| 3 | 健康检查 | `/health` 与 `/ready` 能返回，失败能被监控抓到 | 至少保证有一个可探测的端点 |
| 4 | 错误可查 | 有 requestId，能从一条报错捞到完整链路 | 上线后前 24 小时人工盯日志 |
| 5 | 回滚可执行 | 命令写下来并真的执行过一次 | 不能上；没有回滚手段的上线不是上线 |
| 6 | 指标有阈值 | 知道错误率/延迟超过多少要停 | 定一个临时阈值，上线后补齐 |

第 5 条是硬线。**没有回滚方案的上线请求，应该被拒绝**，包括对自己的项目。

---

## 判断条件

| 情形 | 判断 | 动作 |
|---|---|---|
| L1 过、L2 没过 | 未验证 | 补集成验证，不许用"逻辑很简单"跳过 |
| 三层都过，但闸门缺 3 项 | 不可上线 | 补齐或降级为内部试用 |
| 只改前端文案 | 可简化 | L1 跳过，L3 走主链路一次 |
| 只改配置 | 需重启验证 | 验证启动成功 + 关键接口一次 |
| 数据迁移涉及删列 | 高风险 | 改成分步迁移，不在一批里删 |
| 上线后错误率超过阈值 | 立即回滚 | 先恢复，再排查，不在生产上调 |

---

## 输出格式

```
验证结论
L1 <项数> 条：通过 X / 不通过 Y / 未验证 Z（原因）
L2 <依赖列表>：通过 / 不通过 / 未验证
L3 验收条目：A1 通过、A2 通过、A3 未验证（缺账号）

闸门
1 迁移 2 备份 3 健康检查 4 错误可查 5 回滚 6 指标 —— 逐项 ✅ / ❌ + 一句说明

结论：可上线 / 有条件上线（条件：…） / 不可上线（原因：…）
```

"有条件上线"必须写清条件由谁满足、什么时候复核。含糊的"差不多可以上"不算结论。

---

## 与其他技能的关系

- `czl-dev-spec` 给出验收条目 → 这里逐条销号
- `czl-dev-build` 给出实现约定 → 这里检查是否守住
- 上线后发现问题 → 回到实现，修完重跑对应层，不跳层

---

## 异常处理

- **验证发现的是设计问题**（不是代码 bug）：停下来回 `czl-dev-spec`，改条目再改代码，不要在实现层硬凑
- **上线后才发现没验的条目**：立即记录到交付说明的"未验"一节，不追补成"已通过"
- **回滚失败**：停止一切修复动作，先保住数据（读库、导表），再定位。修复顺序是"止血 → 恢复 → 查因"
- **无法验证的部分**（缺环境、缺账号、缺第三方沙箱）：写清缺什么，交付时列为已知限制，不要用"应该没问题"填坑
