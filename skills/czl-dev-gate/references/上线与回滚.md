# 上线与回滚

## 一、上线顺序

固定顺序，不要按方便程度调整。

```
1 备份（可恢复的那种）
2 迁移（可回退的那种）
3 部署（可回滚的那种）
4 冒烟（3—5 个关键动作）
5 观察（前 30 分钟）
6 宣布完成 / 或回滚
```

### 1. 备份

- 数据库：全量导出或快照，记录时间点
- 用户上传的文件：确认对象存储版本或快照可用
- 配置：把本次要改的环境变量先记下来（旧值也要）

备份的目的是**能回去**。没验证过能恢复的备份，只是一份心理安慰。

### 2. 迁移

- 先在生产副本上试一次，记录耗时
- 破坏性操作分步：加新列 → 双写 → 回填 → 切读 → 停旧列 → 删旧列（中间可停）
- 迁移期间不要同时改代码逻辑，否则出问题分不清是谁引起的

### 3. 部署

- 能从构建产物部署，不从本地目录 rsync
- 灰度或分批：先 1 台 / 10% 流量，观察，再全量
- 部署记录写清：版本号、提交、时间、执行人

### 4. 冒烟

部署完立刻做的 3—5 件事，固定下来，每次都一样：

```
① /health 返回 200
② 登录一次
③ 走一次核心写操作（下一单 / 发一条）
④ 看一眼错误日志有没有新增 error
⑤ 看一眼关键接口耗时
```

### 5. 观察

前 30 分钟盯三个数：错误率、慢请求、关键业务动作的成功数。

**阈值示例（按项目调）：**

| 指标 | 正常 | 停止发布 | 立即回滚 |
|---|---|---|---|
| 5xx 占比 | < 0.1% | > 0.5% | > 1% 持续 5 分钟 |
| 核心接口 p95 | < 500ms | > 800ms | > 1500ms |
| 关键动作成功数 | 与基线持平 | 下降 30% | 归零 |

## 二、回滚

### 回滚也要写命令

```bash
# 应用回滚（按实际平台改）
# 例：容器平台回滚到上一个版本
deploy rollback --service api --to <previous-version>

# 迁移回滚（仅当本次迁移不可与新代码共存时）
node scripts/migrate.js down --to <previous-migration>

# 缓存清理（如果缓存里存了旧结构的数据）
redis-cli FLUSHDB   # 谨慎：确认无其他业务共用

# 验证
curl -s -o /dev/null -w "%{http_code}" https://<host>/health
```

### 回滚的三个判断

| 情况 | 处理 |
|---|---|
| 新代码有 bug，迁移是加列（兼容旧代码） | 只回滚应用，迁移保留 |
| 迁移改了语义，旧代码读不了新数据 | 应用与迁移一起回滚 |
| 数据已被写坏 | 停止写入 → 从备份恢复到新库 → 切换 → 核对 → 再排查 |

**顺序永远先止血再查因。** 在生产上边查边改，是把一次故障变成两次。

## 三、上线后 24 小时

| 时段 | 看什么 |
|---|---|
| 0—30 分钟 | 健康检查、错误日志新增、核心动作成功数 |
| 30 分钟—2 小时 | 慢请求、内存/CPU 是否持续爬升、队列是否积压 |
| 2—24 小时 | 用户反馈、业务指标（转化/下单/留存）是否偏离基线 |

出现下面任一，按故障处理，不按"再观察观察"处理：

- 核心动作成功率下降超过 10%
- 错误率是新版本前的 3 倍以上
- 内存持续上涨且不回落（疑似泄漏）

## 四、热修的边界

允许热修（不回滚直接改）：

- 一行配置错误、拼写错误
- 单个接口的明显逻辑错误，且改动范围可数清

不允许热修：

- 数据迁移相关
- 涉及权限与支付的判断逻辑
- 需要改表结构
- 你还没定位到根因

不确定时一律回滚。回滚不丢人，带着问题硬撑才丢人。

## 五、故障记录（每次都要写，哪怕很小）

```
时间：<开始 — 恢复>
现象：<用户看到了什么>
影响面：<多少人 / 哪些功能 / 是否涉及数据>
根因：<一句话，回到具体那行代码或那次配置>
处理：<回滚 or 热修，做了什么>
遗留：<还需要补的测试 / 监控 / 文档>
```

写故障记录不是为了追责，是为了下次能被检索到。写"操作失误"这种结论等于没写。
