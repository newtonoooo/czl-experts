# 接口与数据约定

## 一、幂等：写操作必须考虑重复

用户连点两次、网络超时自动重试、移动端切后台再回来——重复请求是常态，不是异常。

三种实现，按成本从低到高：

### 1. 唯一约束（最省事）

```sql
ALTER TABLE invoices ADD CONSTRAINT uq_invoice_by_request UNIQUE (tenant_id, client_ref);
```

重复请求撞唯一键，捕获冲突后返回已存在的记录。适合"创建类"操作。

### 2. 幂等键表

```sql
CREATE TABLE idempotency_keys (
  key TEXT PRIMARY KEY,
  result JSONB NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

第一次请求写入结果；后续同 key 请求直接返回缓存的 result。适合"有副作用且要返回结果"的操作（支付、扣库存）。

要点：key 由客户端生成并随请求带上；服务端要对 key 加过期清理，否则表会一直涨。

### 3. 状态机前置判断

```sql
-- 只有状态允许时才推进，天然幂等
UPDATE orders SET status = 'paid' WHERE id = ? AND status = 'pending';
-- 影响行数为 0 说明已经处理过或状态不对
```

适合状态流转类操作。注意：影响行数要检查，不检查等于没做幂等。

**不要用"前端按钮禁用"当幂等方案。** 那是体验优化，不是数据保护。

## 二、分页

| 方式 | 适用 | 坑 |
|---|---|---|
| 偏移分页 `LIMIT ? OFFSET ?` | 后台列表、数据量小 | 数据插入时翻页会重复/漏项；深翻页慢 |
| 游标分页 `WHERE id < ? LIMIT ?` | 信息流、无限滚动 | 不能跳页；排序字段要唯一 |
| 计数分离 | 需要总数时 | `COUNT(*)` 大表很慢，可缓存或给近似值 |

硬约束：**OFFSET 必须由服务端算，且限制最大值**（例如不超过 10000），否则一条精心构造的请求能把库拖死。

`pageSize` 上限要写死（常见 100），不要相信客户端传来的 100000。

## 三、N+1 与过度取数

### 症状

- 列表接口响应时间随条数线性增长
- 日志里一次请求出现几十条结构相同的 SQL
- 内存占用突然变高，且与返回条数无关

### 典型改法

```js
// 差：循环里查
for (const order of orders) {
  order.user = await db.query('SELECT * FROM users WHERE id = ?', [order.userId]);
}

// 好：一次 IN
const ids = [...new Set(orders.map(o => o.userId))];
const users = await db.query('SELECT id, name FROM users WHERE id IN (?)', [ids]);
const map = new Map(users.map(u => [u.id, u]));
orders.forEach(o => { o.user = map.get(o.userId) ?? null; });
```

顺带一条：**只选需要的列。** `SELECT *` 在宽表上会把大字段（文本、JSON、二进制）一起拉过来，改一个只需要 id 和 name 的接口，可能省掉 80% 的传输。

### 索引

改查询时顺手确认索引存在：

- `WHERE` 里出现的列，看执行计划（`EXPLAIN`）是否走索引
- 联合索引注意最左前缀
- `LIKE '%x%'` 基本用不上索引，数据量大时考虑全文索引或搜索服务
- 排序字段与过滤字段组合时，索引顺序按"过滤在前、排序在后"设计

不要凭直觉加索引。加之前看一眼执行计划，加之后再看一眼。

## 四、迁移

三条纪律：

1. **进版本库。** 表结构只存在于某台机器的数据库里，等于没有表结构。
2. **可回退。** 每个迁移写 `up` 与 `down`；删列、改类型这类不可逆操作，用"新建列 → 双写 → 迁移数据 → 停旧列"分多步做。
3. **先在接近生产的数据量上试。** 小表上加索引 100ms，千万行上可能锁表十分钟。

迁移的命名带时间戳，按序执行，不要手工在数据库里改结构——手工改过的地方迟早和迁移文件对不上。

## 五、鉴权与越权

最常见的漏洞不是加密不够，是**忘了校验资源归属**。

```js
// 危险：只查了 id，没查归属
const order = await repo.findById(req.params.id);

// 安全：把归属写进查询条件
const order = await repo.findOne({ id: req.params.id, userId: req.user.id });
if (!order) return notFound();   // 不区分"不存在"和"不是你的"，避免探测
```

三条检查：

- 每个带资源 id 的接口，问一句"这条数据是不是当前用户的"
- 管理端接口单独鉴权，不要靠"路径不好猜"
- 返回 404 而不是 403，避免暴露资源是否存在

## 六、对外调用

- 全部设置超时（连接超时与读取超时分开设）
- 可重试的错误才重试（网络抖动、5xx），业务错误（4xx）不重试
- 重试要退避（指数 + 抖动），且总时长有上限
- 第三方密钥只放服务端，绝不下发到前端
- 回调接口校验签名，校验失败不落库
