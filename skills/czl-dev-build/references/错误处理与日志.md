# 错误处理与日志

## 一、错误要有类型，不要都用同一个 Exception

一个笼统的 `Error('出错了')` 到上层之后，除了返回 500 什么也做不了。

```ts
// shared/errors.ts
type FailureSpec = {
  code: string;        // 给前端用的稳定错误码
  message: string;     // 给用户看的提示
  httpStatus?: number;
  detail?: unknown;    // 只进日志，不出响应
};

export class ApiFailure extends Error {
  readonly code: string;
  readonly httpStatus: number;
  readonly detail?: unknown;

  constructor(spec: FailureSpec) {
    super(spec.message);
    this.code = spec.code;
    this.httpStatus = spec.httpStatus ?? 400;
    this.detail = spec.detail;
  }
}

export class InvalidInput extends ApiFailure {
  constructor(detail: unknown) {
    super({ code: 'INVALID_INPUT', message: '提交的内容有误，请检查后重试', httpStatus: 400, detail });
  }
}

export class Missing extends ApiFailure {
  constructor(what = 'resource') {
    super({ code: 'NOT_FOUND', message: '内容不存在或已被删除', httpStatus: 404, detail: { what } });
  }
}

export class Denied extends ApiFailure {
  constructor(detail?: unknown) {
    super({ code: 'FORBIDDEN', message: '没有权限执行此操作', httpStatus: 403, detail });
  }
}

export class Conflicted extends ApiFailure {
  constructor(detail?: unknown) {
    super({ code: 'CONFLICT', message: '操作冲突，请刷新后重试', httpStatus: 409, detail });
  }
}
```

要点：

- `code` 稳定不变，前端据此做分支；`message` 可以改文案，前端不要依赖它做逻辑
- 业务错误用 `ApiFailure` 的子类；意外错误让它自然抛出，由全局处理器兜 500
- `detail` 只进日志，永远不出响应
- 用对象传参而不是位置参数：四个字段里有三个可选，位置参数迟早会传错顺序

## 二、全局处理器：一个出口

```ts
app.use((err, req, res, next) => {
  const requestId = req.id;

  if (err instanceof ApiFailure) {
    logger.warn('app_error', { requestId, code: err.code, detail: err.detail, path: req.path });
    return res.status(err.httpStatus).json({ ok: false, code: err.code, message: err.message });
  }

  // 意料之外的错误：日志里全量，响应里什么都不给
  logger.error('unhandled_error', { requestId, err });
  return res.status(500).json({ ok: false, code: 'INTERNAL_ERROR', message: '服务暂时不可用，请稍后重试' });
});
```

两条铁律：

1. **对外响应的内容由处理器统一决定**，业务代码不要自己 `res.status(500).send(e.stack)`。
2. **意外错误一律 500 + 通用文案**，堆栈只进日志。生产环境尤其。

## 三、日志字段

一行一条，结构化，字段固定：

| 字段 | 必填 | 说明 |
|---|---|---|
| `ts` | 是 | ISO 8601，带时区 |
| `level` | 是 | `debug` / `info` / `warn` / `error` |
| `event` | 是 | 事件名，短、下划线，例如 `order_created` |
| `requestId` | 是 | 贯穿一次请求；异步传递时用上下文传递，不要靠参数层层传 |
| `userId` | 视情况 | 有登录态时带上，便于定位"谁遇到的" |
| `durationMs` | 视情况 | 对外调用、慢查询 |
| `err` | 错误时 | 类型、message、stack |

示例：

```json
{"ts":"2026-10-26T03:12:44.120Z","level":"warn","event":"app_error","requestId":"r-8f21","code":"CONFLICT","path":"/api/orders"}
```

**反例：** `console.log('创建订单', order)` —— 没有时间、没有级别、没有请求标识，还把整条订单（含手机号）打进日志。

## 四、脱敏

| 字段 | 处理 |
|---|---|
| 密码 | 永不记录 |
| 令牌 / 密钥 / Cookie | 永不记录；排障需要时记录前 4 位 + 长度 |
| 手机号 / 邮箱 | 中间打码，例如 `138****1234` |
| 身份证 / 银行卡 | 只记录后 4 位 |
| 完整请求体 | 默认不记；需要时按白名单挑字段 |

一个常见事故：为了排查问题把请求体全量打进日志，几个月后日志服务被导出，用户手机号全在里面。

## 五、级别怎么定

| 级别 | 什么时候用 | 生产环境 |
|---|---|---|
| debug | 开发期细节 | 关闭 |
| info | 正常业务事件（下单成功、任务完成） | 开 |
| warn | 可恢复的异常（重试成功、参数被纠正、降级生效） | 开 |
| error | 需要人看的（未处理异常、关键依赖不可用、数据不一致） | 开，且应触发告警 |

判断标准：**这条日志出现时，有没有人需要动手？** 需要，就是 error；不需要但值得记，就是 info / warn。

日志级别用错最典型的后果是告警疲劳——满屏 error，真正的问题被淹掉。

## 六、健康检查与可观测的最低配置

| 端点 | 检查什么 | 注意 |
|---|---|---|
| `/health` | 进程活着 | 不做重活，别在这里查库 |
| `/ready` | 能接流量（依赖就绪） | 可以查库连通性，失败返回 503 |

最小可观测配置（上线前至少这三样）：

1. 错误率能看（按分钟或五分钟统计 5xx 占比）
2. 慢请求能看（超过阈值的请求单独记录）
3. 一次请求能被串起来（同一个 requestId 的所有日志）

没有这三样，线上出问题时你只能靠用户描述猜。

---

## 七、日志与合规

- 日志有保留期限，不是永久保存
- 日志服务访问权限要收紧，它往往比数据库更容易泄露
- 涉及个人信息的日志，导出与共享要有记录
- 用户要求删除数据时，日志里的那份也要处理
