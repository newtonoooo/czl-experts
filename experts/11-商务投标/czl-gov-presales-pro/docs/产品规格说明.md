## 一、目标用户与使用场景

### 1.1 用户画像

| 角色 | 真实处境 | 最想要的东西 |
|---|---|---|
| 集成商售前工程师 | 一人跟 3–5 个项目，方案写到凌晨，标书细节靠记忆 | 一个能替他记住条款、并按评分表排篇幅的东西 |
| 销售/客户经理 | 关系能打通，但判断不了"这项目能不能打" | 一页纸结论，好拿去跟领导要资源 |
| 小型软件公司老板 | 没有专职售前，技术负责人兼着写标书 | 别在废标这种低级问题上翻车 |
| 新入行的售前 | 不知道从哪儿下手，容易照抄网上的方案 | 一套能照着走的流程 + 每步的产出物 |

### 1.2 典型场景

1. **看到采购意向公告**：判断要不要提前接触客户、要不要投人力做方案。
2. **拿到招标文件**：48 小时内判断能不能投、缺什么材料、哪些条款是坑。
3. **方案期**：评分表贴在墙上，需要知道每一章写多少页、必须写什么。
4. **交标前 3 天**：全组人对着清单打钩，怕漏密封、漏签字、漏原件。
5. **答辩前一天**：需要 15 分钟脚本和被追问时的答法。
6. **中标后**：交付团队问"标书里到底承诺了什么"。

### 1.3 不适用场景

- 纯土建、货物采购类招标（规则差异大，本产品的规则库不覆盖）。
- 涉密项目（分保体系，不在等保框架内）。
- 需要出具法律意见的争议（应找律师）。

## 二、要解决的问题（按痛感排序）

| # | 问题 | 后果 | 本产品的处理 |
|---|---|---|---|
| P1 | 资格差一条，方案白做 | 直接无效投标 | 资格项设为一票否决，不参与加权，先卡再算 |
| P2 | 废标条款藏在正文第 37 行 | 交标当天被拒收 | 19 条规则按行号扫，分三级，给到具体动作 |
| P3 | 方案结构与评分表错位 | 高分项写得少，低分项写得多 | 按分值分配页数，0 分项压到 1 页 |
| P4 | 报价凭感觉 | 低于成本中标，或高得没竞争力 | 三档成本 + 价格分敏感性 + 让利方式替代纯降价 |
| P5 | 合规写成空话 | 技术分丢分，答辩被问穿 | 等保/密评/信创落成可勾选矩阵，要求"型号 + 证据" |
| P6 | 售前承诺交付不了 | 中标即亏损 | 承诺台账 + 偏差红线，交接前解决 |
| P7 | 判断全靠老售前的直觉 | 人一走，经验就没了 | 打分模型固定权重，结论可复核、可复盘 |

## 三、输入与输出

### 3.1 必要输入

| 关口 | 最少需要什么 | 缺了怎么办 |
|---|---|---|
| 机会判断 | 项目名、客户、预算、资格是否满足、七维自评 | 缺 3 项以上 → 输出"待定" + 必补清单 |
| 需求共创 | 客户访谈记录或会议纪要 | 无记录 → 先给访谈提纲，不硬写方案 |
| 方案 | 评分表（评分项 + 分值）、页数上限 | 无评分表 → 按经验结构出骨架，并标注结构性失分风险 |
| 标书体检 | 招标文件文本（txt/md） | PDF/Word → 先转文本；纯扫描件 → 需 OCR，本产品不做 |
| 报价 | 成本测算、价格分公式、预算上限 | 成本不全 → 用区间估值并标注误差 |
| 答辩 | 方案定稿、评委构成 | 无评委信息 → 按四类角色通用质询库准备 |
| 交接 | 投标文件全文 | 无全文 → 用承诺台账模板逐条回忆补录 |

### 3.2 输出（三档交付深度）

| 档位 | 触发条件 | 形态 | 硬性要求 |
|---|---|---|---|
| 决策备忘 | "投不投" | 1 页 | 结论 + 三条理由 + 风险 + 下一步（含责任人） |
| 体检报告 | 拿到招标文件 | 3–8 页 | 分级风险表（行号 + 原文 + 后果 + 动作）、响应表、材料清单 |
| 完整方案 | 正式投标 | 按评分表 | 章节对齐评分项、架构说明、量化价值、合规矩阵 |

统一写作规则：结论先行；数字带来源与口径；结论标 `[事实]/[推测]/[建议]`；风险写"证据 + 后果 + 动作"。

## 四、通用处理步骤（七关）

```
机会雷达 → 需求共创 → 方案成形 → 标书体检(硬闸门) → 报价商务 → 答辩演练 → 中标交接
   │            │           │            │              │           │          │
 投/不投      建设内容     方案         废标清零        价格区间     脚本      台账
```

每关的职责、输入、步骤、判断条件、输出、异常、依赖已在 `agents/czl-gov-presales-pro.md` 中逐条写明；本文件只规定"必须存在这些环节，且环节之间有硬闸门"，不重复其表述。

**关键设计决策：为什么体检在方案之后、报价之前？**
因为体检的结论会改方案（漏响应的条款要补写）和改报价（缺业绩要评估扣分后是否还值得投）。顺序错了，返工两遍。

## 五、工具能力要求

| 能力 | 要求 | 实现 |
|---|---|---|
| 加权打分 | 权重合计 1.00；一票否决独立于加权；缺项归一化不按 0 分 | `radar.py score` |

| 自检 | 覆盖正常/异常/反向用例 | `selftest.py` |

技术要求：纯 Python 标准库，Windows / macOS / Linux 通用；输出 UTF-8；脚本可独立于对话运行。

## 六、质量、速度、稳定性

| 维度 | 指标 | 当前实测 |
|---|---|---|
| 速度 | 51 万字招标文件扫描 | 0.58 s（见测试报告 T12） |
| 稳定性 | 空文件/坏 JSON/缺字段 | 报错退出码非 0，不静默产出错误结论 |
| 可复核性 | 每条结论能否追溯到输入 | 打分表可逐维核对；体检报告带行号原文；页数分配可按公式复算 |

| 诚实性 | 不给无依据的数字 | 不输出中标概率；缺信息标"待定" |

## 七、与参考对象的功能关系（独立实现声明）

本产品在**功能层面**覆盖并扩展了"政府数字化售前顾问"这一类产品的通用能力（政策解读、方案设计、招投标支持、合规要求、客户关系）。功能是公共需求，不构成他人专有表达。

在此基础上，本产品做了以下**补充与改进**，均为独立设计：

1. **把流程改成关口制并设硬闸门**：体检未闭环不得进入排版，这是原类产品中常见的缺口（多为线性五步流程，无强制阻断点）。
2. **判断从定性改为可计算**：七维加权 + 一票否决 + 短板排序，结论可复核，不依赖个人经验。
3. **体检从清单改为按行号定位**：直接指到"第 37 行"，并给"为什么致命 + 做什么"，而不是给一张通用 checklist。
4. **方案篇幅与评分分值绑定**：解决"高分项写少了"这个最常见的结构性失分。
5. **合规从原则改为矩阵**：等保按级别过滤、密评按八个层面、信创按层次给型号与验证要点。
6. **补齐了原类产品普遍缺失的两块**：报价策略（成本三档 + 价格分敏感性）与中标交接（承诺台账 + 偏差红线）。
7. **工程化交付**：脚本可独立运行、有自检用例、有包完整性检查（专治导入后头像丢失）、有版本与许可文件。
