## 二、开发过程（按时间顺序）

### 阶段 1：功能分析（不做复制）

1. 完整读取参考产品的全部文件：`plugin.json` 元数据、主提示词 380 行、两个随包技能（deep-research、minimax-docx）、README、头像。
2. 提取**功能需求**而非文案：目标用户（集成商售前）、五类能力（政策/方案/招投标/合规/客户关系）、五步流程、四份模板、八项成功指标。
3. 判断哪些是"可独立实现的通用方法"（如"先判断机会再投方案""案例要可核验"），哪些是"受版权保护的具体表达"（提示词原文、模板文本、文档段落、头像图片）。
4. 结论：**功能可以继承，表达必须重写，素材必须重做。** 这条结论写进了 `docs/产品规格说明.md` 第七节。

### 阶段 2：产品定位与命名

1. 花名从"功能 + 气质"出发：投标要的是"胜"，取名 **标胜**（Bidwin）。
2. 职业头衔对标参考产品的"政府数字化售前顾问"，按你的要求前置了限定词并体现全流程：**政府数字化售前中标全流程顾问**。
3. 包标识按要求 `czl-` 前缀 + 功能名：`czl-gov-presales-pro`。
4. 查重：比对本地 27 个已有专家，无同名、无同职业、无同分类冲突（07 分类下现有的是电商、抖音、直播方向，无政务售前）。

### 阶段 3：架构设计（与前作结构不同）

把线性五步改成**关口制 + 硬闸门**，理由是原结构缺一个"必须停下来"的点：

```
线性流程的缺陷：方案写完 → 直接进排版 → 交标 → 发现漏了密封要求
关口制的改法：方案写完 → 体检（废标项未闭环则禁止进入排版） → 才允许装订
```

七关里第四关是唯一不可跳过的，这条写进了主提示词。

### 阶段 4：实现

1. 先写主提示词（294 行），确定七关的职责边界与产出物。
2. 再写四个技能，每个技能遵循"能算的算"原则：打分、扫描、分配、生成，全部落成脚本。
3. 补两个工具：`pack_check.py`（解决你提出的头像问题）、`avatar_norm.py`（在没有 Pillow 的环境里处理头像）。
4. 写 12 项用例，跑通后再写文档——文档里的数字全部来自实际运行。

### 阶段 5：验证与修复

详见 `docs/功能测试报告.md` 第五节。四个真实缺陷：贡献值口径错、用例框架空消息崩溃、页数超限、头像带角标，均已修复并重跑通过。

### 阶段 6：交付

平台校验通过、包自检 9/9、用例 12/12、打包为 zip。

## 三、关键设计决策（留痕用）

| 决策 | 选择 | 理由 | 放弃的方案 |
|---|---|---|---|
| 资格项是否参与加权 | 不参与，单设一票否决 | 高分掩盖废标是最危险的误判 | 加权后总分高就投 |
| 缺维度怎么算 | 按已给维度归一化 | 缺项按 0 分算会系统性低估 | 缺项记 0 |
| 是否输出中标概率 | 不输出 | 没有历史数据支撑的概率是编的 | 给一个"成功率 60%" |
| 体检放在方案前还是后 | 放在方案后、报价前 | 体检结论同时影响方案补写与报价决策 | 先体检再写方案 |
| 合规矩阵是否抄标准条文 | 不抄，按类别归纳自有表述 | 避免版权风险；条款号可按需另补 | 直接摘录标准条文 |
| 头像处理依赖 | 纯标准库自研 | 环境装不上 Pillow，且需要长期可维护 | 依赖 Pillow |
| 是否随包附带 deep-research / minimax-docx | 不带 | 第三方组件权利与许可需单独核实，且与本品核心功能非必需 | 直接拷贝原包技能目录 |

## 四、与参考产品的差异（功能层面对照）

| 维度 | 参考产品（同类通用做法） | 本产品 |
|---|---|---|
| 流程形态 | 五步线性 | 七关制，含一道硬闸门 |
| 机会判断 | 定性评估表 | 七维加权 + 一票否决 + 短板排序，可复算 |
| 标书检查 | 通用清单 | 19 条规则按行号定位，分三级，给动作 |
| 方案结构 | 按模板章节 | 按评分分值分配篇幅，标每章必含要素 |
| 合规 | 原则性章节 | 等保 72 项 / 密评 13 项 / 信创 10 项矩阵 |
| 报价 | 未覆盖 | 三档成本 + 价格分敏感性 + 让利设计 |
| 交接 | 未覆盖 | 承诺台账 + 偏差红线 |
| 工程化 | 提示词 + 文档 | 提示词 + 4 技能 + 3 工具 + 12 用例 + 包自检 |
| 素材 | 自带头像与品牌 | 全部重新设计 |
