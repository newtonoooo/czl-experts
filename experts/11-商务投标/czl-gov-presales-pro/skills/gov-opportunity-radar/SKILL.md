# 机会雷达（gov-opportunity-radar）

这个技能只做一件事：把"要不要投"从感觉变成能复核的分数。
分数不是我拍脑袋给的权重，而是先卡一票否决项，再算加权分，最后把最拖后腿的两三项挑出来。

## 一、什么时候用

| 用户说的 | 用哪条命令 |
|---|---|
| "这项目能不能投" / "值不值得跟" | `score` |
| "我手上有这些信息，怎么填" | `template` |
| "这份评估数据全不全" | `check` |
| "预算还没定，先大概看看" | `score --allow-missing` |

## 二、入口

```bash
python <技能目录>/scripts/radar.py score --input opp.json
python <技能目录>/scripts/radar.py template > opp.json
python <技能目录>/scripts/radar.py check --input opp.json
```

Windows 用 `python`，macOS / Linux 用 `python3`。任何命令加 `--json` 输出结构化结果。

## 三、评分模型

### 第一层：一票否决

`qualification_ok` = 我们能不能满足资格条件（资质等级、案例数量与金额、注册资本、行业许可、本地化要求）。

- `false` → 直接输出"不建议投标"，不算分。资格不满足的项目，方案写得再好也是废标。
- `unknown` → 输出"待定"，先解决资格核实，不要往下推。

### 第二层：七维加权（每维 1–5 分）

| 维度 | 字段 | 权重 | 5 分长什么样 | 1 分长什么样 |
|---|---|---|---|---|
| 资金与立项真实度 | `funding` | 0.18 | 财政预算已批复，有采购意向公开 | 只有口头说法，无预算文号 |
| 竞争位势 | `competition` | 0.18 | 对手无同类案例，或客户明确不倾向现有厂商 | 头部厂商已驻场三年 |
| 客户关系基础 | `relationship` | 0.14 | 已有中层以上技术信任，能约到需求沟通 | 从未接触，只能等公告 |
| 案例与业绩匹配 | `case_match` | 0.14 | 有 3 个以上同类型同规模案例且可核验 | 无同类案例，只能靠通用能力说 |
| 政策契合度 | `policy_fit` | 0.12 | 项目直接落在年度重点任务里 | 政策里找不到出处 |
| 方案差异化空间 | `differentiation` | 0.12 | 有对手做不了的脏活能力（数据治理、系统对接） | 只能拼价格和界面 |
| 交付资源可行性 | `delivery` | 0.12 | 本地驻场团队现成，交付人力有富余 | 需要临时招人，且无本地服务 |

加权总分：`Σ (维度分 / 5 × 权重) × 100`，满分 100。

### 第三层：档位

| 总分 | 档位 | 动作 |
|---|---|---|
| ≥ 70 | 全力投入 | 立项报备、组投标小组、启动需求共创 |
| 55–69 | 选择性参与 | 先补短板，两周后复审；补不上就转分包或放弃 |
| < 55 | 建议放弃 | 保留信息，做伙伴的技术支撑，不做主投 |

### 第四层：短板排序

按 `(5 - 维度分) × 权重` 从大到小排，输出前三项，每项给一条可执行的补齐动作。分数低但权重小的维度不配占用你的时间。

## 四、输入格式

```json
{
  "project": "XX区一网通办升级",
  "client": "XX区行政审批局",
  "budget_wan": 860,
  "bid_date": "2026-12-10",
  "qualification_ok": true,
  "scores": {
    "funding": 4,
    "competition": 3,
    "relationship": 4,
    "case_match": 3,
    "policy_fit": 5,
    "differentiation": 4,
    "delivery": 3
  },
  "notes": "对手是本地集成商，无同类案例"
}
```

必填：`qualification_ok`、`scores` 七项。其余字段缺失会在输出里标"待确认"，不影响计算，但会拉低可信度评价。

## 五、输出格式

默认 markdown，固定四段：

1. **结论**：档位 + 总分 + 一句话理由。
2. **分数表**：七维分数、权重、加权贡献，按贡献降序。
3. **短板三条**：维度、丢分、补齐动作。
4. **下一步**：3 条以内，带责任角色（谁去办），不写"加强沟通"这种废话。

`--json` 输出结构：

```json
{"tier": "全力投入", "total": 72.4, "gate": "pass", "weak": [...], "missing": [...], "actions": [...]}
```

## 六、判断与异常

- 七维里有 3 项以上给不出分 → 信息不足，输出"待定"，并列出必须先拿到的三样东西（预算文号、招标文件、对手名单）。
- 用户把某维度全填 5 分 → 提醒一句：全 5 分通常意味着评估没做，让用户给出一个反例再定分。
- `qualification_ok` 为 false 但用户坚持要投 → 不争论，只输出"已知会导致无效投标的具体条款 + 建议先问招标人能否接受联合体"。
- 金额单位混乱（元/万元）→ 以 `budget_wan` 为准，其他字段忽略并在输出里注明。

## 七、边界

分数是决策辅助，不是决策。评标现场还有评委偏好、现场答辩、突发质疑等不可量化因素。
这个技能不给"中标概率"这种数字——没有历史投标数据支撑的概率是编的。要概率，先积累自己公司的历史中标率。
