# 使用说明

面向使用者的实际操作手册。不解释原理，只说怎么用、什么时候用哪一步。

---

## 第 0 步：准备三样东西

| 东西 | 为什么必须 | 没有怎么办 |
|---|---|---|
| 招标文件的**评审办法/评分标准**章节 | 全部分数的来源 | 先要。给不了就只做结构建议，不做分数判断 |
| 客户方的基本信息 | 主题与摘要的原料 | 用公开信息先做假设，标注为推断 |
| 你的**证据清单**（做过的项目、可核指标） | 没有证据的主题是口号 | 先做证据盘点，这比写方案重要 |

## 第 1 步：拆招标文件（招标解码）

**怎么说**：`这是我拿到的招标文件，帮我拆出评分表和废标红线`，然后把文字贴进来或给文件路径。

**你会拿到**三张东西：

1. 分数地图：每个评分项多少分、什么类型、能争取多少、为什么。
2. 废标红线：哪些条款不满足就出局，带原文和行号。
3. 隐性偏好：反复出现的词，说明评委在意什么。

**先看一个数**：主观可写分占总分的比例。

- 高于 50%：这份标书值得认真写。
- 30%-50%：重点写高权重那几项，其余保证不漏。
- 低于 30%：写作空间很小，把精力放到报价与材料完备上。这不是消极，这是算账。

**自己也能跑**：

```bash
python skills/bid-rfp-decode/scripts/rfp_decode.py 招标文件.txt --total 100
```

`--total` 填满分。如果脚本抓到的分值和满分对不上，它会告诉你还差多少——这通常意味着评分表跨页了或者有未量化项，回去补。

## 第 2 步：定主线（赢标主题）

**怎么说**：`帮我提炼 3 条赢标主题，要有证据`

**一条好主题长这样**：

> 蜀通 3 个前置仓不停业切换：双跑两周、每周比对台账，切换期差错率压在千分之二内

它包含三样：客户的具体处境（3 个前置仓）、一个能被追问的做法（双跑 + 比对台账）、一个可验收的结果（差错率）。

**自己测**：把主题填进 `themes.json`，跑

```bash
python skills/win-theme-forge/scripts/theme_stress.py themes.json
```

8 分以上保留，5.5-8 分改写，5.5 以下删掉。**宁可交 2 条硬主题，也不要凑 5 条软话。**

## 第 3 步：排结构（三幕架构）

**怎么说**：`帮我把章节按评分点重排，每章要拿多少分`

**你会拿到**章节蓝图 + 逐章任务书。任务书是给写手用的：这一章替哪个评分项拿分、论点是什么、证据在哪、多少字、不能写什么。

**字数怎么分**：按分值占比，不按写作手感。20 分的章节拿 30% 篇幅；10 分的章节写 40% 是浪费。

**最常见的错误**：把"项目理解"写成行业综述。评委要看的是"你懂不懂我们的问题"，不是"你懂不懂这个行业"。

## 第 4 步：改开头（摘要审查）

**为什么单独做**：评委的真实顺序是 封面 → 摘要 → 决定精读还是跳读。摘要写砸了，后面全白写。

**五段式**：处境 → 代价 → 判断 → 证据 → 结果。每段 1-3 句，全篇 700 字以内。

**自己测**：

```bash
python skills/exec-summary-polish/scripts/summary_audit.py 摘要.md --client 客户名
```

0-100 分。75 以上可交，50-75 要改，50 以下重写。

**一个土办法**：把摘要单独发给一个不了解项目的人，让他复述你要干什么。复述不出来就重写。

## 第 5 步：模拟评审（黑帽）

**怎么说**：`你扮演评委和最可能的对手，找出我丢分的地方`

**关键动作**：逼自己给每一项填一个得分率（0-1）。填的时候你会发现问题——很多项你其实不知道评委会怎么给分，这说明评分口径没读透。

```bash
python skills/blackhat-review/scripts/score_sim.py assess.json
```

**会给你三个东西**：

1. 三档总分（悲观/中性/乐观）。
2. 最不确定的三项：区间越宽，说明你越没底。
3. 追分排序：每小时能追回几分，先做最划算的。

**注意**：报价类不参与追分排序。价格分靠报价决策，改文字追不回来。

**如果"全部拉满仍不够线"**：这句话很重要。它意味着这个项目不是靠改文字能赢的，要么动报价策略，要么放弃。别在这里耗时间。

## 第 6 步：报价页（报价叙事）

**顺序不能反**：先算不做的代价，再让价格出现。

```bash
python skills/price-narrative/scripts/roi_model.py price.json
```

**三档配置**：够用 / 推荐 / 加厚。作用是让客户在"少要点"和"多给点"之间选，而不是在"买"和"不买"之间选。

**让价必须换东西**：每让 3%，换一条范围收缩或一个付款节点前置。无条件让价会引来第二次砍价。

**算不出收益就别写 ROI**。改成"范围透明 + 单价拆解 + 验收绑定"的写法。编一个"提升 40%"是最容易被评委追问的。

## 第 7 步：交付体检

**怎么说**：`明天要交，帮我查一遍`，给目录或文件。

```bash
python skills/bid-package-qc/scripts/qc_check.py ./标书目录 --client 客户全称
```

**三级清单**：

- 阻断：占位符、客户名缺失、绝对化用语 → 必须清零
- 警告：金额写法不一、编号断号、评分项找不到落点 → 建议改
- 提示：其他

**脚本查不到的，必须人工核**：字体字号、页数上限、签章位置、电子标上传格式、资质原件、是否需公证。这些脚本一律视为"未验证"，不是"通过"。

## 常见问题

**Q：只有一天时间，做哪几步？**
A：第 1 步（拆分）→ 第 7 步（体检）。先保证不因低级错误出局，再谈分数。有半天余量就加第 4 步（改摘要），性价比最高。

**Q：客户不给我评审办法怎么办？**
A：只做结构与摘要建议，明确告知"分数判断不成立"。不要用行业惯例代替。

**Q：它能不能保证中标？**
A：不能，也不会给这个承诺。它给的是区间和假设，不是概率。任何说能保证的，都在骗你。

**Q：方案是我老板写的，我能改吗？**
A：能，但要拿分数说话。用追分排序告诉老板"这两处改动能追回 X 分"，比说"我觉得不好"有效。

**Q：数据会被上传吗？**
A：不会。所有脚本在本地跑，只用 Python 标准库，无网络调用。

## 三个不要

1. **不要让脚本替你判断得分率。** 它不会，也不该会。你的判断才是产品的一部分。
2. **不要跳过第 1 步。** 没有分数地图，后面六步都在猜。
3. **不要把报告直接贴进标书。** 报告是给你看的，里面全是内部判断和 [待补] 标注。
