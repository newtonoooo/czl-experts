# 摘要审查

## 为什么单独做这一节

评审现场的真实顺序是：翻封面 → 看摘要 → 决定是精读还是跳读。摘要不是方案的缩写，是**结案陈词放在最前面**。它的任务只有一个：让评委带着"这家懂了"的预判去读正文。

## 输入

必需：摘要初稿，或由赢标主题 + 章节蓝图新写一稿。
必需：客户名、一个最硬的证据、一组目标数字。

## 五段式

| 段 | 写什么 | 反面例子 |
|---|---|---|
| 1 处境 | 客户现在卡在哪，用他们的词 | 我司成立于 2008 年 |
| 2 代价 | 不解决会怎样，尽量带数 | 随着信息技术的快速发展 |
| 3 判断 | 我们的做法，一句话说清 | 我们提供全方位解决方案 |
| 4 证据 | 一个同类项目的可核结果 | 我们拥有丰富的行业经验 |
| 5 结果 | 几个月后客户能验收什么 | 助力客户实现数字化转型 |

每段 1-3 句，全篇 700 字以内。超过一页的摘要，评委会跳读后半段。

## 步骤

1. 先删：把所有"致力于/全方位/一站式/领先/赋能"删掉，再读一遍，通常已经好一半。
2. 重排：把公司介绍整段删掉，开场直接写客户处境。
3. 补数：处境段给现状值，结果段给目标值，证据段给证据里的值。三个数撑起一份摘要。
4. 跑脚本体检。
5. 按脚本的问题清单逐条改，改完再跑一次，直到 ≥75 分且五段齐。
6. 最后做一次"外行测试"：把摘要单独发给一个不了解项目的人，让他复述你要干什么。复述不出来就重写。

## 判断

| 情况 | 处理 |
|---|---|
| 第一段出现"我司/本公司/成立于" | 整段删除重写 |
| 有"证据"字样但全文无数字 | 补数，或把该段降级为方法说明 |
| 通篇没有一个客户专属名词 | 这份摘要可以发给任何客户，等于没写 |
| 超过 900 字 | 砍到 700 以内，砍重复陈述不砍数字 |

## 输出

`执行摘要.md` + 一页修改说明（改了什么、依据是什么、还剩哪些需要客户提供的信息）。

## 脚本

```bash
python scripts/summary_audit.py 摘要.md --client 蜀通 --json audit.json
```

检查五项：开头视角、五段结构、空洞词、句长、字数。输出 0-100 分与逐条改法。

分数线只是体检指标：75 分以上可交，50-75 要改，50 以下重写。分数高不代表评委会给高分，只代表这份摘要没有明显的自伤动作。

## 异常

- 客户名不能出现在正文（有些保密项目）：用项目代号替代，但摘要里必须有至少一个只有内部人知道的细节。
- 证据不足：宁可只写"我们在同类场景做过的两个项目"，也不要写"行业领先"。

## 依赖与上下游
