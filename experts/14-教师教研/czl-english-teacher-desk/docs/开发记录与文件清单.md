## 一、需求来源与处理方式

功能分析对象为已安装的第三方专家 `highschool-english-teacher`（作者 xtgxiso），仅用于**研究它覆盖了哪些教师任务、哪些环节薄弱**。处理原则：

| 原包内容 | 处理 |
|---|---|
| 8 个并列功能模块的划分思路 | 参考其覆盖面，重新组织为"有数据依赖的六段闭环" |
| 主提示词文本 | 不复制；重写路由、纪律、契约、异常矩阵四部分 |
| 两份 references（学科知识、输出模板） | 不复制；按新的六段结构重写为 10 份知识库，内容自撰 |
| 头像 `expert.jpg` | 不使用；重新生成并裁剪 |

**没有做的事**：没有把原提示词改几个词后使用；没有沿用其章节顺序；没有复制其模板表格的文字。两份文本的可比段落（如"教学过程的环节名"）属于学科通用表述，不构成表达复制。

## 二、设计与实现决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 产品结构 | 六段闭环（W1–W6） | 原产品的模块之间没有数据依赖，教师每次要重新描述背景；闭环让上一段产物成为下一段输入 |
| 知识库组织 | `references/` 10 份 + `plugin.json.knowledge` | 按需读取，避免整包塞进上下文；每份对应一类判断（口径/方法/质检） |
| 是否用 `skills/` | 不用 | 六个技能会在启动时全部预加载，挤占上下文；工作流文件按需读更省 |
| 脚本选型 | 4 个纯标准库 Python 脚本 | 教师机器不一定有第三方库；统计与校验是可程序化的部分，先做扎实 |
| 质检机制 | 脚本 + 清单 + 成品内质检单 | 让"是否可用"可验证，而不是靠自我评价 |
| 分类 | `09-OperationsHR` | 平台客户端仅识别 12 个类目，无教育类；`15-Education` 不在校验白名单内，会导致校验失败 |
| 头像 | AI 生成 + 裁剪重构 | 保证无第三方素材；裁掉平台角标带，512×512、218 KB |
| 许可 | 自定义专有许可 | 允许个人/校内使用，禁止转售与二次分发为竞品 |

开发中修复的问题：

1. 细目表渲染时 `str.format()` 关键字重复导致 `TypeError`（已修复）。
2. 统计脚本把"空单元格"与"非法字符"混为一谈，提示语误导（已改为"空值/非数字"）。
3. 测试用例两处断言写错（输出位置、误命中），已改为精确断言。

```bash
python <expert-manager>/scripts/validate_expert.py <expert-dir>

# 功能回归

# 重新注册（修改任何字段后都要执行）

# 重新打包

```
