## 二、开发顺序与关键决策

### 1. 先立计算内核，再谈解读

第一天做的第一件事不是写提示词，是写星历。原因：术数产品的可信度全部压在"盘对不对"上，提示词写得再好，盘错一个时辰就全废。

内核分四层，逐层验证后再往上叠：

```
astro.py          儒略日 / 太阳视黄经 / 月亮视黄经 / 节气 / 朔
calendar_core.py  干支 / 农历（定朔定气）/ 真太阳时 / 四柱
bazi.py           十神 / 藏干 / 五行力量 / 纳音 / 空亡 / 神煞 / 大运 / 流年
ziwei.py          命身宫 / 五行局 / 紫微定位 / 14 主星 / 四化 / 大限
divination.py     梅花体用 / 六爻京房八宫装卦
almanac.py        建除 / 黄道黑道 / 二十八宿 / 冲煞 / 吉时 / 择日打分
```

### 2. 太阳位置用高阶序列，不用低精度公式

**决策过程**：初版用经典低精度太阳黄经公式（标称误差 0.01°）。实测对照紫金山天文台发布值，系统性偏早 6–14 分钟——这是用户拿手机一查就能发现的偏差，产品不能接受。

改为 VSOP87 地球日心黄经截断序列（L0–L5，约 130 项）+ FK5 改正 + 章动主项 + 光行差。改后偏差降到 4–21 秒。

**踩过的坑**：VSOP87 的自变量是**儒略千年**、量纲是**弧度**，初版按"儒略世纪 + 度"处理，结果节气全盘错位到别的月份。这个 bug 是"跑出来一看日期完全不对"才发现的，说明**必须用外部权威值对表**，不能只看程序跑通。

### 3. 农历自己算，不内嵌历表

**决策**：不采用常见的"1900–2100 农历压缩表"（一个 200 项的十六进制数组）。理由有二：一是那张表的编码方式属于他人的具体表达，权利状态不明；二是它无法覆盖 2100 年以后。

改为定朔定气法自算：月球黄经截断周期项（60 项）→ 求日月黄经差为 0 的时刻 → 定朔；太阳黄经 30° 倍数定中气；无中气之月为闰月。

**踩过的坑（重要）**：闰月判定的周期边界。初版在"上一年十一月 → 本年十一月"这个区间内找无中气之月，导致 2033 年被判成**闰七月**，并且整个年份少了"十月"、十一月错位。这是著名的"2033 年问题"。

正确做法：闰月必须在"**含冬至之月为十一月**"的那个周期内部判定。改后 2033 年得到 闰十一月，冬至正确落在十一月内，2034 年春节 2 月 19 日与公认历表一致。

这条也说明：**闰月规则不是"找第一个无中气的月"这么简单**，还要受"十一月必须含冬至"的约束。

### 4. 建除、值神、宿、吉时——四个都靠外部黄历对齐

这四项传统上各有起例表，凭记忆写极易错位。做法是：先按规则实现，再拿 2026-10-26 的公开黄历条目逐字段对。当天核对了 8 个字段（干支、纳音、建除、值神、宿、冲、煞方、财神喜神、吉时）。

**踩过的坑**：值神（黄道黑道十二神）日级起例用**月支**定青龙，时级才用**日支**。初版把两者混用，值神判成"玉堂"（应为"天德"）。修正后与黄历一致，同时吉时也自动对上（酉日青龙在寅 → 吉时恰为子寅卯午未酉）。

### 5. 京房八宫用生成法，不硬编码 64 卦表

八宫序列（本宫→一至五世→游魂→归魂）可以用"逐爻翻转"规则生成，比硬编码 64 条更不容易错，也便于自检。生成后仍做了单点核对：乾为天、天风姤的宫属、世应、纳甲六亲全部对上通行体例。

**踩过的坑**：`_hexagram_name` 返回 `(卦名, 意象)` 二元组，调用处直接把元组当卦名塞进结果，导致 CLI 输出 `本卦：('火地晋', '光明渐进…')`。是自动化测试扫出来的，改为一律解包。

### 6. 大限方向对了，宫名却错配

紫微大限：阳男阴女顺行、阴男阳女逆行。初版判方向正确，但把"顺行"理解为宫位编号递增，导致宫名与宫位对不上（命宫在寅，顺行的下一步应是兄弟宫在丑，却给了卯）。

修正：顺行 = 按十二宫顺序走（宫位递减），逆行 = 命→父母→福德（宫位递增）。修正后 1990 年阳女样本的大限为 命(寅)5–14 → 父母(卯)15–24，与体例一致。

### 7. 头像：自拟提示词生成，裁切成型（v1.1.1 更换形象）

用 ImageGen 生成 1024×1024 原图，提示词自拟（现代编辑插画、深藏青西装、黄铜算卦台线稿、方构图、不要老人感）。生成结果带工具水印，用自写的纯标准库 PNG 工具裁去边缘并缩放为 512×512（345 KB）。

**处理说明**：原图保留为 `avatars/expert-raw.png`，成品为 `avatars/expert.png`。裁切仅为构图与去除工具水印。若平台要求保留生成水印，请替换为 raw 版本——这一条已列入风险清单。

**v1.1.1 更换形象**：首版头像沿用了"司南"的罗盘意象（女性形象），定名「算卦台」后与名字脱节。换成三十出头的道士：混元巾 + 高束髻铜簪、深靛道袍配古金滚边、右肩后细线八卦环。刻意避开白胡子老道的刻板印象——道士的专业感应该来自**服装结构与器物符号的精确**，而不是年龄和胡须。裁切框 (40,20,900,900) → 512×512，430 KB。

### 8. 文档与提示词最后写，但先定规范

先定三条硬约束（算法优先 / 不做宿命断言 / 硬边界），再写模块。这样每个 SKILL.md 的"执行步骤"都有落点，不会写成泛泛而谈的说明书。

### 9. 发布前改名：司南 → 算卦台

首版定名「司南」（取"指南"之意），定位写成"术数决策参谋"。首次交付后用户反馈：**名字看不出这是算命的**，用户第一眼无法判断产品用途。

这是定位问题，不是审美问题：产品名承担的是"三秒内让人知道你能干什么"。改名后：

- 中文名 **算卦台**，英文 Guatai
- 职业定位 **算命与占卜参谋**（en: Fortune-Telling & Divination Advisor）
- 能力描述改为正面说明"会算命也会算卦"，不再用"决策参考框架"这类抽象表述
- 标签改为 八字算命 / 算卦占断 / 择日择时
- 首条推荐提问改为"帮我算个命，排八字盘看看…"

**结构处理**：WorkBuddy 专家的 `name`、`agentName`、目录名是唯一标识，不支持原地改名。因此按新标识**重建**了整个包（`czl-guatai`），文件内容随迁并更新全部引用，旧包删除。功能与代码逻辑不变，仅标识与文案变化。

**同时修掉的 bug**：`pick` 子命令的文字输出路径此前从未被测试覆盖（只测了 `--html` 分支），文本模式会因缺少 `date` 字段报 KeyError。已修，并补进回归清单。
