## 阶段一 · 需求分析（读取与分析参考对象）

### 做了什么

完整读取本机已安装的 6 个 A股/投研方向专家包全部文件：

| 参考包 | 读取内容 |
|---|---|
| `a-stock-trading-assistant` | agent 提示词 1 份、plugin.json、README，共 5 个文件 |
| `smart-stock-analyst` | agent 提示词、skill 1 份、references 6 份，共 10 个文件 |
| `tdx-stock-diagnostician` | agent 提示词、README、上架申请报告，共 6 个文件 |
| `tdx-stock-hunter` | agent 提示词、README、上架申请报告，共 6 个文件 |
| `strategy-backtest-expert` | agent 提示词、4 个 skill、参考文档与示例脚本，共 40 个文件 |
| `equity-research` | agent 提示词、3 份 rules、15 个 skill 及引用文档，共 32 个文件 |

### 得出的判断

六个包各自解决一个片段，但共性缺口是同一批：

1. **能力与数据可得性错配**：`smart-stock-analyst` 列了 TickFlow/Tushare/AkShare 等 11 个数据源，普通用户多数没有 key；`tdx-*` 两个包完全绑定通达信 MCP，未装即全部失效。
2. **只有分析没有成品**：输出是聊天段落，不是文件。唯一提到 HTML 的 `smart-stock-analyst` 只给了色彩规范，没有可运行模板。
3. **A股本土规则缺位**：涨跌停、T+1、ST、复权、北向口径，普遍只在"注意事项"里提一句。
4. **证据不分级**：公告数字、管理层说法、券商转述混在一段。
5. **没有交付闸门**：写完就交。
6. **没有记忆**：同一标的反复被推翻，无台账。

### 决策 D1：产品定位

不做"又一个个股分析器"，做**投研内容生产线**——因为前 5 个缺口最终都指向同一件事：**产出不可交付、不可复核**。

定位表述：从"一只股票"到"一份能交出去的文件"。

## 阶段二 · 规格设计

### 做了什么

先写 `SPEC.md`，再写代码。核心是把推导路径反过来：

```
要交付什么 → 这个交付物回答哪个问题 → 最少需要什么证据 → 证据能不能拿到 → 怎么说才不算骗人
```

### 决策 D2：工作流按"判断闭环"切，不按数据类型切

常规做法是按数据分模块（基本面模块、技术面模块、资金面模块）。本产品按"一次判断的完整闭环"切分，得到 8 个流程。

理由：模块按数据切，用户拿到的是一堆分析；按判断切，用户拿到的是一个决定。副作用是流程之间有依赖关系，需要显式画出上下游与回退路径（见 SPEC 第 9 节）。

### 决策 D3：脚本零第三方依赖

环境实测：本机 Python 3.13 无 numpy / pandas / requests / PIL。

这本来是个限制，后来被定为产品原则：**专家包要能在未配置环境的机器上直接跑，装不上就等于没有**。所有脚本改用标准库实现，包括 PNG 编码（`zlib` + `struct` 手写）和 HTTP（`urllib`）。

代价：无法做向量化计算，指标计算用纯 Python 循环，250 根 K 线耗时 <0.1 秒，可接受。

### 决策 D4：报告用内联 SVG，不引 CDN

`smart-stock-analyst` 与 `equity-research` 都允许 CDN 引入 Chart.js/ECharts。本产品改为手绘内联 SVG。

理由：断网要能开、打印要能出、企业内部环境常常无外网。代价是图表能力受限（只有折线/柱/散点），复杂图表需另出图片。

## 阶段三 · 实现

### 文件产出顺序

1. `SPEC.md` — 规格
2. `agents/czl-ashare-research-writer.md` — 主体提示词
3. `rules/` 3 份 — 证据分级、A股规则、交付标准
4. `skills/` 8 个 — intake → evidence → autopsy → value → tape → thesis → quality → position
5. 脚本 6 个 — arrules / arfetch / arindicators / arvalue / arreport / archeck / arposition
6. `tests/test_all.py` — 三层测试
7. `tools/make_avatar.py` + 头像
8. 文档 7 份

### 脚本开发顺序与理由

按"依赖从少到多"排：`arrules`（纯计算）→ `arindicators`（纯计算）→ `arvalue`（纯计算）→ `arfetch`（网络）→ `arreport`（字符串处理）→ `archeck`（依赖 arrules）→ `arposition`（纯计算）。

每个脚本写完立即跑内置自检，不等全部写完再测。这个顺序让后面脚本出错时能快速定位是不是前面脚本的问题。

## 阶段四 · 调试记录

实际运行暴露的 5 个缺陷，全部修复后回归（详见 `功能测试报告.md` 第五节）。其中两个值得单独说明：

### 缺陷 3：HTML 结论段缺"结论"二字

**怎么发现的**：离线链路测试里，一份完全合规的报告被判"缺失段落：结论"。

**为什么值得记**：这不是代码错误，是**设计不一致**——Markdown 版由 `## 结论` 标题生成，HTML 版用样式块（`.verdict`）代替标题，所以文本里没有"结论"二字。闸门按文本查段落，自然判缺失。

**修法**：HTML 结论区补一个视觉上低调但文本存在的 `<h2>`。教训：**机器检查必须以文本为准，不能用视觉结构推断。**

### 缺陷 5：闸门把股票代码当数据

**怎么发现的**：A4 数字匹配率长期偏低（0.74-0.88），逐项打印未匹配样本，发现 `600519.0`、`2026.0` 在列。

**为什么值得记**：如果不修，闸门会对**每一份**正常报告误报，使用者会习惯性忽略它，整个质量机制形同虚设。这类"狼来了"型误报比漏报更危险。

**修法**：抽取数字时排除 6 位纯数字（股票代码）与 19xx/20xx（年份）。修复后匹配率升到 0.93-1.0。

## 阶段五 · 头像

### 过程

1. **第一版（弃用）**：用生成模型出图，构图是笔尖 + 三根柱体。结果右下角带平台水印"AI生成 WORKBUDDY"，且红点位置失衡。
2. **判断**：水印不能进商业包；生成内容的商用授权状态不明；构图不可控。
3. **第二版（弃用）**：改用自写几何脚本绘制，但顶部有一条孤立横线，整体重心偏下。
4. **第三版（弃用）**：把最高柱的红色收头改成三角笔尖。实测读起来像箭头，中间那道米白缝像杂点。
5. **第四版（采用）**：回到矩形收头，重排几何——基线 y=694、三根柱顶端 514/414/314、柱宽 120、间距 92、外圈留白 ≥180px。

### 决策 D5：头像用代码画，不用生成模型

理由三条：

1. 生成模型会在角落打水印，商业包不能带第三方水印；
2. 几何图形用代码画，边缘精准（2 倍超采样抗锯齿）、可复现、可举证为自主创作；
3. 同一脚本任意机器重跑结果一致，便于版本管理。

**符号含义**（v1.0.0 版，已由 v1.0.1 替换）：三根递增柱体 = 结论的递进；下方基线 = 事实底座；最高柱的朱红收头 = A 股"涨为红"的约定，也当作一个句点。

**举证**：脚本 `tools/make_avatar.py` 保留在包内，任何人可重跑复现。

## 阶段七 · 头像改版（v1.0.1）

### 为什么改

v1.0.0 的头像是"三根递增柱体"，干净但有一个实际问题：**柱状图是通用数据符号，不携带"股市"信息**。放在专家列表里，它会被读成"数据分析""报表"，而不是"行情"。

用户反馈也指向同一处：希望有股市折线特征。折线才是这个品类不可替代的识别符——K 线的走势、分时图的形态，都是折线。

### 怎么改

第五版（v1.0.1 采用）：**一条带两次回撤的上升折线 + 一条基线，末端朱红结点实心收口。**

三个刻意的取舍：

1. **保留两次回撤**，不做成一路向上的直线。一路向上的图是宣传插画，读不出真实行情；有回撤才像走势，也顺带传达了本产品的态度——不做"必涨"叙事。
2. **去掉刻度点**。试过在基线上加三个低对比度刻度点，想暗示"有刻度的坐标系"，但 1024 下几乎不可见、缩到 256 更像屏幕灰尘，删掉。
3. **红点改实心**。原先做成带孔圆环，看起来像靶心（"目标价命中"），语义跑偏；改实心后才是"当下这个点"。

重排几何两轮：第一版折线压在画布下半部、基线离折线 122px，读起来两者不相干；第二版整体上移 40px、x 左移 20px、基线提到 y=676，上下留白各约 300px，重心回到画布中心。

### 技术改动

`tools/make_avatar.py` 新增两个绘制原语：

- `stroke_segment()`：按点到线段的距离填充，只遍历包围盒。端点自然成圆头，不需要另画圆。
- `fill_disc()`：实心圆，包围盒内按弦长算水平跨度。

校验项同步增加两条：`折线整体向上`（末点比首点高 100px 以上）、`含回撤（非单调上行）`。第二条第一次写错了——判据写成"内点 y 最大值超过首点"，而真实回撤是局部的（592→622），并不会低过起点，导致误报。改为"存在某一段的 y 递增"。

## 阶段六 · 文档与风险梳理

### 决策 D6：把"做不到"写进 README

多数产品文档只写能力。本产品在 README 与 USAGE 中明确列出"做不到"清单（无财务数据库、无一致预期、行情有延迟、不支持分钟级回测）。

理由：**承诺落空是最快的差评来源**。写清边界，用户的预期管理成本会低很多，也降低合规风险（不构成"专业投顾"暗示）。

### 决策 D7：风险清单交回给开发者决定

`docs/商业发布风险清单.md` 列出 12 项风险与 6 项待决事项（D1-D6），没有替开发者做决定。

理由：名称是否保留"专业"、是否采购数据源、许可模式，这三件事涉及商业判断与法律责任，工具开发者比代码作者更有资格决定。
