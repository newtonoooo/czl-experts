## 二、开发顺序与关键决策

### 第一步：读透同类产品，只提炼需求

逐文件读完同类财税顾问产品的清单、主提示词、技能入口与三份知识文件。读的目的不是学写法，而是回答四个问题：它服务谁、解决什么、缺什么、在哪容易出错。

得到的判断：

- 它的知识覆盖是完整的（分析、报税、预算、内控、发票五块都在）。
- 它的结构是**扁平并列**的：五个技能互不约束，模型可以选择任何一个开始，也可以混着来。这带来一个后果——**没有"先校验数据"这个强制环节**。用户给的报表如果不平，模型会照样算下去，算出来的比率看起来专业，实际全错。
- 它的计算靠模型心算。毛利率、周转天数、量价拆分这类计算，模型容易出错且错误不可见。
- 它给的是"要点 + 模板"，没有把"用户怎么问"和"该走哪条路"连起来。

### 第二步：定结构

据此设计了 G0—G5 六阶段，核心是把"校验"变成不可跳过的一步：

```
G0 接单与脱敏 → G1 数据校准（放行条件：勾稽差异已解释）→ G2 诊断 → G3 税务判定 → G4 方案 → G5 交付
```

同时保留三种工作模式（快问快答 / 单阶段深做 / 全流程），避免用户问一句"房租发票几个点"就被套上完整流程。

### 第三步：把计算从模型手里拿走

写了 `toolkit.py`，四个子命令。设计时定下三条：

1. 缺字段跳过，不填默认值（填 0 会让校验假通过）。
2. 只做算术不做判断（判断需要情境，脚本做不了）。
3. 每个输出带公式（用户能手工验算）。

写完后用内置用例验证恒等式：勾稽关系、杜邦三因子乘积等于 ROE、价差加量差等于总差异。9 条全部通过。

### 第四步：写知识文件

拆成七份而不是一份长文档，理由是上下文稀释：一份两千行的文件放进去，每段的具体性都会下降。

七份的分工按阶段切：

- 01 受理（G0）· 02 规范化与勾稽（G1）· 03 诊断口径（G2）· 04 税种判定树（G3）· 05 内控（G4）· 06 交付模板（G5）· 07 场景剧本（跨阶段索引）

第 07 份是新增的：十二个高频场景，每个给"听出什么信号 → 走哪几个阶段 → 关键判定 → 容易答错的地方"。这一份解决的是"用户的问题和知识条目对不上号"的问题。

### 第六步：打包与自检

写 `validate_package.py`（38 项检查）和 `build_package.py`（构建 + 包内校验 10 项）。**这两个脚本的动因来自用户反馈的一个真实故障**：导入新环境后头像位置显示成一个汉字。定位原因后（见 `头像故障诊断.md`），把平台的解析规则复现成检查项，使同类问题在上传前就能被发现。

## 三、遇到的具体问题与处理

| 问题 | 处理 |
| --- | --- |
| 自我介绍容易写成模板 | 主提示词第八节直接规定"不要长篇自我介绍，先跑校验证明你读了数据" |
| 建议容易空泛 | G4 阶段设四要素硬条件，"加强管理"类表述视为未通过 |
| 税率表述风险 | 全部加"截至 2026 年 10 月"标注；不确定的文号直接不写，改为政策名称 |
| 申报日历不准 | 只做周末顺延，明确声明不含法定节假日与征管延期，避免给出错误截止日 |
| 表格在终端对不齐（中文占两列） | 增加 `dwidth/pad` 函数按东亚字符宽度补齐 |
| 自检脚本扫描到自身关键字 | 独立性扫描跳过 `dev/`（该目录不进发布包） |

## 四、头像的生成与处理链路

1. 用图像生成工具生成两版方案：第一版深色背景带细白环，第二版浅色背景、深藏青圆角徽章内嵌金色递增柱与白色对勾。
2. 选第二版：浅底在浅色主题的列表中不突兀，深色徽章保证小尺寸下仍有对比度。视觉符号是"递增柱形（经营）+ 对勾（合规）"，不含文字与人物，避免小尺寸糊成一团，也避免"老派专家头像"的观感。
3. 后处理：`dev/prepare_avatar.py` 用背景色覆盖右下角平台水印区域 → 居中裁切 880×880（保留徽章完整与均匀留白）→ LANCZOS 缩放到 512×512 → 输出 `avatars/avatar-512.png`。
4. 校验：正方形、512×512、168 KB、目录内仅一个文件、路径大小写与清单一致。

原始生成图保存在 `dev/avatar-raw/`（不随包发布），便于日后证明创作过程。
