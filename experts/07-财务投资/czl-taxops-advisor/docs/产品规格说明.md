## 一、需求来源与独立性声明

本产品为独立开发。开发前对同类财税顾问类产品做了功能分析，仅提炼**功能需求**（能做什么、需要什么输入、产出什么、失败在哪），未采用其提示词文本、知识文件表述、代码或目录结构。产品规格、工作流、提示词、知识文件、脚本、头像均为本次新写。

具体来说：

- 借鉴的是**通用方法论**：三表勾稽、杜邦分析、量价拆分、内控职责分离、税种判定逻辑——这些属于会计与税务领域的公共知识，不属于任何一方的独创表达。
- 重新设计的是**产品结构**：同类产品多采用"五个并列技能 + 三份知识库"的扁平结构；本产品改为"六阶段带放行条件的流水线 + 场景剧本"，并新增可执行计算工具。结构不同，导致回答的组织方式、失败模式、可验证性都不同。
- 主动补足的是**原结构的四个薄弱点**（见第三节），它们直接决定了同样的用户问题会得到质量不同的回答。

## 二、目标用户与使用场景

### 用户画像

| 用户 | 典型身份 | 真实诉求 | 支付意愿来源 |
| --- | --- | --- | --- |
| 小微企业老板 | 10—80 人公司实际控制人 | 这个月赚没赚钱、钱去哪了、税上有没有坑 | 避免一次罚款/一次错误决策的损失 |
| 个体户 / 工作室负责人 | 餐饮、设计、咨询、电商 | 核定还是查账、要不要升一般纳税人、报销怎么管 | 省代账费、避免补税 |
| 新入职财务 / 兼职会计 | 1—3 年经验 | 申报口径、勾稽关系、发票处理、老板问的问题答不上来 | 降低出错概率 |
| 兼管财务的行政 / 合伙人 | 无财务背景 | 报销审核、预算表怎么填、报表怎么看 | 少被老板问住 |

### 典型场景

1. **月末**：拿到利润表与资产负债表，想知道经营状况与问题所在。
2. **季初**：确认本期要报哪些税、金额怎么算、几号前报完。
3. **异常发生时**：账上没钱但报表赚钱、税负率被预警、发票开错、股东借款挂账。
4. **年度**：编预算、做汇算清缴准备、梳理内控漏洞。

### 不适用场景

审计鉴证、税务争议代理、涉刑案件定性、投资决策、跨国有转让定价——这些需要持证机构或专业律师，本产品只做识别与转介。

## 三、需求清单

### 3.1 功能需求（F）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| F1 | 接收报表数据（文本/表格/截图转文字），校验勾稽关系并输出差异定位 | P0 |
| F2 | 基于校验后的数据做结构、比率、现金流质量诊断，输出可指回数据的结论 | P0 |
| F3 | 按纳税人身份与业务行为判定涉及税种、计税依据、期限，输出涉税事项清单 | P0 |
| F4 | 编制预算骨架，做差异分析并拆分量差/价差 | P1 |
| F5 | 针对具体环节给内控控制点与三流一致核查 | P1 |
| F6 | 判定发票可否报销、如何查验、异常如何处理 | P1 |
| F7 | 判定税收优惠适用性（四态：符合/大概率符合/不符合/需确认） | P1 |
| F8 | 输出待补数据清单，并指出补哪一项收益最大 | P0 |
| F9 | 对风险分级（A/B/C）并给出金额敞口与整改时限 | P1 |
| F10 | 生成申报日历（含周末顺延） | P2 |
| F11 | 数字可复算：计算类输出必须能由用户手工验算 | P0 |

### 3.2 非功能需求（N）

| 编号 | 需求 | 验收方式 |
| --- | --- | --- |
| N1 | 离线可用，不依赖外部接口即可完成 P0 功能 | 断网环境下走通一次完整体检 |
| N2 | 计算脚本零第三方依赖 | 仅 import 标准库 |
| N3 | 政策表述带时间标注，不编造文号 | 抽查 20 处政策表述 |
| N4 | 信息不足时明确说"无法判断"，不用模糊表述填充 | 构造缺数据场景测试 |
| N5 | 不承诺节税结果、不出鉴证意见 | 构造诱导性提问测试 |
| N6 | 单次回答聚焦，不一次性倾倒全部内容 | 人工评估对话节奏 |
| N7 | 包体小于 1MB（不含原图），导入后头像正常显示 | 打包校验脚本 |

### 3.3 对同类产品的补足（差异点）

分析同类产品后，识别出四个影响实际效果的薄弱点，本产品逐项做了结构性改进：

| 薄弱点 | 后果 | 本产品的做法 |
| --- | --- | --- |
| 缺数据校验环节 | 用户给的数据本身不平，模型照着算，结论全错但看起来很专业 | 设 G1 阶段与放行条件：勾稽不平不得进入诊断；提供 `check` 子命令 |
| 计算依赖模型心算 | 比率、杜邦、量价拆分容易算错，且无法复核 | 提供 `toolkit.py`，四个子命令覆盖主要计算，输出可手工验算 |
| 知识以"要点+模板"平铺 | 用户问题与知识条目对不上号时，模型只能泛泛而谈 | 改为场景剧本（12 个），每个剧本给出识别信号→阶段路径→关键判定→常见错答 |
| 建议缺可验收性 | 输出"加强应收管理"这类无法执行的结论 | G4 阶段硬性要求"做什么/谁做/何时/怎么验证"四要素，否则不放行 |

## 四、输入与输出规范

### 输入

| 类型 | 形式 | 处理方式 |
| --- | --- | --- |
| 结构化数据 | JSON（推荐，字段见 references/02）| 直接交给脚本 |
| 半结构化 | 粘贴的表格文本、Excel 复制内容 | 先整理为 JSON，字段对不上则手算 |
| 非结构化 | 截图 OCR 文字、口述 | 先复述关键字段请用户确认，再计算 |
| 票据信息 | 发票代码/号码/日期/金额/税率 | 五要素核对 + 查验路径指引 |

### 输出

固定五段式（全流程任务）：

1. 结论（三句话内）
2. 数据与计算（表格，标注口径）
3. 待补清单（含"补哪项最划算"）
4. 风险台账（级别/敞口/动作/责任人/时限）
5. 口径声明（数据来源、计算口径、政策时点、假设、免责）

单阶段任务只输出对应成果物，不套用五段式。

## 五、技术实现

| 组件 | 职责 | 技术选择与理由 |
| --- | --- | --- |
| `plugin.json` | 平台识别的元数据 | 按平台清单规范；头像使用相对路径 `avatars/avatar-512.png` |
| `agents/*.md` | 主提示词，决定对话行为 | Markdown + YAML frontmatter，与平台一致 |
| `skills/*/SKILL.md` | 技能入口与路由 | 平台按需加载，避免主提示词过长稀释注意力 |
| `references/*.md` | 分主题深度知识 | 拆成七份而非一份长文档，便于按阶段加载 |
| `scripts/toolkit.py` | 计算与校验 | 纯标准库；argparse 子命令；缺字段跳过而非崩溃 |
| `dev/*.py` | 打包与自检 | 复现平台解析规则，把"导入后图标消失"这类问题挡在上传前 |

设计取舍：

- **为什么用脚本而不是让模型算**：算术是模型的弱项，且错误不可见。脚本的错误是可见的、可修的、可回归测试的。
- **为什么工具只做算术不做判断**：判断需要行业常识与情境，脚本做不了；强行做会把错误固化。
- **为什么知识拆成七份**：单份长文档在上下文里会被稀释，按阶段加载能保持每段的具体性。

## 六、质量与验收标准

| 维度 | 标准 | 当前状态 |
| --- | --- | --- |
| 正确性 | 勾稽公式与比率公式与会计准则一致；自检用例覆盖恒等式 | 9/9 通过 |

| 兼容性 | 包结构、头像引用符合平台解析规则 | 10/10 通过 |
| 可维护性 | 政策更新只需改 references/04 与 calendar 常量 | 已文档化 |

## 七、版本与维护计划

- 当前版本 1.0.0，功能范围见 CHANGELOG。
- 维护触发条件：① 增值税、企业所得税、个税主要税率或优惠调整；② 申报期限规则变化；③ 平台清单格式变化。
- 维护动作：更新 `references/04` 与 `toolkit.py calendar` 中的常量与日期，跑 `selftest` 与 `validate_package.py`，升次版本号。
- 明确不做的事：不承诺政策预测，不在未核实的情况下给出具体文号。
