## 一、需求分析阶段

### 1.1 对参考对象的处理方式

开发前对一个通用"企业财务会计专家"包做了**只读**的功能结构分析：列出它覆盖的能力范围（凭证、对账、报表、差异、结账、审计六条线）、技能的数量与组织方式、输入数据的处理路径、输出形态。

分析结论只用于三件事：确认功能覆盖不遗漏、确认目标用户与场景、找出它的薄弱环节作为差异化起点。**未复制其提示词语句、表格样式、代码或文件组织。** 该包内的 Apache 2.0 许可证文件未被沿用（本包为独立作品，采用自有许可），也未删除或修改该包任何文件。

### 1.2 找到的三个薄弱点（差异化的起点）

| 观察 | 本产品对策 |
|------|-----------|
| 准则重心在 US GAAP / SOX，中国会计用户用不上（ASC 606、FICA、401k 等） | CAS 作一等公民：科目、专普票、增值税、当月增加下月计提、报表列报全部按中国实务 |
| 能力载体几乎全是提示词模板，没有可执行计算，用户拿到的仍是"要自己算" | 写 `ledgerkit.py`：9 个命令覆盖平衡校验、滚算、调节、折旧、摊销、差异、勾稽、重要性 |
| 缺数据时按模板补位，风险与缺口不显性 | 接单门禁 + 缺件清单（写明"缺了会怎样"）+ A/B/C/D 来源分级 + R0/R1/R2 风险分级 |

### 1.3 需求转化为产品主线

不做"七个技能并列陈列"，改为**一条主线 + 节点工具**：接单 → 做平 → 校表 → 归档。这样用户永远知道自己现在走到哪一步、还差什么。四段闭环是本次独立提出的组织方式。

## 二、设计与实现阶段

### 2.1 命名决策

- 包标识 `czl-accounting-close`：`czl-` 前缀 + 功能名。已核对本地专家目录 18 个已注册包，无同名、无同功能（现有 `czl-stock-research` 属投资研究，非账务）。
- 花名「账衡」：账（账务）+ 衡（天平、称量），指向"账账相符、账实相符"。与已有花名（案头、朱笔、陆工、定盘、简锋、刻度、文衡）不重复。
- 英文名 `Zhangheng`：花名音译，与本地其他专家命名风格一致。

### 2.2 工作法设计

四柱滚算是中国簿记传统（旧管 + 新收 − 开除 = 实在），也是所有 roll-forward 的本质。把它作为"做平"阶段的核心校验，比单纯说"对账"更可执行，且能一句话讲清阶段完成判据。

风险分级用 R0/R1/R2 三级而非"高/中/低"：R0 定义为"未清不得结账"，是一个动作门禁，不是形容词。

### 2.3 工具设计约束

- **只用标准库**：避免第三方依赖的许可证与分发风险，也避免用户装不上（pip 失败是最常见的交付障碍）。
- **Decimal 全链路**：浮点会让借贷差 0.01，直接被判不平，这是会计场景的硬伤。
- **双输出形态**：文本给人看，`--json` 给底稿与脚本用，`--out` 落盘留痕。
- **三档退出码**：0/1/2，便于串联到结账脚本里做门禁。
- **内置自检**：8 个用例覆盖最易错处（尾差、提足、加法闭合、两侧调平），发布前跑一次就知道工具没坏。

### 2.4 内容设计要点

- **空话黑名单**（差异说明）：直接列出五种禁写句式及原因，比"要写得具体"这种要求可执行。
- **证据分级 A/B/C/D**：让复核人一眼看出哪句话是单据支撑、哪句是口述。
- **勾稽倒查顺序**：不给"自己找原因"，给四步顺序（账本身 → 净利润衔接 → 现金口径 → 版本一致）。
- **结账压缩只给三条真手段**：模板化 L1 分录、对账改滚动、关联方月中预对。明确写"催人加班不改变关键路径"，避免正确的废话。

### 2.5 头像

生成式工具产出 1024×1024 原图（深蓝底 + 金色点缀、天平与账页符号、年轻职业形象），本地裁剪为 920 方形（去除右下角平台水印）后缩放至 512×512，PNG 优化至 157 KB。原图留存在 `docs/assets/avatar-source-1024.png` 作为生成记录。

## 四、遇到并修正的问题

| 问题 | 现象 | 处理 |
|------|------|------|
| 直线法尾差期望值写错 | 自检首月 3,166.67、末月应为 3,166.55，初版期望写成 3,166.63 | 修正期望值；公式本身正确（末期倒挤） |
| 银行调节样例数据不自洽 | 账面 118 万 / 对账单 120 万，调节后两侧差 6,000 | 反推正确账面应为 117.4 万（企业已付 2.3 万、银行已收 0.3 万），改样例与自检 |
| 干净批次被误报 R1 | 收款 212,000 整额触发"整额估数" | 改样例为 212,486.30；规则本身保留（整额确实是关注信号） |
| 差异表合计行写错 | 分项 37.4/80.0 却写成 137.4/180.0 | 修正合计行，占比与分项一致 |
| Windows 控制台编码 | 中文表格输出可能乱码 | 脚本启动即 `reconfigure(encoding="utf-8")`；JSON 读取用 `utf-8-sig` 兼容 BOM |
