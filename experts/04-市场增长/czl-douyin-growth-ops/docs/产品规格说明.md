## 一、需求是怎么来的

### 1.1 目标用户

| 用户类型 | 特征 | 他们最缺什么 |
|---|---|---|
| 个体经营者 / 手艺人 | 一个人做号，边干活边拍，预算几千块 | 没人告诉他数据算好还是差，改哪儿 |
| 小商家（1—5 人） | 有货、有直播需求，运营是老板兼的 | 排品靠感觉，播完不知道亏在哪 |
| 品牌新渠道运营 | 有 KPI，要向上面解释投放为什么亏 | 缺一套能拿去汇报的口径和表格 |

### 1.2 真实使用场景

1. 账号做了两三个月，播放卡在几百，怀疑被限流，但不知道问题出在内容还是账号。
2. 想投 DOU+，纠结投多少，投了之后说不清赚没赚。
3. 周六要播两小时，货盘堆在那儿，不知道先讲哪个、什么时候放福利。
4. 稿子写完自己念着挺顺，发出去完播 15%，不知道为什么。
5. 供应商给的卖点里全是"最好""根治"，隐约觉得不对但不知道怎么改。

### 1.3 要解决的问题（按优先级）

1. **判断没有依据**：所有决策停在"感觉这个封面更好"。
2. **归因错误**：完播低就怪选题，实际是第 12 秒有个废话段。
3. **算不清账**：不知道保本线在哪，投放和直播都是盲打。
4. **合规靠运气**：绝对化用语、疗效承诺随手就写，被限流后不知道为什么。
5. **改不对地方**：一次改五样，数据变好也不知道是哪样起的作用。

## 二、功能需求（转换成可验收的条目）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F1 | 账号体检 | 输入 ≥3 条视频数据，输出唯一主断点 + 30 天排期；缺字段必须报错指出字段名 |
| F2 | 口播脚本 | 输出六列时间轴；总时长与钩子落点由工具算出，误差 ≤10%（相对实际朗读） |
| F3 | 直播台本 | 输出货盘结构 + 15 分钟节奏环 + 话术卡 + 场控表；保本 GPM 必须由工具算出 |
| F4 | 投放测算 | 输出单笔净毛利、保本 CPA、保本 ROAS、分档压力测试 |
| F5 | 合规筛查 | 输出等级统计、命中明细（含行号）、替换建议、改后稿；高风险命中时退出码非 0 |
| F6 | 缺口处理 | 用户缺数据时按 A/B/C 三档降级，且必须显式声明"参考区间不等于你的实测值" |

### 2.1 输入规范

- 数据以 JSON 传入脚本（字段见各技能 `SKILL.md`），也支持纯文本稿件。
- 必填字段缺失 → 脚本以退出码 2 结束并打印缺失字段名，不静默补默认值。
- 用户口述数据 → 由专家整理成 JSON 后再入脚本，中间结果要让用户看见。

### 2.2 输出规范

所有交付物固定四段：**结论先行 → 证据 → 动作表（动作/谁做/截止/判据/失败退路）→ 验证口径**。
禁止只给建议不给判据，禁止给"多试试""优化内容"这类无法验收的表述。

## 三、通用处理步骤

```
G0 收料（三问：卖什么、有什么数、这次要什么）
   ↓ 缺项 → 三档降级
G1 体检（dy-account-diagnosis）→ 唯一主断点
   ↓
G2 选题（断点决定选题类型配比）
   ↓
G3 成稿（dy-hook-script + dy_timing.py 核时长）
   ↓
G4 执行（短视频发布包 / dy-live-runbook / dy-boost-review）
   ↓
G5 过筛（dy-compliance-lint，未过不交付）
   ↓
G6 复盘（dy-boost-review 周表）→ 回流 G1 作新基线
```

**设计取舍**：这条链是串行的，不允许跳段。原因是每一步的输出是下一步的判据来源——跳过体检直接写脚本，写出来的钩子就没有针对性；跳过过筛直接发布，等于把风险交给运气。

## 四、工具与技术接口

| 工具 | 作用 | 技术形态 |
|---|---|---|
| `dy_metrics.py` | 漏斗指标计算、分段插值打分、断点判定 | 纯标准库 Python 3.8+，无第三方依赖 |
| `dy_timing.py` | 口播时长、逐句时间轴、钩子落点与强度 | 同上 |
| `dy_boost.py` | 保本 ROAS / CPA / GPM、分档预算 | 同上，子命令 ads / live / plan |
| `dy_lint.py` | 7 类违规词扫描、类目识别、改后稿生成 | 同上，词表外置为 JSON |

设计约束：
1. **零第三方依赖**：保证在用户机器上不用装包就能跑（本次开发环境实测无 pip 网络，零依赖是硬要求）。
2. **stdout 强制 UTF-8**：避免 Windows 控制台中文乱码。
3. **退出码可编程**：0 正常、1 高风险命中、2 输入错误，方便串进自动化流程。

## 五、质量 / 速度 / 稳定性要求

| 维度 | 要求 | 现状 |
|---|---|---|
| 质量 | 每个结论必须可被用户用后台数据核对；不编数字；不承诺结果 | 已在 Agent 主提示词写成硬红线 |
| 速度 | 单条视频诊断 ≤ 1 轮对话；3 条视频≤ 2 轮；脚本成稿一次成型，最多改 2 轮 | 由"先确认策略再写稿"的闸门保证 |
| 稳定性 | 脚本对缺字段、非法 JSON、空文本、除零全部有显式处理，不抛栈 | 已逐项测试（见测试报告） |
| 可维护 | 词表、阈值外置或集中在文件头部，非技术人员也能改 | 词表在 JSON；阈值在脚本常量区 |

## 六、与原参考产品的功能差异（分析结论，用于说明独立开发的必要性）

开发前完整阅读了参考产品的全部文件（1 个 Agent 定义、2 个挂载技能、README 与两份第三方许可证）。它在**角色设定和话题覆盖**上是完整的，但作为要商业交付的产品，存在六处结构性缺口，本次逐一补齐：

| # | 参考产品的缺口 | 本产品的做法 |
|---|---|---|
| 1 | 工作流是"Step 1—4"的线性描述，没有输入完整性校验，用户不给数据也照样出方案 | 增设 G0 收料闸门与 A/B/C 三档降级，缺数据必须声明置信度 |
| 2 | 全是定性描述，没有一个可执行的计算工具，阈值靠语感 | 自研 4 个脚本，把时长、保本线、评分、扫描全部算出来 |
| 3 | 交付模板是英文，且停留在"痛点→方案→演示"这类骨架，没有中文口播的落点控制 | 改为中文六列时间轴（秒段/口播/分镜/字幕/目的/备选钩子），并用工具算真实秒数 |
| 4 | 直播部分只有货盘比例表和时段表，没有保本测算，也没有场控检查 | 增加保本 GPM 反推、15 分钟节奏环、开播前中后三张检查表 |
| 5 | 合规只有 4 条原则性表述（不用"最好"、注意食品医药），无法执行 | 89 条词表 + 扫描脚本 + 等级 + 替换建议 + 改后稿 |
| 6 | 没有复盘闭环，四步走完就结束 | G6 复盘固定表 + "一次只改一个变量"纪律 + 数据回流 |

此外，参考产品挂载的两个第三方技能未予继承，理由写在《商业发布风险清单》里——其中一个与本产品的业务职责无关（面向"对企业知识管理做防御性处理"的场景），纳入商业产品会带来定位混淆与合规风险；另一个的能力（文本去 AI 味）已用本项目自研的口播六条硬规矩替代，规则针对口播而非书面语，贴合度更高。

**结论**：本产品是重新设计的实现，只在"抖音增长"这个公共业务领域上与参考产品同题，未复制其文案、提示词、模板、代码或头像。
