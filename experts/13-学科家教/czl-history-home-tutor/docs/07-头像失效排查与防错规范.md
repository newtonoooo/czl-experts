# 头像失效排查与防错规范

**问题：** 专家导入到另一台（或新装的）WorkBuddy 后，能选中、能对话，但列表里的小图标不见了，变成一个汉字。
**结论：** 不是配置格式问题，也不是名称含中文的问题。**是头像文件在包内解析不到，客户端静默返回空字符串，前端于是画一个"名字首字 + 色块"。**

这份文档记录成因、本机的真实坏样本、以及本产品如何从流程上根治。

---

## 一、客户端到底怎么解析头像

以下逻辑取自本机 WorkBuddy 客户端主进程（`resources/app.asar`），关键字 `resolveAvatarUrl`：

```
async resolveAvatarUrl(avatar, expertDir) {
  if (!avatar) return ''                                  // ① 字段空 -> 空串
  if (/^(https?|data):/.test(avatar)) return avatar        // ② 只放行 http(s)/data:
  const rel = avatar.replace(/^\.\//, '')
  const abs = path.resolve(expertDir, rel)                // ③ 相对【专家包根】解析
  if (!abs.startsWith(path.resolve(expertDir) + path.sep)) return ''   // ④ 越界 -> 空串
  if (await pathExists(abs)) return toLocalFileUrl(abs)    // ⑤ 存在 -> local-file://
  return ''                                               // ⑥ 不存在 -> 空串
}
```

调用处：

```
if (manifest.avatar) manifest.avatar = await this.resolveAvatarUrl(manifest.avatar, expertRootDir)
```

前端拿到空串之后：

```
function resolveAvatarUrl(v) { return /^(https?|file|data|local-file):/.test(v) ? v : '' }
function getAvatarFallbackBackground(name) { return `var(--ec-avatar-fallback-bg-${(name?.charCodeAt(0)||0)%8+1})` }
```

**空串 → 走 fallback → 用名字第一个字的字符码选一个背景色 → 显示一个字。**

关键点：**第 ⑥ 步返回空串时不抛异常、不写日志、不提示。** 所以这个错误在界面上完全不可见，只能靠"图标变成了字"这一个现象反推。

## 二、六种触发条件（按发生概率排序）

| # | 触发条件 | 为什么必然变字 |
|---|---|---|
| 1 | **zip 里根本没有头像文件** | 大多数包只留了空的 `avatars/` 目录或 `.gitkeep`。**zip 不保存空目录**，导入后连目录都不存在 |
| 2 | **文件名与 `avatar` 字段不一致** | 字段写 `avatars/expert.png`，实际叫 `czl-history-home-tutor.png`，解析到不存在的路径 |
| 3 | **`avatar` 写成绝对路径或协议地址** | `C:/...`、`file://`、`local-file://` 全被第 ④ 步判越界；换机器后原路径必然失效 |
| 4 | **大小写不一致** | `Expert.PNG` vs `expert.png`，Windows 能读，macOS/Linux 读不到 |
| 5 | **头像放进了子目录** | 解析以包根为基准，`skills/x/avatar.png` 会被当作包根下的 `skills/x/avatar.png`，不在预期位置 |
| 6 | **展示快照缓存了旧的本地绝对路径** | 客户端把头像缓存成 `local-file://local/C:/Users/.../avatars/expert.png`；换机器、换用户名后这条地址指向空气，界面沿用旧快照就仍是字 |

另外两个不致命但会扣分的：尺寸不是 512×512、体积超过 500KB。

## 三、本机实测（2026-10-31）

对 `~/.workbuddy/plugins/marketplaces/` 下全部 100+ 个专家包做了头像体检，**本机确实存在三个同类型的坏样本**：

| 专家包 | `avatar` 字段 | 实际情况 | 导入后表现 |
|---|---|---|---|
| `czl-chemistry-home-tutor` | `avatars/expert.png` | **文件不存在**（目录只有 `.gitkeep`） | 显示"顾" |
| `czl-physics-home-tutor` | `avatars/expert.png` | **文件不存在** | 显示"顾" |
| `czl-english-home-tutor` | `avatars/expert.png` | **文件不存在** | 显示"渡" |

这三例的共同点：**建包时先生成了目录和 `.gitkeep`，头像那一步没跑成，打包时也没检查。** 源目录在本机看着"有个 avatars 文件夹"，实际是空的。

同时扫了 `assistant-display/*.json` 共 467 条快照，发现 2 条已失效的本地头像地址（`gaochi-content-ops`，包已被删除），说明第 6 条触发条件也真实存在。

**这解释了你看到的现象：** 不是"新 WorkBuddy 不认这个专家"，而是那个包里压根没有图片可显示。开发者本机之所以看着正常，是因为源目录里可能还留着图，或者界面沿用了旧快照。

## 四、根治办法（本产品已落地）

### 1. 字段写法固定为最短相对路径

```json
"avatar": "avatars/expert.png"
```

不带 `./`、不带盘符、不带协议头、全小写 ASCII、正斜杠。

### 2. 头像必须是真实文件，且必须进 zip

- 用 `tools/prepare_avatar.py` 生成，强制 512×512、8 位 RGB PNG、≤500KB。
- 打包时由 `tools/build_release.py` **回读 zip**，确认 `包名/avatars/expert.png` 这一条真的存在。

### 3. 打包前跑体检

```bash
python tools/verify_avatar.py .
```

脚本把本文第一节的六条规则逐条验一遍，并在失败时直接打印"导入后会显示成名字首字"，同时列出 `avatars/` 里实际有哪些文件——**因为最常见的错就是名字对不上。**

### 4. zip 结构只允许一个顶层目录

客户端的导入逻辑（`installExpertZipFromPath`）先找 `zip根/.codebuddy-plugin/plugin.json`，找不到再要求"**恰好只有一个顶层目录**"（`resolveSingleTopLevelDir`）。所以：

- ✅ `czl-history-home-tutor/.codebuddy-plugin/plugin.json`
- ❌ 直接把 `.codebuddy-plugin/` 放在 zip 根下（能装，但装完目录名会变成 `expert-package`，不易维护）
- ❌ zip 根下同时有包目录和 `__MACOSX/`、`README.txt`（顶层目录数 ≠ 1，直接 `invalid_package`）

### 5. 导入后重启一次

快照缓存的是绝对路径。迁移场景下不重启，界面可能继续用旧路径。

## 五、换机器/上架前的自查清单

- [ ] `avatar` 字段是 `avatars/expert.png` 这样的最短相对路径
- [ ] 该文件真实存在，`ls avatars/` 能看到它（不是只有 `.gitkeep`）
- [ ] 512×512，PNG，≤500KB
- [ ] 文件名与字段**逐字符**一致（大小写也要一致）
- [ ] `python tools/verify_avatar.py .` 退出码为 0
- [ ] `python tools/build_release.py .` 的第 4 步回读验收通过，且打印出的"头像条目"体积不为 0
- [ ] 导入后重启客户端
- [ ] 若仍是字：检查 `~/.workbuddy/assistant-display/*.json` 里是否有指向旧路径的 `local-file://` 快照

---

## 六、给平台侧的两条建议（仅记录，非投诉）

1. 头像解析失败时建议在控制台打一条 warning，而不是静默返回空串。目前这个错误对开发者完全不可见，只能靠现象猜。
2. 展示快照里的 `local-file://` 地址建议带"来源目录指纹"，目录变更时重建，而不是继续沿用。
