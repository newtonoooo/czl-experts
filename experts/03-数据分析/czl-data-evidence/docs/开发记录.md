## 一、需求从哪里来

起点是一个通用需求："做一个数据分析专家"。同类产品通常覆盖这些环节：澄清需求 → 数据体检 → 探索 → 归因 → 检验 → 汇报。这是行业通用流程，属公共知识，不专属于任何产品。

我做了两步：

1. **功能归纳**：把上述环节拆成可交付的动作（要什么输入、产出什么、判据是什么）。
2. **找差异**：如果只是把通用流程再写一遍，产品没有存在理由。我选择在一个具体的痛点上做深：**结论凭什么可信**。于是有了"三账五验"和 A/B/C/D 定级。

需求阶段我只查看了同类产物的**文件构成**（多少个角色、多少份文档、脚本分几类），用于确认功能覆盖面，没有抄它的提示词、工作流定义、脚本代码或文档表述。原因是它的署名不是我，许可证也未授予商业分发权，直接复用会带来权利风险。

## 二、设计决策

### 1. 为什么是单 Agent，不是多角色团队

多角色（分析师 + 工程师 + 统计师 + 顾问 + 复核官）看起来更专业，但有两个实际代价：每增加一个角色，就要多维护一份提示词与一套交接协议；而真实分析里，判断是连续的，硬切成角色容易在交接处丢信息。

我改成"一个人 + 六道工序 + 五道验证"。工序负责节奏，验证负责质量。复核不靠另一个角色，靠一张证据账——五验逐条打勾，比"另一个 AI 说行"更可查。

### 2. 为什么把"定级"做成核心交付物

用户真正焦虑的不是"没有结论"，是"这个结论敢不敢用"。A/B/C/D 四个字解决的正是这件事。它同时约束了我自己：没有对照就不能给 A，样本不够就只能给 C。定级是产品对用户的承诺，也是对自己的限制。

### 3. 为什么脚本全用标准库

三个理由：安装零门槛（不用 pip）、可审计（没有依赖树可以藏东西）、跨平台（不依赖编译产物）。代价是要自己写统计分布、分位数、bootstrap 和 docx 生成——多花时间，但换来"你打开就能看到每一行在算什么"。

### 4. 为什么不做联网、不做预测

联网抓平台数据有合规风险，且分析结论不应依赖实时抓取；预测则容易让用户据此压预算、压库存，一旦失准代价由用户承担。产品明确划掉这两块，写在提示词和 README 里。

### 5. 为什么样例数据要带"手算真值"

如果样例只是"看着像"，测试就退化成"能跑就行"。我给四份数据都设计了可以口算核对的真值（比如 5 月 40,000 → 6 月 36,000，量贡献 -12,000、价贡献 +11,428.57、交互 -3,428.57）。这样脚本算错任何一个环节都会被测出来。

## 四、开发中发现并修复的问题

这些都是我自己写出来的问题，记录在此以便复盘。

| # | 问题 | 现象 | 修法 |
|---|---|---|---|
| 1 | 漏斗的"相对跌幅"参照系用错 | 拿相邻两步的单步率互相比，出现"第 3 步比第 2 步提升 46.5%"这种无意义结论 | 改为两种模式：无基线时对比"各步平均单步率"并明确声明这不是真实跌幅；新增 `--baseline` 支持真正的两期对比（实测加购 -15.8%） |
| 2 | 同期群把"观测不到"算成留存 0 | 均值被拉低（36.7%），区间出现 0.0% | 增加可观测性判断，观测不到的格子标「—」并从均值剔除；同时裁掉整列为空的期数（12 列缩到 3 列） |
| 3 | 占比列在负增长时符号翻转 | 显示"占总变化 +300%" | 改为"占变化绝对值比重"，各项加起来 100% |
| 4 | 字符串里的 `%%` 被字面打印 | 输出"超过 30%%" | 去掉多余转义 |
| 5 | 金额单位在同行内混用 | 一行里同时出现"1.00 万元"和"9,000.00 元" | 调整阈值：≥10 万才用"万"，其余带千分位 |
| 6 | 样例数据自带"断档" | 体检评级被扣到 C，使用者会误以为工具报错 | 生成器改为每天都有数据；同时把样例放大到分组 ≥200，评级回到 A |
| 7 | 测试脚本把产物写进包内 | `docs/运行目录/` 里出现 docx、html、空 csv | 测试改为在系统临时目录运行，交付包内零残留 |
| 8 | 体检报告中"完整率最高列"的措辞 | 零缺失时说"缺失率最高的列是订单号，0.00%"，读起来像有问题 | 零缺失时改为"所有列无缺失" |

修完这些问题后，62 项自动化测试全部通过（见 `docs/测试报告.md`）。

## 五、没有做的事（避免误导）

- **没有做 Excel 直读**：需要用户另存为 CSV。原因是 `.xlsx` 解析要引入 zip + XML + 共享字符串等一整套逻辑，收益不抵复杂度，且 CSV 更通用。
- **没有做图表输出**：本产品定位是"判断与证据"，画图交给专门工具，只给"该画哪些指标"的规格。
- **没有做多语言**：提示词与文档为中文，面向中文商业场景。
- **没有做联网校验外部数据**：不联网，也不会声称自己核对过外部口径。
- **没有用任何第三方代码**：包括不舍得为"看起来更专业"而引入开源统计库。

## 七、后续维护建议

1. 指标定义库（`references/02`）最容易过时，建议每季度核对一次；
2. 若平台或行业出现新的统计口径（如新的归因模型），补进 `references/03`，不要改脚本；
3. 脚本改动必须同步跑 `run_functional_tests.py`，真值不允许为了"测试通过"而修改；
4. 版本号遵循语义化：文档修订 +0.0.1，新增工作流或脚本 +0.1.0，接口不兼容 +1.0.0。
