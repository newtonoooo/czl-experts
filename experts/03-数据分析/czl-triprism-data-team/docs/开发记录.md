## 二、功能继承与补充

### 继承的通用思路（不属任何人的专有表达）

- 一份表格 → 多视角并行分析 → 合成一份报告
- 视角互斥（时间 / 结构 / 异常三分）
- 多格式交付（网页 / 表格 / 幻灯片）

### 补充的六个环节（目标产品没有的）

| # | 补充 | 为什么必须补 |
|---|---|---|
| 1 | **体检闸门** | 原流程直接进入分析。数据不可用时，三路会各自产出"看起来专业"的垃圾结论。新增 P1：评级 A–D，`block` 直接停 |
| 2 | **口径冻结** | 原流程三个分析者各自读表、各自定分母，报告易自相矛盾。新增 P2：产出 `contract.json` 并机器校验 |

| 5 | **分组内异常检测** | 只看整列分布会被组间量级差异掩盖。新增组内稳健 z + 相对中位数偏离 40% 双规则 |
| 6 | **运行清单** | 原流程无留痕。新增 `run.json`：输入 sha256、耗时、输出清单，可追溯 |

## 三、架构决策

### 3.1 为什么是五阶段而不是"直接分析"

数据分析的失败大多不是算错，而是**在错的前提上算对了**。
把"能不能分析"和"怎么算"拆成两道独立闸门，比事后解释便宜得多。

### 3.2 为什么加"校验官"这个不产出结论的角色

三个并行角色必然产生：口径漂移、重复结论、方向冲突。
如果让主理人自己校验，等于让出题人自己判卷。
独立角色 + 机器复算，才能把"我觉得对"变成"算过，对"。

### 3.3 为什么零第三方依赖

商业发布要控三件事：许可证风险、版本漂移、安装失败率。
`pandas / numpy / openpyxl / python-pptx` 每一个都带来上面三项中的至少一项。
最终用标准库自实现了 CSV/XLSX 读写、统计、SVG 图表、XLSX 写出，代价是多写了约 1600 行代码，收益是**在任何装了 Python 的机器上都能跑**。

### 3.4 为什么不做 .pptx

从零拼 OOXML 幻灯片（母版 + 版式 + 主题 + 关系）能做出文件，但无法在本机验证 PowerPoint 是否弹"修复"提示。
与其交付一个"结构上合法、视觉上没验过"的文件，不如输出 `deck_spec.json` 交给平台成熟的 PPT 能力。
这是**能力边界的诚实处理**，不是偷懒。

### 3.5 图表为什么用内联 SVG

- 无外部依赖（不引 ECharts/Chart.js，避免许可证与 CDN 依赖）
- 单文件离线可看，打印成 PDF 不失真
- 数字直接来自 JSON，渲染层不做任何计算，杜绝二次口径漂移

## 四、头像图标显示异常的排查（重点）

### 4.1 现象

目标专家团导入到另一个 WorkBuddy 实例后，选中该专家，**左上角小图标不显示，退化成一个汉字**（首字占位）。

### 4.2 排查过程与证据

**第一步：排除图片本身的问题**

```
lead.png            512×512  RGB  152,889 字节
trend-analyst.png   512×512  RGB   27,236 字节
structure-analyst   512×512  RGB   22,837 字节
anomaly-analyst.png 512×512  RGB   27,236 字节
```

四张都是合法方形 PNG，尺寸一致。平台代码中头像大小上限为 `5242880`（5MB），
`lead.png` 仅 149KB，**不是尺寸或格式问题**。

**第二步：看它被装到了哪个通道**

本机安装记录：

```json
"<目标包名>@experts": [{
  "installPath": "...\\plugins\\cache\\experts\\<目标包名>\\1.0.1"
}]
```

对比本机其他能正常显示图标的专家：

```json
"czl-guatai@my-experts": [{ "installPath": "...\\plugins\\cache\\my-experts\\czl-guatai\\1.1.1" }]
```

关键差异：**`experts` 是插件市场通道，`my-experts` 是自定义专家通道。**

**第三步：读平台的解析逻辑（`app.asar` 反编译字符串）**

自定义专家通道 `ExpertCustomRuntime`：

```js
async readCustomExpertFromDir(e, t) {
  ...
  r.avatar &&= await this.resolveAvatarUrl(r.avatar, e);
  if (Array.isArray(r.members)) for (let t of r.members)
    t.avatar &&= await this.resolveAvatarUrl(t.avatar, e);
  ...
}
async resolveAvatarUrl(e, t) {
  ...
  if (await pathExists(r)) {
    let t = await O.stat(r);
    return t.size > ge ? (warn("avatar file is too large"), "") : l.v(r);   // → local-file:// URL
  }
  return "";
}
```

→ 自定义通道会把本地相对路径转成 `local-file://` URL，**头像能显示**。

插件/清单通道 `buildExpertFromManifest`：

```js
function buildExpertFromManifest(e, n) {
  return a.Fn({ id: n, categoryId: "", name: {zh: r, en: r},
                avatar: "",            // ← 头像被硬编码为空，不读 plugin.json 的 avatar
                plugin: e.name, expertType: ..., agentName: e.agentName, prompt: {} });
}
```

→ 插件通道**根本不读 `plugin.json` 里的 `avatar`**。

团队头像还有一条独立路径 `attachExpertAssistantIdentity`：

```js
let i = resolveExpertAvatarUrl(t.avatar);   // t = leader member
...
function resolveExpertAvatarUrl(e) { ... return buildExpertUrl(t.startsWith("/") ? t : "/" + t); }
function buildExpertUrl(e) { return `${Vi.baseUrl}${e}`; }
// Vi.baseUrl = "https://acc-1258344699.cos.accelerate.myqcloud.com/workbuddy/expert-marketplace"
```

→ 相对路径 `avatars/lead.png` 会被拼成**远程 CDN 地址**，本地包在该地址上不存在 → 404 → 前端回退成首字文字头像。

**第四步：确认团队团长匹配**

```js
function pickTeamLeaderMember(e) {
  let t = readTeamMembers(e);              // 仅当 expertType === "team" 才读 members
  if (t.length === 0) return;
  let n = readTrimmedString(e.leader);
  return t.find(e => e.role === "lead") ?? (n ? t.find(e => readMemberId(e) === n) : void 0) ?? t[0];
}
```

→ 团长按 `role === "lead"` → 顶层 `leader` 字段 → `members[0]` 三级回退。
目标包的 `members[0]` 有 `role: "lead"`，这一层没问题，但它的 `avatar` 走了 CDN 解析，仍然失败。

### 4.3 结论

> **不是图片坏了，是安装通道不对。**
> 该专家包被当作「插件市场插件」安装（`plugins/cache/experts/...`），
> 这条通道下 `plugin.json` 的 `avatar` 被丢弃，团队团长头像被拼成远程 CDN 地址而 404，
> 前端于是回退为「名称首字」占位。

同类包如果装进 `my-experts`（自定义专家通道），`avatar` 会被转成 `local-file://`，图标正常。

### 4.4 本产品的规避设计

针对上述机制，做了三层兼容：

1. **安装位置**：包同时投放到 `my-experts/plugins/czl-triprism-data-team` 并在
   `my-experts/.codebuddy-plugin/marketplace.json` 登记 → 走自定义专家通道，头像可解析
2. **路径写法**：`avatar` 用 `avatars/lead.png`，不带 `./`、不带前导 `/`、不写成 URL
3. **团队结构**：`members` 中团长显式 `role: "lead"`（`pickTeamLeaderMember` 的第一优先级）
4. **体积**：5 张头像 57–187KB，远低于 5MB 上限；512×512 正方形

> 曾同时提供 `leader` 与 `icon` 两个字段作双保险。后经上传校验确认，二者均为平台非标准字段
> （本机 24 个专家包中仅本包使用），已移除：团长身份由 `role: "lead"` 表达，
> 头像由 `avatar` 表达，多余字段只会增加上传被拒的风险。

### 4.5 上传校验规则（v1.0.1 补记）

首次上传被平台校验器拒绝，报三条：

```
tags 须固定 3 个，当前 4 个
defaultInitPrompt.zh 必须与 quickPrompts[0].zh 一致
defaultInitPrompt.en 必须与 quickPrompts[0].en 一致
```

这三条在本地 `app.asar` 里搜不到，说明校验发生在服务端。

**反推方法**：统计本机 24 个专家包的字段规格，找出「已通过校验」的共同特征：

| 特征 | 24 个包的实际情况 |
|---|---|
| `tags` 数量 | 21 个为 3；不合规的 2 个正是出问题的包 |
| `quickPrompts` 数量 | 全部为 3 |
| `defaultInitPrompt == quickPrompts[0]` | 21 个为真；不合规的 2 个为假 |
| `displayDescription.zh` 长度 | 合规包 41–52 字；不合规包 93、96 字 |
| `leader` / `icon` 字段 | 仅本包使用（非标准） |

据此修正：tags 降到 3 个、默认提示与第一条快捷提示完全对齐、
`displayDescription.zh` 压到 57 字、删除 `leader` 与 `icon`。

**教训**：平台字段规则没有公开文档，只能靠「已知能通过的样本」反推。
这类规则已全部写进 `tools/verify_package.py`，以后打包前跑一次即可拦截。

### 4.6 settings.json（v1.0.2 补记）

修完 tags 与默认提示后再次上传，报：

```
settings.json 不存在或无法读取（Team 型专家必须在 plugin root 下提供 settings.json）
```

**排查**：

1. 本机 24 个专家包**全都没有** settings.json——因为它们都是 `agent` 型，只有 Team 型需要
2. 平台内置插件里有：`welcomemode-work/settings.json` 内容为 `{"agent": "work"}`
3. 客户端解析函数 `readGeneratedAgentOverride()` 只接受**单字段** `agent`：

```js
let n = JSON.parse(t);
return Object.keys(n).length !== 1 || typeof n.agent !== 'string' || n.agent.trim() === ''
  ? null : { agent: n.agent };
```

**结论**：Team 型专家的 `settings.json` 用来指定会话默认 agent（即团长），
形态就是 `{"agent": "<agentName>"}`。

**已加**：插件根目录 `settings.json` → `{"agent": "czl-triprism-data-team"}`。

**一个副作用要知道**：平台在激活专家时会调用 `removeGeneratedAgentOverrideFile()`，
把这种形态的文件当作「运行时生成的覆盖文件」删掉。所以**安装副本在首次激活后可能丢这个文件**。
这不影响运行（团队结构在 `plugin.json` 的 `teamInfo` / `members` 里），
但重新打包必须从源码目录打，不能从安装目录打。

### 4.5 仍需你确认的一件事

上述结论基于对平台代码的静态分析 + 本机安装记录对比，
**尚未在"全新 WorkBuddy 实例 + 官方导入入口"上实测**。

建议验证步骤：
1. 在目标实例的专家中心用导入功能装入本包
2. 选中「三棱镜·专业数据分析专家团」，看左上角是否显示棱镜头像
3. 若仍显示文字，检查安装路径落在 `cache/experts/` 还是 `cache/my-experts/`；
   若落在 `experts/`，说明该入口走插件通道，需要改由「我的专家」入口导入

## 六、测试驱动的三次改进

1. **默认指标选错**：首轮报告围绕"订单数"展开，因为它是第一个数值列。
   → 加入金额类关键词优先级 + 波动性排序，改为优先"销售额"。

2. **拐点误报**：`2025-02` 被报成拐点（前面只有 1 个点）。
   → 改为前后各留 ≥2 期样本，且序列长度 ≥7 才检测。

3. **组内异常漏检**：埋点在第 78 行的 42% 下跌未被发现（整列 z 不敏感）。
   → 新增组内检测：稳健 z ≥3.5 或相对中位数偏离 ≥40%，且用维度交叉分组。

每一次都是先写用例、看它失败、再改实现，不是事后补测试。

## 七、原创性声明

本产品的以下部分为独立设计，与其他同类产品在表达层面无重合：

- 五阶段闸门式流水线（P0–P5）与退出码约定
- 角色划分与命名（主理人 / 走势官 / 拆解官 / 验伤官 / 校验官）
- 派单信封与回传信封的 JSON 结构
- `recheck` 复算规格的 9 种算子（delta_pct / mom_pct / inflection_delta / share / hhi / share_shift / value_at / duplicate_rows / row_count）
- A/B/C/D 证据分级与 PASS/FAIL/SKIP 三态判定
- 组内相对中位数偏离规则
- 报告七节结构、四件套组合
- 全部代码、文档、头像视觉概念

功能层面（并行多视角分析、多格式交付）属通用需求，不主张排他。
