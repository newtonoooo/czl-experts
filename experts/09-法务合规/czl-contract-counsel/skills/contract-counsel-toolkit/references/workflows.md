# 契约守门人 · 五条工作流规格

本文件是五条工作流的唯一权威定义。Agent 执行时按此规格走，不临场发明流程；脚本 `scripts/cc.py` 是各工作流中"能自动化的部分"，Agent 负责判断、补位与交付。

公共约定：

- **站位（stance）**：`a` = 甲方/委托方/出租人/用人单位/出借人；`b` = 乙方/受托方/承租人/劳动者/借款人；`neutral` = 中立。未指定时按"提出需求的一方即己方"，并在结论中写明假设。
- **工作目录**：默认 `.contract-workspace`，与用户合同文件分离，便于打包归档。
- **信息透传**：合同类型、双方主体、站位、金额、期限在首次确认后跨工作流复用，不重复询问。
- **失败不空转**：同一操作失败 2 次即停止，报告已完成的步骤与卡点，给出 1-2 个替代方案。

---

## W1 起草台（Drafting）

**职责**：把业务诉求装配成结构完整、条款齐备、可直接签署的合同文本。

**输入参数**

| 参数 | 必填 | 说明 | 缺失时的处理 |
|---|---|---|---|
| `type` | 是 | 合同类型（可别名） | 🔴 必须问：类型决定整套条款结构 |
| `a_name` / `b_name` | 是 | 双方主体全称 | 🔴 必须问：主体不明无法成约 |
| `amount` | 视类型 | 金额（数字） | 采购/服务/借款/租赁必填；🟢 缺失则正文留空并标注 |
| `subject` | 是 | 标的/服务范围/房屋 | 🟢 缺失用类型默认描述，标注待补 |
| `stance` | 否 | 用户站位 | 默认 `a`，影响管辖地写法 |
| `start_date` | 否 | 起始日 | 默认今天 |
| `term_months` | 否 | 期限（月） | 用类型默认（如租赁 12 个月） |
| `delivery_days` / `payment_days` / `acceptance_days` / `warranty_months` | 否 | 交付/付款/验收/质保 | 用行业默认（30/30/7/12） |
| `spec` | 否 | 完整 JSON（含条款覆盖、增删） | 见 `io_spec.md` |

**执行步骤**

1. 解析类型（含别名）；解析失败即返回可选清单。
2. 合并三层默认值：全局默认 → 类型默认 → 用户输入；记录每一处用到的默认值。
3. 计算派生字段：金额大写、到期日、押金（租金×月数）、试用期工资（80%）、管辖地。
4. 装配正文块：标题 → 编号 → 双方主体 → 鉴于条款 → 各条正文 → 签署页。
5. 渲染 `.docx`（自研 OOXML 写入器）+ `.md` 预览 + `.meta.json`（含履约节点提示）。
6. 结构自检：包内部件齐全、XML 可解析、段落与表格数正常。

**判断条件**

- 金额 ≥ 100 万或涉及股权/担保/涉外/建设工程 → 交付时追加"建议执业律师复核"提示。
- 用户站位为付款方/付款义务人 → 预付款比例默认压到 30%，验收期限给足 7-10 个工作日。
- 用户明确要求"改某条" → 走 `clauses_override`，只改该条，不重排全篇。
- 用户要求加自定义条款 → 走 `clauses_add`，排在正文末尾、签署页之前。

**输出格式**

`.docx`（A4、宋体小四、1.5 倍行距、首行缩进 2 字符、条款标题黑体加粗、签署区两栏无框线）+ `.md` 预览 + `.meta.json`（`used_defaults`、`ledger_hints`、`verify` 结果）。

**异常处理**

- 金额非数字 → 保留原文，`used_defaults` 标注，正常出稿。
- 占位符无法填充 → 正文写 `＿＿`，`missing_placeholders` 列出，交付时提醒补齐。
- `.docx` 写入失败 → 降级只交付 `.md`，明确说明未生成 docx，不给假路径。
- 用户要求"先给大纲" → 可以给，但必须紧接着出文件，不能停在大纲。

**依赖**：`clause_library.json`、`cc_docx.py`、`cc_common.py`。

**与其他工作流的关系**：产出可进 W2（自查）、W3（改版后比对）、W5（导入履约节点）。W2 的高风险条款回流到 W1 改稿。

## W2 审查台（Review）

**职责**：对既有合同逐条识别风险，分级、给改法、给依据，并指出缺失的必备要素。

**输入参数**

| 参数 | 必填 | 说明 | 缺失时的处理 |
|---|---|---|---|
| `file` | 是 | `.docx` / `.txt` / `.md` | 其他格式：明确告知不支持并要求转换 |
| `type` | 否 | 合同类型 | 自动识别（要素命中打分），置信度低时提示用户确认 |
| `stance` | 否 | 审查站位 | 默认 `a`，结论中显式写明 |
| `focus` | 否 | 关注点（如"只看押金和提前解约"） | 有则结论优先回应，但风险表仍全量 |

**执行步骤**

1. 读取正文（`.docx` 直接解析 OOXML，不经第三方库）；识别失败即返回格式说明。
2. 切条：按"第X条"→ 序号标题 → 空行段落 三级退化。
3. 类型识别：要素命中数 ×2 + 别名命中数 ×1，取最高分。
4. 要素覆盖检查：对该类型必备 7-8 个要素逐一判在/缺。
5. 规则扫描：regex / numeric / absent / mutual / conditional_absent 五类；同一规则同一位置只记一次。
6. 打分与结论：按等级权重做指数衰减，映射为四档结论。
7. 生成 Markdown 报告与 JSON；Top3 必改条款给替换文本。

**判断条件**

- 识别类型与用户描述不一致 → 以用户指定为准，并在报告注明。
- 风险 > 10 条 → 全部高风险展开，中低风险折叠为统计 + 追问入口。
- 合同为空白模板（大量 `【】`、`＿＿`）→ 先提示这是模板，逐条填实优先于条款审查。
- 文本含大量乱码或不足 300 字 → 提示可能解析失败，请确认文件，不硬出结论。

**输出格式**

Markdown：结论 → 风险表（等级｜位置｜问题｜证据）→ 必改 Top3（问题/后果/改法/依据）→ 其余改法速查 → 缺失要素 → 免责声明。
JSON：`findings[]`（含 `rule_id`、`level`、`clause`、`clause_index`、`evidence`、`why`、`fix`、`basis`）、`coverage[]`、`counts`、`score`、`verdict`。

**异常处理**

- 单条规则正则异常 → 跳过该规则，其余照跑，不中断。
- 条款切分只得到 1 条 → 退化按段落切，并在报告注明"未能按条号切分，定位可能不精确"。
- 用户给的是扫描件图片 → 直接说明无法读取，要求提供文本。

**依赖**：`risk_rules.json`、`clause_library.json`、`cc_common.py`。

**与其他工作流的关系**：高风险条目 → W1 改稿；涉及条文争议 → W4 核查；改后版本 → W3 比对。

## W3 比对台（Compare）

**职责**：判断两版合同的实质差异，分出"必须谈"和"可以让"。

**输入参数**

| 参数 | 必填 | 说明 | 缺失时的处理 |
|---|---|---|---|
| `a_file` | 是 | 原版 | 缺失则询问哪一版是原版 |
| `b_file` | 是 | 新版（对方回传版） | 同上 |
| `stance` | 否 | 站位 | 默认 `a`，用于判断哪一方受损 |

**执行步骤**

1. 两版分别切条。
2. 对齐：条号重合率 ≥60% 按条号对齐；否则按顺序对齐并提示"两版条号体系不一致"。
3. 逐条比对：文本相似度 + 数值集合比对（金额/比例/天数/月数/年数）+ 甲乙方指向翻转检测。
4. 分级：数值变动或指向翻转为重大；核心利益条款实质改写（相似度 <0.90）为重大；表述强化为一般；措辞润色为轻微。
5. 过滤：纯排版、标点、空白差异不计入清单。
6. 生成变更全景、重大变更详表、谈判清单（最多 3 条，附让步建议）。

**判断条件**

- 用户没说哪版是原版 → 按传参顺序（A=原版），报告开头显式写明，允许一句话调换。
- 变更 > 20 处 → 重大全列，一般与轻微折叠统计。
- 两版条款数差异 > 50% → 提示可能是两份不同合同，先确认再比对。

**输出格式**

Markdown：变更全景（新增/删除/修改 + 分级统计）→ 重大变更表（位置｜类型｜原版｜新版｜影响）→ 一般变更 → 轻微变更 → 谈判清单 → 免责声明。
JSON：`changes[]`（含 `kind`、`level`、`similarity`、`numbers`、`impact`）、`stats`、`negotiation[]`、`align_mode`。

**异常处理**

- 任一文件格式不支持 → 立即停止，说明哪一份不支持，不输出半成品报告。
- 两版完全一致 → 明确回复"未发现差异"，不编造变更项。

**依赖**：`cc_common.split_clauses`、`difflib`。

**与其他工作流的关系**：重大变更常需 W4 提供依据；谈判清单可直接作为 W1 改稿的输入。

## W4 依据核查（Authority）

**职责**：把"我觉得有风险"换成"哪一条这么规定"，并说明适用条件与例外。

**输入参数**

| 参数 | 必填 | 说明 | 缺失时的处理 |
|---|---|---|---|
| `q` | 是 | 关键词 / 法名 / 具体场景 | 场景过泛时追问：金额、地区、争议阶段、对方态度 |
| `context` | 否 | 关联的合同条款 | 有则给出针对性结论 |

**执行步骤**

1. 先本地检索 `law_index.json`（`laws` 命令），命中即用条号 + 要点。
2. 判断是否需要原文：用户要"法条原文""具体第几款" → 必须联网核对官方来源（国家法律法规数据库 / 最高法 / 中国政府网），核对前只给要点。
3. 检查 `confidence`：`verify` 的条号在结论中标注"条号请复核"。
4. 输出"条号 → 要点 → 适用条件 → 例外情形"，并与用户合同条款挂钩。

**判断条件**

- 问题属常识性概念（什么是不可抗力）→ 直接解释，不必引用条号。
- 涉及地方性规定（最低工资、租金指导价、限购）→ 必须提示"以当地现行规定为准"，不套用其他城市。
- 涉及效力判断（合同是否有效）→ 只提示风险点与判断因素，不下结论。

**输出格式**

结论（1 句）→ 可执行建议（有则列）→ 解释 → 法律依据（法名 + 条号 + 要点 + 置信度）→ 免责声明。

**异常处理**

- 索引无命中 → 明确说"本地索引未覆盖"，联网检索后仍无把握 → 用口径化表述，不编条号。
- 用户引用的条文已修正（如旧民诉法条号）→ 指出可能已变更，给现行条号或建议核对。

**依赖**：`law_index.json`；（联网核对时）官方来源。

**与其他工作流的关系**：为 W2 的风险条目补依据；为 W3 的重大变更提供谈判理由；为 W1 的条款设计提供边界。

## W5 履约跟踪（Ledger）

**职责**：把合同里"谁在什么时候该干什么"变成可核对的节点台账。

**输入参数**

| 参数 | 必填 | 说明 | 缺失时的处理 |
|---|---|---|---|
| `contract` | 是 | 合同名称 | 用文件名兜底 |
| `item` | 是 | 节点名称（可多个） | 从 draft 的 `ledger_hints` 自动带出 |
| `obligor` | 否 | 义务方 | 留空，列表显示为空 |
| `due` | 视情况 | 截止日 | `import` 时按"基准日 + 偏移天数"计算 |
| `note` | 否 | 备注 | 可空 |
| `path` | 否 | 台账文件 | 默认 `.contract-workspace/ledger.json` |

**执行步骤**

1. `import`：读起草产出的 `.meta.json`，按 `ledger_hints` 的偏移天数批量生成节点（基准日 = 合同起始日）。
2. `add`：手工补节点（如对方口头承诺的整改期限）。
3. 状态计算：按当天日期实时算出剩余天数，映射为 正常 / 临近（≤7 天）/ 逾期 N 天 / 已完成 / 无截止日。
4. `report`：输出台账表，逾期项单独点名。

**判断条件**

- 节点已逾期 → 优先提示"立即处理"，并给补救动作（补发催告、留存凭证、评估解除权）。
- 无截止日的节点 → 标"无截止日"，提醒补明时间。
- 同一合同节点 > 10 个 → 按义务方分组展示，避免表格过宽。

**输出格式**

台账表（编号｜合同｜节点｜义务方｜截止日｜剩余｜状态）+ 逾期清单 + 免责声明；JSON 含 `days_left`、`state`。

**异常处理**

- 台账文件损坏 → 报错要求先备份再重建，不静默覆盖用户数据。
- 编号不存在 → 返回可用编号列表。
- 日期格式错误 → 标"日期格式有误"，不猜日期。

**依赖**：`cc_draft` 的 `.meta.json`（可选）。

**与其他工作流的关系**：消费 W1 的产出；W2 发现"没有约定验收期限"时，可建议在 W1 补齐后重新导入节点。

## 工作流串联示例

**场景：对方发来一份合同，要今天回签**

1. W2 审查 → 得到 5 项高风险 + 3 项缺失要素。
2. W4 核查争议最大的两条（违约金比例、管辖约定）→ 拿到条号与要点。
3. W1 按改法重出 `.docx`（只覆盖争议条款）。
4. W3 把改后版本与对方原版比对 → 生成谈判清单。
5. 签完后 W5 导入履约节点 → 到期提醒。

**场景：公司要模板化 20 份采购合同**

1. W1 用 `spec` + `clauses_override` 固化公司口径，出母版。
2. W2 审母版 → 确认无规则覆盖范围内的风险（自检基线）。
3. 每份合同只改 `a_name/b_name/amount/subject` 四项，其余继承。
4. W5 批量导入节点。
