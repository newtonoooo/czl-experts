## 阶段一 · 功能分析（只提取能力，不提取文案）

对"资深合同法专家"这一类产品做了能力层面的拆解，归纳出用户真正会提的五类需求：

1. 给一份能签的合同（起草）
2. 判断手上的合同有没有坑（审查）
3. 看清两版改了什么（比对）
4. 要一个"哪条这么规定"的依据（检索）
5. 签完之后别忘了节点（履约）

**取舍**：原类产品通常包含"在线发起签署"，该能力必须依赖第三方电子签服务（账号、鉴权、额度、上传合同到云端）。本产品不接入任何第三方签署服务，因此**不宣称具备在线签署能力**，把这部分需求用"履约台账"承接——签不了，但能帮用户盯住签完之后的事。这是功能选择，不是能力缩水。

**没有做的事**：未复制对方提示词的任何句子、未沿用其阶段编号体系（Phase 1–5）、未沿用其额度/鉴权话术、未纳入其依赖的第三方 Skill（含其 SKILL.md、脚本与 LICENSE 文件）、未使用其头像与 README 文案。

## 阶段二 · 架构设计

### 决策 1：不引入 python-docx，自研 DOCX 写入器

合同文档只需要"标题 + 段落 + 表格 + 签署区"。引入 python-docx 会带来第三方依赖与再分发授权问题，且用户机器上未必有该包。因此按 OOXML 最小可用子集手写包结构（`cc_docx.py`，414 行），产出物能被 Word / WPS / pandoc 正常解析。

代价：不支持复杂排版（图片、页眉页脚、目录、批注）。合同场景不需要，接受。

### 决策 2：规则引擎数据化，不改代码就能改口径

31 条规则全部写在 `risk_rules.json`，字段为"触发方式 + 为什么是问题 + 怎么改 + 法律依据 + 置信度"。用户自己的行业红线可以直接加一条 JSON，不需要动 Python。

五类检测器刻意做得简单可解释（正则 / 数值阈值 / 要素缺失 / 双方不对称 / 有条件缺失），因为合同审查的价值在于"能对上原文"，而不是模型给个黑箱分数。

### 决策 3：法条只存"条号 + 要点 + 置信度"，不存长段原文

理由有两个：一是条文会随修正变化，存长文本容易过期；二是任何未经核对的"原文"都有误导风险。因此索引只给导航，需要原文时要求核对官方来源，`confidence=verify` 的条目在交付时必须提示复核。

### 决策 4：风险分级克制

只把"不改就可能直接损失钱、失去救济手段、或条款可能被认定无效"的问题列为高风险。措辞不严谨、标点、格式一律不计。宁可少报，不可滥报——滥报会让用户整体不信这份报告。

## 阶段三 · 内容生产（全部手写）

| 内容 | 规模 | 编写原则 |
|---|---|---|
| 条款库 | 6 类合同 / 72 条条款 | 参照行业通行做法与《民法典》合同编强制性规定自行组织表述；每条给编号（P01、S01、L01、W01、N01、D01）便于覆盖与增删；金额、比例、期限一律用占位符，避免硬编码 |
| 风险规则 | 31 条（高 14 / 中 14 / 低 3） | 每条必须能落到具体条款文本上；同一规则同一位置只报一次；对等表述（"另一方有权解除""双方承担保密义务"）不判为不对称 |
| 法条索引 | 4 部法律 / 44 条导航 / 10 个场景索引 | 只写有把握的条号；不确定的标 `verify`；给"适用场景"而不只是条号 |
| 工作流规格 | 5 条 | 每条写清输入参数、步骤、判断条件、输出、异常处理、依赖、与其他工作流关系 |
| 主提示词 | 1 份 | 只写判断规则与交付标准，不写空洞的角色形容词 |

合同的"鉴于条款"、双方主体区、签署页格式按中国大陆商务合同的通用体例组织，属于行业惯常表达，不来自任何特定模板产品。

## 阶段四 · 代码实现（2162 行 Python）

| 文件 | 行数 | 职责 |
|---|---|---|
| `cc_docx.py` | 414 | OOXML 写入器 + 结构校验 |
| `cc_review.py` | 366 | 切条、类型识别、五类检测器、打分、报告 |
| `cc.py` | 325 | 统一 CLI（draft/review/compare/ledger/laws/amount/doctor） |
| `cc_draft.py` | 293 | 默认值合并、派生字段计算、正文装配、产物落盘 |
| `cc_compare.py` | 281 | 对齐策略、相似度、数值比对、指向翻转、谈判清单 |
| `cc_common.py` | 277 | 文本读取（含 docx 解析）、切条、金额大写、IO |
| `cc_ledger.py` | 206 | 台账增删改查、日期推算、状态计算、报告 |

模块间关系：`cc.py` 是唯一入口，其余模块可被单独 import；`cc_common` 与 `cc_docx` 为底层，无反向依赖。

编码过程中实际处理的边界：Word 保存的 docx 段落结构差异、明细行以 `\n` 分隔、金额千分位与中文大写的对应、条款无条号时的降级切分、规则正则写错时的单条跳过、台账 JSON 损坏时不静默覆盖。

## 阶段五 · 测试（真实执行，记录见 TEST_REPORT.md）

按"先自检、再逐流验证、最后交叉验证"的顺序执行：

1. `doctor` 六项自检全通过。
2. 起草采购合同 → 15 条 / 89 段 / 1 表 / 8 部件，结构校验通过。
3. 用 pandoc 作为第三方 DOCX 阅读器解析生成文件，退出码 0，正文完整。
4. 把生成的 docx 回读做审查（信任链）→ 15 条正确切分，0 条误报，风险分 100。
5. 故意写坏的租赁合同 → 5 高 / 7 中 / 2 低，植入的 5 个高风险全部命中。
6. 四类合同的数值规则逐条探针（劳动 / 借款 / 租赁 / 采购）→ 期望规则全部命中。
7. 前后两版比对 → 7 处重大变更，含 1 处甲乙方指向翻转。
8. 台账导入 → 5 个节点，日期推算与临近提醒正确。

过程中修掉的问题：审查规则对全文类问题重复报（改为全文只跑一次）、评分过早归零（改为指数衰减）、比对把"6 个月"误读成"6 个"（补充单位优先级）、验收条款被误判为"甲乙方指向翻转"（收窄触发条件）、合同 1.1 条"数量为详见附件一"读起来不通（改模板措辞）。
