## 四、测试中发现并已修复的缺陷

| # | 问题 | 原因 | 处理 |
|---|---|---|---|
| 1 | 全文类风险（如"押金无退还约定"）在每个条款下重复报 | 按条款逐条跑全文规则 | 全文类规则改为全文只跑一次，并标注位置 |
| 2 | 风险分极易直接归零，无法区分"很差"与"极差" | 线性扣分封顶 | 改为按等级权重指数衰减 |
| 3 | 比对把"6 个月"读成"6 个"、"7 个工作日"漏识别 | 单位匹配优先级错误 | 调整单位顺序为最长优先，并支持"个" |
| 4 | 验收条款被误判为"甲乙方指向翻转" | 仅比对甲乙方词频 | 改为优先识别"所在地"翻转，词频翻转限定在解除/管辖/付款类条款 |
| 5 | 合同 1.1 条出现"数量为详见附件一"读不通 | 模板措辞与默认值冲突 | 改为"数量：{{qty}}"结构 |
| 6 | 服务合同到期日不自动推算；工时制出现"标准工时工时制度" | 派生字段缺分支、默认值措辞不当 | 增加"起始日 + 服务天数"分支；默认值改为"标准" |

## 五、未验证 / 无法验证的事项（未标记为通过）

| 事项 | 原因 | 建议 |
|---|---|---|
| 在 Microsoft Word / WPS 中人工打开检查版式 | 自动化环境禁止 COM 调用（安全策略拦截 `New-Object -ComObject`） | 上架前手动双击打开一份生成文件，确认字号、行距、缩进、表格框线、签署区两栏样式 |
| PDF / 扫描件解析 | 产品刻意不引入 PDF/OCR 依赖 | 已在文档中声明限制，不作为缺陷 |
| 多人并发写同一台账文件 | 单机单用户场景，未设计锁 | 单用户使用无影响；多人共享需改用版本管理 |
| 超长合同（> 200 条）性能 | 未构造该规模用例 | 首次遇到时补测 |
| 法条条号的现行有效性 | 索引中 8 条标注 `confidence=verify` | 需人工在官方数据库核对后转正 |
| 真实用户场景下的判断质量（如"这份合同该不该签"） | 属主观商业判断，无法自动化断言 | 依赖模型侧判断，规则只保证"风险不漏报明显模式" |

## 七、结论

- 五条工作流的核心链路可用，产物齐全且结构合法。
- 审查引擎在"故意写坏的合同"上识别率 100%（植入的 5 类高风险全部命中），在"自产合规合同"上误报 0 条，说明规则阈值设置合理。
- 异常路径处理明确，不静默失败，不伪造产物。
- 主要剩余风险不在代码，而在：真实 Word/WPS 版式未人工确认、部分法条条号待人工核对、规则库无法覆盖行业特殊监管。这三项已在 `RELEASE_RISK.md` 中列明。
