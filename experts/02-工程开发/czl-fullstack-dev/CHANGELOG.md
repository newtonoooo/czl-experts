## 1.0.3 — 2026-10-26

**改动原因：** 1.0.2 的「验收驱动」偏方法论，作为商品标题缺乏分量感。换成一个描述**能力上限**的形容词，而不是描述资历的（资深／首席／顶级属于虚构资质，不采用）。

**改动内容：**

| 字段/位置 | 1.0.2 | 1.0.3 |
|---|---|---|
| `profession.zh` | 验收驱动全栈开发工程师 | **生产级全栈开发工程师** |
| `profession.en` | Acceptance-Driven Full-Stack Development Engineer | Production-Grade Full-Stack Development Engineer |
| `version` | 1.0.2 | 1.0.3 |

**为什么"生产级"撑得住：** 它对应包内可核对的条件——编号条目有证据、三层验证、六项上线闸门、回滚命令实际执行过。这句话已写进 Agent 提示词与 README，把形容词变成清单，避免变成空喊。

**关键词未损：** 新头衔仍包含连续的 `全栈开发` 与 `开发工程师`，13 个候选搜索词命中情况与 1.0.2 一致。

**未改动：** 标识、花名「陆工」、全部技能、模板、示例、头像、授权条款。

**备选形容词（如再被判重名）：** 端到端全栈开发工程师 → 工程化全栈开发工程师 → 可交付全栈开发工程师。

## 1.0.0 — 2026-10-26

首个版本。独立开发，不含任何第三方技能或素材。

### 产品定位

面向"从想法到上线一个人全包"的开发者与小型团队。解决三个接缝问题：需求到代码、代码到验证、验证到上线。

核心机制：**编号验收条目（A1、A2…）贯穿全程**，代码只在其对应条目带证据通过后计为完成。

### 首次发布包含

| 模块 | 内容 |
|---|---|
| Agent 人设 | 六段主线（定桩 / 切片 / 实现 / 验证 / 上线 / 交接）、任务分流表、四要素验收条目、四行汇报格式、出错处理、边界承诺 |
| `czl-dev-spec` | 定桩四问、条目拆分规则、一页技术方案、闸门确认；含《验收条目写法》与两份模板 |
| `czl-dev-build` | 七项实现约定（目录、配置、错误、日志、查询、接口、前端）；含三份深入参考 |
| `czl-dev-gate` | 三层验证（单元/接口 → 集成 → 端到端）、上线六项闸门、回滚方案、交付说明模板 |
| 示例 | 一个虚构报价单功能的完整走法，覆盖六段与一次真实的问题定位 |
| 头像 | 几何构成风格，512×512 |

### 设计取舍（写下来供后续版本对照）

1. **验收条目上限 12 条。** 超过就说明需求没定清，应拆成两期，而不是把条目写得更细。
2. **探路片允许不销号。** 技术不确定性优先用半天验证掉，不占验收编号，但要给结论。
3. **回滚是硬闸门。** 没有可执行回滚的上线请求应被拒绝——包括对自己。
4. **不打包第三方技能。** 本版刻意只带自研方法，避免授权链与体积问题（平台单包上限 3MB）。
5. **不承诺结果。** 不写"保证通过审核""保证不出故障"，只承诺"没跑的写未验证"。

### 已知限制

- 三层验证中的 L3（端到端）依赖用户提供可运行环境；无环境时会标记为未验证，不会代填。
- 不内置浏览器自动化能力，需要点页面时由用户提供截图或录屏。
- 未包含多角色协作（单专家形态）。
