# 项目结构与配置

## 一、两种规模的目录做法

### 小规模（1—5 个功能，单人维护）

不要过度设计。一个入口、一个配置、按功能分文件即可。

```
src/
  index.ts
  config.ts
  orders.ts
  payments.ts
  db.ts
```

判据：文件数少于 15 个时，目录层级越少越好。这个阶段建 `services/`、`repositories/` 只是为了让目录看起来专业。

### 中规模（5—20 个功能）

```
src/
  orders/
    routes.ts service.ts repo.ts types.ts
  payments/
  shared/
    config.ts errors.ts logger.ts db.ts
  index.ts
```

`shared/` 只放跨功能使用的东西。放进 `shared/` 的门槛：**至少两个功能在用**。只有一个功能用的工具，就放在那个功能目录里。

### 什么信号说明该拆了

- 某个文件超过 400 行且职责不止一件
- 两个功能互相 import 对方的内部文件
- 改 A 功能必须重新测 B 功能

前两条出现时就拆；第三条出现时先看看是不是共享状态太多。

## 二、配置层怎么写

### 唯一入口

```ts
// shared/config.ts
function need(name: string): string {
  const raw = process.env[name];
  if (!raw) throw new Error(`缺少必需配置项：${name}（参考 .env.example）`);
  return raw;
}

function optionalNumber(name: string, fallback: number): number {
  const v = process.env[name];
  if (v === undefined || v === '') return fallback;
  const n = Number(v);
  if (Number.isNaN(n)) throw new Error(`配置项 ${name} 不是合法数字：${v}`);
  return n;
}

export const config = {
  env: process.env.NODE_ENV ?? 'development',
  port: optionalNumber('PORT', 3000),
  dbUrl: required('DATABASE_URL'),
  jwtSecret: required('JWT_SECRET'),
  upstream: {
    baseUrl: required('UPSTREAM_BASE_URL'),
    timeoutMs: optionalNumber('UPSTREAM_TIMEOUT_MS', 5000),
  },
};
```

三个要点：

1. **缺项在启动时炸，不要在第一个请求时炸。** 启动时炸，你知道原因；请求时炸，用户先知道。
2. **数字类型当场转换校验。** `Number('abc')` 是 NaN，不校验就会在业务里莫名其妙地算错。
3. **嵌套分组，不要一长串平铺。** `config.upstream.timeoutMs` 比 `config.upstreamTimeoutMs` 好读。

### 多环境

- 用同一份代码 + 不同环境变量，不要写三份配置文件
- 环境差异只允许出现在变量里；如果某个环境的逻辑要分叉（例如支付用真实网关还是沙箱），在配置里显式写 `paymentMode: 'sandbox' | 'live'`，不要靠 `NODE_ENV` 隐式推断
- `.env.example` 提交进版本库，`.env` 绝不提交

### 密钥

| 做法 | 评价 |
|---|---|
| 写在代码里 | 不可接受，泄露即失守 |
| 写在 `.env` 但入库 | 不可接受，删了历史记录也没用 |
| `.env` 本地 + 部署平台注入 | 可接受 |
| 密钥管理服务（KMS / Secrets Manager） | 推荐，尤其多人协作时 |

发现已泄露的密钥：**先轮换，再清理。** 顺序反了等于白干。

## 三、启动自检

服务启动时做一次自检，比事后排查便宜得多。

```ts
async function preflight() {
  const checks: Array<[string, () => Promise<void>]> = [
    ['数据库连通', async () => { await db.query('SELECT 1'); }],
    ['迁移是否最新', async () => { await assertMigrationsApplied(); }],
    ['必需配置齐全', async () => { void config; }],
    ['上传目录可写', async () => { await fs.access(config.uploadDir, fs.constants.W_OK); }],
  ];
  for (const [name, fn] of checks) {
    try { await fn(); }
    catch (e) { throw new Error(`启动自检失败：${name} — ${(e as Error).message}`); }
  }
}
```

要不要自检的判断：**这项如果不满足，服务是不是一定不正常？** 是，就加；不确定，就别加，免得自检本身成为故障源。

## 四、构建产物与部署一致性

一条容易被忽略的纪律：**线上跑的代码必须能由当前源码构建出来。**

- 交付/部署前，从干净目录构建一次，产物上传
- 不要把本地 `dist/` 或 `node_modules` 打包分发
- 锁文件必须提交（`package-lock.json` / `pnpm-lock.yaml` / `poetry.lock` / `go.sum`）
- 依赖版本有漂移风险时，固定到具体版本而不是 `^`

判断：把仓库给另一个人，他构建出的产物行为应该和你一致。不一致就是环境没锁住。
