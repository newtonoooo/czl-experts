# 定桩：把话说死，再动手

定桩这一步只解决一个问题：**这段话到底要验收什么。**

不解决"能不能实现得漂亮"。那是后面的事。这一步结束时，你手上应该有一张表，表里每一条都能被人指着说"过了"或"没过"。

---

## 何时触发

- 需求里出现"友好""流畅""合理""差不多就行"这类词
- 同一个需求里有两个互相打架的要求
- 用户只说"做个类似 XX 的东西"
- 功能涉及钱、权限、数据删除、对外通知——出错代价高的
- 用户已经说清楚，但没说"什么情况下算失败"

最后一条最容易漏：只写正常流程，不写反例，等于只验了一半。

---

## 四步

### 第一步：问四个问题（只问这四个）

| 问题 | 为什么必须问 | 答不上来时的处理 |
|---|---|---|
| 谁用 | 决定权限模型和界面复杂度 | 按"内部少数人使用"假设，并标注 |
| 在什么场景用 | 决定性能要求和部署形态 | 按"低频、单机"假设，并标注 |
| 做完能看到什么 | 决定验收条目长什么样 | 让用户描述"你会怎么判断它成了" |
| 什么情况下不能这么做 | 决定反例与安全边界 | 主动列出三条典型误用场景供确认 |

问不到就假设，假设要写在条目表开头的"前提"里。**不要用反复追问代替判断**——用户常常也说不清，说清了就不会来找你。

### 第二步：拆条目

按 `references/验收条目写法.md` 的规则拆。几个实操要点：

- 先写**主链路**（用户从进入到拿到结果），一段一段拆
- 再写**反例**（错误输入、越权访问、重复提交、中途退出）
- 最后写**边界**（空数据、超大数据、第一条与最后一条）
- 每条给编号 A1、A2……；编号一旦给出就不要复用，删掉的条目保留编号并划掉

数量控制：**5—12 条**。少于 5 条通常漏了反例；多于 12 条说明该拆成两个功能。

### 第三步：一页技术方案

用 `templates/一页技术方案.md`，必须能在一屏内看完：

- 技术选型：一句话 + 为什么（不比较三个框架的优劣，选一个能交的）
- 数据：存哪、表结构要点、迁移怎么走
- 接口：有哪几个，各自的输入输出
- 风险点：**最不确定的一件事**，写清"如果它不通，改走什么"
- 第一片做什么：通常是那个风险点，不是最简单的那个

### 第四步：闸门

把条目表和技术方案一起交给用户，明确问一句：

> 这 8 条按现在的写法验收，你认可吗？第 5 条我按"允许重复提交但只生效一次"理解，如果你的意思是"直接拦截第二次"，我改条目。

**认可后才进入开发。** 用户没回，就停在这里——不要用"我先做起来"代替确认，返工的成本由你承担，不由用户承担。

## 判断条件汇总

| 情形 | 判断 | 动作 |
|---|---|---|
| 条目里有形容词 | 不可验收 | 改写成可观察的动作或数值 |
| 一条里含"并且/同时"两个结果 | 该拆 | 拆成两条 |
| 条目数 < 5 | 大概率漏反例 | 补越权、重复提交、空数据三类 |
| 条目数 > 12 | 需求过大 | 建议拆成一期、二期，一期先交付主链路 |
| 技术风险点无法定位 | 方案没想清 | 先做一个 30 分钟的技术验证，再回到定桩 |
| 用户要求"先做出来再说" | 接受，但降级 | 只写主链路条目，反例条目列为"二期"，在交付说明里注明未验范围 |

---

## 输出格式

```
前提（假设）：<三条以内，每条一行>

验收条目
A1 <一句话标题>
   操作：<用户/系统做了什么>
   预期：<可观察的结果>
   反例：<至少一个>
   证据：<怎么留证>

一页方案
选型 / 数据 / 接口 / 风险 / 第一片

闸门问题：<一句具体的确认问题>
```

---

## 异常处理

- **用户说不清"做完能看到什么"**：给他三个具体画面选，不要让他凭空描述。
- **用户嫌条目太多**：把"必须验"和"可以后补"分开标，条目不减——减掉的是验的范围，不是记录。
- **用户中途改需求**：不直接改代码。先改条目表，标出哪几条作废、哪几条新增，再继续。
- **两条需求冲突**：不当场裁决，把冲突写成一行摆出来，让用户选。技术侧只给"各自代价"。

## 与其他技能的关系

- 定桩完成 → `czl-dev-build`（实现约定）
- 实现完成 → `czl-dev-gate`（验证与上线）
- 定桩阶段发现"这功能其实不该做" → 直接说，不做技术包装
