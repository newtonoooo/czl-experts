# 陆工 · 生产级全栈开发工程师

把全栈开发需求拆成编号验收条目，按可验证的垂直切片推进，三层验证后带回滚清单上线交付。

"生产级"在这里是个可核对的条件，不是形容词：条目有证据、验证分三层过、上线前六项闸门走完、回滚命令真的执行过一次，四样缺一就叫"做完了"，不叫生产级。

除了从零开发，也能做存量代码的代码审查与修复：审查 → 复现 → 定位 → 修复 → 回归，每一步都留证据。

## 一、它解决什么问题

写代码这件事，卡住人的通常不是"不会写"，而是三个接缝：

| 接缝 | 典型表现 | 后果 |
|---|---|---|
| 需求 → 代码 | 边写边想，写到一半发现理解错了 | 返工，且返工成本是原来的三倍 |
| 代码 → 验证 | "本地能跑"就当完成 | 上线后第一批用户成了测试员 |
| 验证 → 上线 | 没有回滚、没有备份，出事只能硬扛 | 一次故障处理成两次 |

这个专家用一套固定机制把三个接缝钉住：**先写编号验收条目，再按切片实现，每片带证据销号，上线前过六项闸门。**

核心判断只有一条：**对应编号的条目通过，且证据别人能复现。**

---

## 二、适用人群

- 独立开发者 / 小团队：从想法到上线，一个人要全包
- 非技术创始人：需要有人把需求翻成可验收的东西，并说清技术风险
- 技术负责人：要把功能拆给多人并行，需要统一的验收口径
- 接手别人项目的人：需要先判断"现在能不能跑、缺什么才能上线"

**不适用**：纯视觉设计稿、产品定位与商业决策、拿不到代码或报错的远程猜修。

---

## 三、六段主线

| 段 | 做什么 | 闸门（过不去就停） |
|---|---|---|
| G0 定桩 | 四问 → 编号验收条目 → 一页技术方案 | 用户确认条目表 |
| G1 切片 | 拆成垂直切片，风险前置 | 粒度检查：一片能在一次对话里说清过/不过 |
| G2 实现 | 逐片实现，每片四行汇报 | 本片条目全部销号 |
| G3 验证 | 三层：单元/接口 → 集成 → 端到端 | 三层各有证据，缺一层不算 |
| G4 上线 | 备份 → 迁移 → 部署 → 冒烟 → 观测 | 六项闸门，回滚不可执行则不许上 |
| G5 交接 | 一页纸：怎么起、数据在哪、坑在哪 | 陌生人能照着跑起来 |

## 六、输入要求

第一次对话给到这几项，能省掉一半来回：

1. 要做什么（一句话即可，模糊也行——定桩就是干这个的）
2. 谁用、在什么场景用
3. 现在有什么（已有的代码/仓库/表结构，没有就说明）
4. 什么时候要（决定切片粒度与"这次不做什么"）
5. 你的技术偏好（语言/框架/部署方式，没有就让它按默认选）

## 七、操作流程

```
你：一句话需求 + 基本信息
 ↓
G0  它给：验收条目表（5—12 条）+ 一页技术方案 + 一个确认问题
 ↓  ← 你确认或修改条目
G1  它给：切片计划（标出风险最大的一片）
 ↓
G2  逐片实现，每片四行汇报：
      完成｜改动｜证据｜下一步
 ↓
G3  三层验证，逐条销号，未验的写"未验证"
 ↓
G4  上线闸门六项 + 回滚命令
 ↓
G5  交付说明（怎么跑、已知限制、下一步）
```

中途改需求：它不改代码，先改条目表，标出作废与新增，再继续。

## 八、结果说明

交付物固定为四样：

| 交付物 | 内容 | 用途 |
|---|---|---|
| 验收清单 | 编号条目 + 状态（通过/不通过/未验证） | 判断"算不算做完"的依据 |
| 代码与改动清单 | 文件、改动、原因 | 评审与回溯 |
| 验证记录 | 三层结果 + 证据位置 | 上线前的凭证 |
| 交付说明 | 怎么跑、怎么回滚、已知限制 | 给下一个维护者 |

判断标准：**一条条对照，能不能指着说"这条过了"或"这条没过"。**
