# 分包与体积预算

## 一、上限口径（先记住这两条）

- **单个包（主包或任一分包）不超过 2MB**
- **所有分包合计不超过 20MB**

> 具体数值与计费方式以微信官方「分包加载」文档为准，历史上有过调整，动手前建议在文档页确认当前值。工具里用的是上面这两个数，若官方已变，改 `wx_doctor.py` 顶部的 `MAIN_LIMIT` / `TOTAL_LIMIT` 两个常量即可。

## 二、为什么要先算再写

体积超限的代价不在"传不上去"这一刻，在于**返工方式极其难看**：页面已经互相引用，这时再切分包要动路由、动相对路径、动组件引用，改一处崩三处。所以顺序永远是：**先估 → 再写 → 写完核**。

## 三、预算表怎么填

| 包 | 内容 | 预算 | 实测 | 余量 |
|---|---|---|---|---|
| 主包 | tabBar 页 + app 三件套 + 首屏组件 | ≤ 1.7MB（留 15%） | `budget` 输出 | |
| 分包 goods | 商品详情、搜索 | ≤ 1.5MB | | |
| 分包 user | 订单、售后、地址 | ≤ 1.2MB | | |
| 图片总量 | — | ≤ 主包预算 40% | | |

**85% 红线**：主包超过上限的 85% 就要再切一次。理由很实际——下一步随便加一个页面就会破线，那时候你在赶上线，没有余量做结构调整。

## 四、什么东西最吃体积（按经验排序）

1. **未压缩的图片**：一张 1080p 的 banner 轻松 800KB。包内只留图标和首屏小图，其余走 CDN。
2. **字体文件**：中文字体动辄几 MB，要么裁剪子集，要么用系统字体。
3. **第三方 UI 库全量引入**：只用 3 个组件却引入整个库。
4. **`node_modules` 未排除**：`packOptions.ignore` 没配。
5. **源文件混入**：设计稿 `.psd/.sketch`、备份目录、`.md` 文档。
6. **未按需注入组件**：`lazyCodeLoading` 没开。

## 五、分包策略三种

| 策略 | 适用 | 注意 |
|---|---|---|
| 普通分包 | 大多数场景 | 依赖主包，主包加载完才能用 |
| 独立分包 | 低频完整功能、扫码直达页 | 不能依赖主包组件；包内要有自己的公共代码 |
| 分包预下载 | 高频但非首屏 | 消耗流量，别给所有分包配 |

## 六、切分顺序建议

```
第 1 刀：把非 tabBar 页面全部移出主包
第 2 刀：按业务域切（商品 / 订单 / 用户 / 内容）
第 3 刀：把某个域里最重的独立功能做成独立分包
第 4 刀：图片与字体搬家（CDN / 云存储）
```

大多数项目切到第 2 刀就够；切到第 4 刀还没下来，说明资源管理有问题，不是切分问题。

## 七、核算口径要说清

工具算的是**磁盘字节累加**，开发者工具上传时会做压缩与 tree-shaking，两者会差 10%-30%。所以：

- 早期用工具看**方向**（哪个包重、哪个文件大）
- 上线前用开发者工具「代码依赖分析」看**真实上传体积**
- 两个数都记进 `docs/预算表.md`，差异大时以工具（开发者工具）为准

## 八、常见误判

| 误判 | 真相 |
|---|---|
| "分包了就不会超" | 单个分包也有 2MB 上限，切完还要看每个包 |
| "图片放 CDN 就没体积问题" | 首屏仍需占位图；且 CDN 域名要配白名单 |
| "代码压缩能救" | 压缩救不了 800KB 的图 |
| "先上线再优化" | 超限直接传不上去，没有"先上线"这个选项 |
