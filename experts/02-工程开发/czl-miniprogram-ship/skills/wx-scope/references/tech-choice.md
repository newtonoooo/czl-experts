# 选型口径：技术栈与后端

选型不是比谁先进，是比**谁在这个项目上返工最少**。以下判断只看四个变量：团队人手、是否要上多端、是否强依赖微信原生能力、后期谁来维护。

## 一、前端框架三选一

| 维度 | 原生（推荐默认） | uni-app | Taro |
|---|---|---|---|
| 上手门槛 | 会 JS 就能干 | 需要懂 Vue 语法 | 需要懂 React 语法 |
| 微信原生能力 | 全部可用，无需中间层 | 大部分可用，个别能力需条件编译 | 大部分可用，个别能力需条件编译 |
| 包体积 | 最小，没有框架运行时 | 有运行时开销，分包策略要额外设计 | 同左，视版本而定 |
| 多端能力 | 只能微信 | 可发 H5/App/其它小程序 | 同左 |
| 排错难度 | 报错即代码 | 报错可能在框架层，要会看编译产物 | 同左 |
| 审核风险 | 最低（就是原生工程） | 低，但产物结构需说明 | 低 |

**判定规则：**

- 只发微信、团队 ≤ 3 人、强依赖支付/订阅消息/小程序码这类原生能力 → **原生**。理由：少一层编译，包体最小，出问题一眼看到底。
- 已有 Vue 团队、明确要同步发 H5 或 App → **uni-app**。
- 已有 React 团队、同上 → **Taro**。

> ⚠️ 一旦选了跨端框架，**体积预算要在框架产物上算**，不能按源码估。先跑一次真机上传，拿到实际包体再定分包。

## 二、后端三选一

| 维度 | 云开发（推荐默认） | 自建服务端 | 第三方 BaaS |
|---|---|---|---|
| 起步速度 | 最快，无需服务器与备案 | 慢，要域名+备案+证书+部署 | 快，但受平台能力限制 |
| 成本结构 | 按量，前期极低 | 固定服务器成本 | 按量或套餐 |
| 支付回调 | 云函数可直接承接 | 需公网可访问的 https 回调 | 看平台支持 |
| 数据可控性 | 数据在云开发环境内 | 完全自控 | 受第三方约束 |
| 迁移成本 | 中（数据库与云函数要重写） | 低 | 高 |
| 适合规模 | 中小体量、快速验证 | 有合规/私有化要求、体量大 | 无运维人手的小团队 |

**判定规则：**

- 从零起步、无运维、要快速上线 → **云开发**。
- 有等保/私有化/数据出境等合规要求，或已有后端团队 → **自建**。
- 明确不想管服务器但云开发不满足（如需复杂事务、外部系统对接） → 第三方 BaaS，并把"迁移出口"写进方案。

## 三、必须一起定下来的三件事

选型只定框架是不够的，下面三件不定，后面一定返工：

1. **登录态在哪**：服务端签发 token / 云开发用 openid 直接鉴权。定不下来就别写业务代码。
2. **图片放哪**：包内 / CDN / 云存储。这一条直接决定体积预算能不能过。
3. **环境怎么分**：测试与正式各一套 AppID 或至少各一套后端环境。混用是上线事故的常见根因。

## 四、选型结论怎么写（一句话模板）

> 前端用原生，因为只发微信且强依赖支付与订阅消息，少一层编译包体更可控；后端用云开发，因为无运维人手且首版要两周内上线；图片走云存储 + CDN，包内只留图标。

不要写"原生生态好、uni-app 跨端强"这种谁都能说的话，用户要的是**在他这个项目上为什么这么选**。
