# 立项收口（W0）

## 什么时候用

- 用户只有一句想法："我想做个社区团购的小程序"
- 需求含糊到没法验收："做得好看点、流畅点"
- 要判断技术栈：原生 / uni-app / Taro，云开发 / 自建后端
- 要判断能不能做：类目、资质、平台红线

## 输入

| 输入 | 必需 | 说明 |
|---|---|---|
| 需求描述 | 是 | 一句话也算，越糙越好，收口是我的活 |
| 目标用户 | 否 | 没有就按品类推断，并写明假设 |
| 现有代码 | 否 | 有就先扫一遍再谈条目 |
| 类目/资质状态 | 否 | 敏感类目必问 |

## 步骤

1. **补齐四要素**：品类与核心功能、目标用户、后端方案、当前阶段。缺哪个问哪个，一次最多四问，问完就动手，不无限追问。

2. **写条目**。每条必须过"第三人测试"：另一个人照这条描述操作，能判出真假。写不出验证动作的，退回重写需求本身。

   | 反面 | 正面 |
   |---|---|
   | 首页要好看 | 首页首屏在 iPhone SE 宽度下不出现横向滚动，分类区一屏可见 6 个 |
   | 登录要做好 | 未登录可浏览商品；点"下单"才触发手机号授权，拒绝后可继续浏览 |
   | 性能要快 | 商品列表 20 条首屏渲染完成，不出现超过 300ms 的空白（真机中端机） |

3. **定技术栈**（见 `references/tech-choice.md`）。给一句理由，不给长篇对比。

4. **扫红线**：支付、手机号、位置、UGC、直播、医疗/教育/金融/食品类目 → 直接写进台账第 1 段的资质状态，缺资质先标红。

5. **落文件**：
   - `docs/一页方案.md`（模板：`templates/one-page-plan.md`）
   - `docs/acceptance.json`（用 `scripts/ledger.py init` 建）
   - `docs/交付台账.md` 骨架（五段结构，见主 Agent 第三节）

## 判断条件

| 情况 | 动作 |
|---|---|
| 条目含"美观/流畅/体验好/完善" | 打回，改成可观察动作 |
| 条目数 > 25 | 砍到首版，其余进"后续版本"清单 |
| 命中敏感类目 | 先要资质结论，再排开发顺序 |
| 需求涉及诱导分享/强制关注/刷量 | 直接拒绝，给合规替代方案 |
| 用户要求"先做出来再说" | 至少给出条目表与预算再开工，不裸奔 |

## 输出

1. 一页方案（含**不做什么**清单，这条比做什么更重要）
2. 编号条目表（ID / 需求 / 验证动作 / 文件 / 状态）
3. 技术栈与后端定档理由（各一句）
4. 红线与资质状态
5. 显式假设清单（📌 开头）

## 异常处理

| 异常 | 处理 |
|---|---|
| 需求完全空白 | 四问后仍不清 → 按默认假设（工具类、原生、云开发、从零）开工，方案开头列出假设 |
| 用户拒绝写验证动作 | 说明后果：没有验证动作的条目在交付时无法判定完成，也过不了我的体检闸门 |
| 类目说不清 | 给"最可能的两三个类目 + 各自资质要求"，标注以公众平台后台为准 |
| 需求本身违规 | 停，说清触发的是哪条平台规则，给合规替代 |

## 依赖

- `scripts/ledger.py`（条目台账，纯标准库）
- `references/acceptance-rules.md`（条目写法细则）
- `references/tech-choice.md`（选型口径）
- `templates/one-page-plan.md`（一页方案模板）

## 与其它工作流的关系

- 上游：无（这是入口）
- 下游：**W1 骨架与预算**直接消费条目表；条目表是 W2/W5 的唯一进度源
- 被消费：W6 驳回整改时，新问题要作为新条目插回表里，不口头记

## 自检

- [ ] 每条都有验证动作，且不含"好看/流畅/完善"
- [ ] 条目数在 25 以内，超出部分进了后续清单
- [ ] 技术栈给了理由，不是"都可以"
- [ ] 敏感类目资质状态写进了台账
- [ ] 假设显式列出，没有藏在正文里
