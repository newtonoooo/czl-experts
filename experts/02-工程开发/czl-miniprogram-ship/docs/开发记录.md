## 一、开发方式

从零独立开发。**没有**基于任何现有专家包做改名、删版权声明或改作者字段。

参照对象是一份公开的微信小程序开发专家包（下称"参照包"），仅用于**功能分析**——看它覆盖了哪些任务、缺什么，不作为代码与文案来源。参照包的文本、提示词、工作流定义、头像均未被复制或改写使用。

## 二、功能分析阶段

先读了参照包的全部 9 个文件（主 Agent + 8 份参考），记录其能力边界，然后做了三件事：

1. **提取它的通用流程骨架**：需求收口 → 项目结构 → 页面组件 → 能力接入 → 云开发 → 性能 → 审核 → 排查。这是行业通用的问题分解方式，不属于任何人专有。
2. **找它的短板**（这是新产品定位的依据）：
   - 全部是文档，**没有一个可执行脚本**。"包超 2MB 就分包"这类话写了，但没有任何工具能算出你的包现在多大。
   - 检查项靠模型记忆执行，无法复现：同一个工程问两次可能给不同结论。
   - 进度靠对话上下文，跨会话必丢。
   - 部分表述（如基础库 3.x 适配）停留在"需以官方文档核实"，但没给出核实方法。
3. **决定差异化方向**：不做一个"文档更多"的专家，做一个**闸门可执行**的专家。

## 三、设计决策

### 决策 1：用脚本承担"能判真假"的部分

凡是能由文件内容判定的事（页面有没有 `.wxml`、主包多大、隐私接口有没有声明、密钥有没有明文），一律写成代码，不交给模型记忆。

结果：4 个子命令、24 项检查、7 个预算判定。

### 决策 2：给每个结论标注"可判定 / 需人工"

静态扫描有盲区。与其假装全知，不如在 `checks-catalog.md` 里逐条写清每个检查的漏报与误报场景，并在报告末尾固定一句"真机与视觉仍需人工核实"。

**这条决定了整个产品的可信度**：用户不会因为它漏报一次就不再信任，但会因为一次"应该没事"而彻底不信。

### 决策 3：把进度做成机器可读

`acceptance.json` + `ledger.py`。核心设计是**状态闸门**：条目没绑文件，不许标"已完成"。这不是为难用户，是因为"没绑文件的完成"在交接时等于零。

第一版实现后专门测了这条：`set --status accepted` 在未绑文件时退出码 2，符合预期。

### 决策 4：不写具体版本号与限额的绝对值

包内涉及基础库版本、平台上限、类目要求的地方，一律写"以官方文档为准"并给查询路径。原因：这些数字会变，写死就是在埋雷。唯一写死的两个常量（2MB / 20MB）放在脚本顶部，注释里写明"若官方已变，改这两个常量即可"。

### 决策 5：七道工作流而不是一个流程

参照包是一个大流程。这里拆成 W0-W6，每个都给"判断条件 + 异常处理 + 上下游"。拆的依据是**返工成本**：W0 改需求便宜，W5 改分包贵十倍。所以闸门要早设。

## 六、"图标变文字"问题定位

用户反馈：专家导入到新的 WorkBuddy 后，选中它时小图标不显示，变成了一个字。

**排查过程**：

1. 确认 UI 逻辑：前端存在 `expertAvatarImage` 与 `expertAvatarInitial` 两个样式类，说明图标区是"图片加载失败 → 显示名称首字"的降级结构。所以症状 = 图片加载失败。
2. 查参照包的头像文件：`avatars/expert.png` 的文件头是 `FF D8 FF E0 4A 46 49 46`（JPEG/JFIF），**不是 PNG 的 `89 50 4E 47`**。即：文件内容是 JPEG，扩展名是 `.png`。
3. 扫了本机全部 50 个专家包的头像，发现 2 个扩展名与实际格式不符（参照包是 JPEG 冒充 PNG，另一个是 PNG 存成 `.jpg`）。
4. 另一方面，用户自己此前打的包里 `.gitkeep` 与头像都在，路径也正确，说明**路径与打包结构不是主因**，格式错配才是这次的具体原因。

**结论（按可能性排序）**：

1. **扩展名与真实格式不符**（本次已确认存在）。部分加载链路按扩展名决定解码方式，错配会导致解码失败，直接降级成首字。
2. **头像文件未被打进 zip**（打包时根目录层级不对，或漏掉 `avatars/`）。
3. **头像超过平台建议的体积**（建议 512×512、≤500KB）。
4. `plugin.json` 里 `avatar` 路径与实际文件名大小写不一致（Windows 不敏感、其它环境敏感）。

**本包的规避措施**：真实 PNG（`89 50 4E 47`）、512×512、312.9KB、路径 `avatars/expert.png` 与清单完全一致、打包时验证 zip 内含该文件（见测试报告 T-20 与打包输出）。

## 七、遇到的坑

| 坑 | 处理 |
|---|---|
| 图像模型产出带右下角水印 | 自写 PNG 解码/编码器，用左/上边缘二维插值填充水印区，再 2×2 箱式降采样（512 下接缝不可见） |
| 首版头像 PNG 485KB，压不下来 | 原因是写 PNG 时全部用 filter 0；改为逐行在 5 种过滤器中选绝对值和最小的一个，降到 313KB |
| `app_secret` 检测不触发 | 正则 `app\s*secret` 不匹配下划线，改为 `app[\s_-]*secret`，复测通过 |
| Windows 下中文路径 | 全部走 `os.path`；命令行加引号；文件读写显式 `encoding='utf-8'` |
| 报告写到哪里 | 默认写工程内 `docs/体检/`，`--out` 可改；写失败只警告不中断（控制台输出仍完整） |

## 八、自评

**做得好**：闸门可执行、结论可复现、盲区明说。这三点让产品在"看起来差不多"的一堆小程序助手里有实质差别。

**不足**：
- 未在微信开发者工具与真机验证骨架（测试报告已列为未验证）。
- 静态扫描的漏报面（动态调用、混淆密钥）没法根治，只能标注。
- 单日完成，参考文档深度不均：`wx-capability` 与 `wx-doctor` 较厚，`wx-skeleton` 相对薄。

**下一版优先级**：先补 `check --code` 逐条复检（驳回整改真实痛点），再补云函数与前端调用名一致性检查。
