# 示例走法：一次完整交付长什么样

这是一个真实跑通的例子（工程见测试样例）。看一遍，就知道这个专家的节奏。

---

## 起点：一句需求

> "我想做个给小区邻居拼团买菜的小程序，两个月内上线，我自己一个人写。"

## W0：收口

**它先问四件事**（不超过四问）：

1. 邻居是自提还是配送？
2. 要不要在线支付，还是群里转账？
3. 有没有营业执照（决定能不能开电商类目）？
4. 你自己写过小程序吗？

假设回答：自提、要在线支付、有、写过 demo。

**它给的条目（节选）：**

| ID | 需求 | 验收动作 |
|---|---|---|
| A-01 | 首页展示在售团购 | 打开首页 → 看到不少于 3 个在售团，每个有标题/价格/剩余时间 |
| A-02 | 点团进详情 | 点任一团 → 详情页显示商品明细与自提点，返回后首页滚动位置不变 |
| A-03 | 下单并支付 | 选数量 → 提交 → 唤起支付 → 支付成功后订单状态为"待自提" |
| A-04 | 我的订单 | 未登录时提示登录；登录后只看到自己的订单 |
| A-05 | 主包体积可控 | 主包 ≤ 1.7MB（实测，非估算） |

**它同时给出的"不做什么"**：

- 不做配送路线
- 不做退款自动审批（首版人工处理）
- 不做拼团分享裂变（首版只做自然分享）
- 不做多自提点切换

**技术定档一句话**：

> 前端原生（只发微信、强依赖支付），后端云开发（一人开发、无运维），图片走云存储（包内只留图标）。

**红线提醒**：

> 电商类目需要营业执照；支付需要商户号。两个都没有的话，A-03 可以先写代码但走不通，建议先办。

## W1：骨架与预算

它写了一个 `spec.json`，生成骨架：

```
生成: pages/index/index.js / .json / .wxml / .wxss
生成: pages/cart/cart.*      （tabBar）
生成: pages/mine/mine.*       （tabBar）
生成: packages/goods/detail/detail.*
生成: packages/goods/search/search.*
生成: app.json / app.js / app.wxss / sitemap.json / project.config.json
```

生成的页面不是空壳，打开就有三态：

```xml
<view wx:if="{{status === 'loading'}}" class="state">加载中…</view>
<view wx:elif="{{status === 'empty'}}" class="state">还没有内容 <button size="mini" bindtap="onRetry">刷新试试</button></view>
<view wx:elif="{{status === 'error'}}" class="state">{{errorMsg}} <button size="mini" bindtap="onRetry">重试</button></view>
```

然后跑预算：

```
=== 体积预算 ===
结论: P0=0  P1=0  P2=0
```

主包只有骨架，很轻。这时候它说了一句关键的话：

> 现在主包 200KB，看着很宽裕。但详情页的轮播图如果用未压缩的原图，一张就能吃掉 800KB。所以图片处理规则现在就要定：包内只放 ≤ 50KB 的占位图，大图走云存储。

## W2：一条一条写

写完 A-01，它做两件事：

```bash
python ledger.py set docs/acceptance.json --id A-01 --status done
python wx_doctor.py scan ./miniprogram
```

第一次跑 `set` 时用户没绑文件，被拒了：

```
错误: A-01 要进"已完成(待验)"，必须先绑对应文件（--files）。没绑文件的状态没有意义。
```

补上 `--files pages/index/index.js` 才通过。这个小摩擦是设计出来的——**没绑文件的"完成"是假的**。

## W3：支付

它先过四道闸门，然后给链路：

```
前端：createOrder → getPayParams → wx.requestPayment → queryOrder
服务端：下单（价格从库里取）→ 统一下单 → 签名 → 返回
             ↑
        支付回调（验签 → 幂等 → 校验金额 → 发货）
```

它强调的那句话：

> 前端 `success` 只用来跳转订单页。真实状态永远回服务端查。不然用户断网重连时你会漏单。

## W5：提审预检（真实输出）

在样例工程上跑出来的报告长这样（这是实际输出，不是示意）：

```
=== 提审预检 ===
结论: P0=3  P1=4  P2=2
  [P0] SCAN-002  页面四件套缺失
        pages/detail/detail 缺 .wxml
  [P0] SCAN-040  隐私接口被调用但未在 app.json 声明
        getLocation（出现在 pages/index/index.js）
  [P0] SCAN-050  前端出现疑似密钥明文
        app.js: AppSecret 疑似明文
  [P1] SCAN-012  tabBar 图标文件不存在
        iconPath -> assets/icons/mine.png
  [P1] SCAN-041  用了定位但没有权限用途说明
  [P1] SCAN-061  存在 http 明文域名
  [P2] SCAN-042  采集类接口清单（需在隐私保护指引中说明）
  [P2] SCAN-060  需要配置服务器域名白名单
存在 3 个阻断项，不可提审。
```

注意它说的是"**不可提审**"，不是"建议优化"。

报告还附了一份材料清单（7 项，可勾选）和两张表：采集接口清单（填隐私指引用）、外部域名清单（配白名单用）。

## W6：被拒之后

假设驳回原文是：

> 你的小程序存在收集用户信息未说明用途的情况，请补充说明后重新提交。

它的处理：

| 拆句 | 定位 | 整改 |
|---|---|---|
| 收集了什么 | `preflight` 拉出 `getLocation`、`chooseImage` | 两条都写进隐私指引 |
| 没说用途 | `permission.desc` 为空 | 改成"用于显示距离你最近的自提点" |
| 没声明 | `requiredPrivateInfos` 缺 `getLocation` | 补声明 |
| 授权时机 | `onLoad` 里就调了定位 | 改到用户点"选自提点"时再调 |

最后给一段复审说明，让审核员能直接按步骤验：

> 1. 进入首页不弹任何授权；2. 点"选择自提点"才请求位置；3. 拒绝后仍可手动选择自提点，功能不阻断。

## 这个走法里，哪些是工具干的，哪些是人干的

| 环节 | 谁干 |
|---|---|
| 列条目、判真假、定范围 | 专家（人判断） |
| 生成骨架、算体积、查四件套、查隐私声明、查密钥 | 脚本（可复现） |
| 写页面与云函数 | 专家（代码） |
| 真机测试、视觉检查、类目选定 | **你**（工具覆盖不到，明确标注） |

最后这条很重要：**没有任何工具能替你在真机上点一遍。** 这个专家会把这句话写在每份报告的末尾，而不是假装全都能自动验。
