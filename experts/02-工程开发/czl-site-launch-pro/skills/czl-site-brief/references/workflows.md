# 工作流总表（W1–W8）

八个工作流，每个都写清九件事：名称、职责、输入、步骤、判断、输出、异常、依赖、关系。
W1–W3 由 `czl-site-brief` 执行，W4–W6 由 `czl-site-build` 执行，W7–W8 由 `czl-site-ship` 执行。

入口分流（不属于任何单一工作流，由主提示词的分流表完成）：先判断用户这句话属于哪一类，
再决定从 W1 还是从 W4/W5/W7 进。**分流错了，后面所有步骤都是白做。**

---

## W1 · 立项目标锁定

| 项 | 内容 |
|---|---|
| **职责** | 把一句口头需求变成一页可确认的立项单，同时划出"本期不做"的范围 |
| **输入** | 用户的自然语言描述；可选：竞品链接、已有素材、品牌资料 |
| **步骤** | 1. 问七问（谁看/看什么/看完做什么/从哪来/什么设备/什么时候要/不做什么）<br>2. 逐条确认素材四项（文案、图片、Logo、域名与备案）<br>3. 落成 `templates/brief.md` 结构<br>4. 请用户逐条确认，改到点头为止<br>5. 把"不做"清单单独列出来复述一遍 |
| **判断** | 七问中"待定"≥3 个 → 立项未完成，只能做单页试用版；素材缺 ≥2 项 → 阻塞 W4，先解决素材；"不做什么"为空 → 必须补，否则范围必然蔓延 |
| **输出** | 立项单（一页 Markdown），字段见 `io-contract.md` 的 Brief 定义 |
| **异常** | 用户答不上来 → 给三个具体选项让他选，不替他编；用户中途加页 → 写进"本期不做"并说明延后什么；用户拿竞品说"照这个做" → 拆成结构/内容/视觉三层，只允许结构层参考 |
| **依赖** | 无需代码；只需对话与用户确认 |
| **关系** | 下游 W2 必须有立项单才能选型；W5 的渠道信息来自本步第 4 问 |

## W2 · 技术选型路由

| 项 | 内容 |
|---|---|
| **职责** | 用三个与用户有关的问题决定技术方案，而不是问"你想用什么框架" |
| **输入** | 立项单；内容更新频率；是否需要登录/支付/实时数据；维护者能力 |
| **步骤** | 1. 跑 `project_scan.py`（老项目改造时必做）<br>2. 按三问过 `references/stack-matrix.md` 的决策树<br>3. 写三句话结论：选什么、为什么、放弃的方案代价<br>4. 列出该方案的构建命令与产物目录<br>5. 确认部署平台与产物形态匹配（静态产物 vs 需要 Node 运行时） |
| **判断** | 能静态就不上框架；需要服务端却选了静态托管 → 必须停下改选型；维护者不会改代码 → 内容必须走 Markdown 或 CMS，不能是硬编码在 HTML 里 |
| **输出** | 选型结论（三句话）+ 目录骨架 + 第一个可运行命令 |
| **异常** | 用户已指定框架但与需求冲突 → 说明冲突点与代价，让他决定，记录下来；依赖装不上（网络/版本）→ 降到零依赖静态方案，不硬扛 |
| **依赖** | `scripts/project_scan.py`（判断存量项目类型） |
| **关系** | 上游 W1；下游 W3 按结论搭骨架；W7 的部署方式由本步产物形态决定 |

## W3 · 骨架与职责划分

| 项 | 内容 |
|---|---|
| **职责** | 产出一个能跑起来的空壳，每个文件有唯一职责 |
| **输入** | 选型结论；页面清单（来自立项单） |
| **步骤** | 1. 建目录树（页面 / 资源 / 配置 / 说明四类）<br>2. 每页写语义骨架（header/nav/main/footer + 一个 h1）<br>3. 抽一个样式入口文件，一个脚本入口文件<br>4. 起本地服务确认能打开<br>5. 写 README：怎么改、怎么发、改坏了怎么退 |
| **判断** | 空壳打不开 → 不许往下走；页面职责说不清一句话 → 页面该合并或删掉；出现 `utils2.js` → 重新划分边界 |
| **输出** | 可运行空壳 + 目录树说明 |
| **异常** | 用户要求先看视觉稿 → 用低保真结构图代替，不做高保真设计；框架脚手架报错 → 用最小静态骨架顶上，先把内容跑通 |
| **依赖** | 构建工具（若有）；本地静态服务器 |
| **关系** | 上游 W2；下游 W4 在骨架上填内容 |

## W4 · 页面实现

| 项 | 内容 |
|---|---|
| **职责** | 按"结构→样式→交互→内容"的顺序把页面写完整 |
| **输入** | 骨架；文案与图片素材；立项单里的行动目标 |
| **步骤** | 1. 先写语义结构（标题层级、地标、表单字段）<br>2. 写样式（移动优先，一次只加一个断点）<br>3. 写交互（四态：默认/悬停/加载/失败）<br>4. 填真实内容，标出占位内容<br>5. 每写完一页跑一次 `audit_html.py` |
| **判断** | 单页 h1 不等于 1 → 先修结构再加样式；图片无原图 → 用占位并标注，不许拉伸变形；交互无失败态 → 不算完成 |
| **输出** | 完整页面文件 + 每文件一句职责说明 |
| **异常** | 素材缺失 → 占位 + 清单；设计要求破坏语义（两个主标题） → 视觉两个、语义一个；样式互相覆盖 → 先建变量与层级，不要靠 `!important` 堆 |
| **依赖** | `scripts/audit_html.py` |
| **关系** | 上游 W3；与 W5 交替（写完一页就补元信息）；下游 W6 全站复检 |

## W5 · 索引可见性

| 项 | 内容 |
|---|---|
| **职责** | 让页面能被搜到、被正确分享，不留技术性障碍 |
| **输入** | 已成型页面；正式域名；渠道信息 |
| **步骤** | 1. 每页写唯一 title 与 description（按阈值）<br>2. 配 canonical（绝对 URL）、og 三件套<br>3. 按页面类型加 JSON-LD，只写真实字段<br>4. 生成 sitemap 与 robots（`seo_files.py --write`）<br>5. 确认测试环境已 `Disallow`，生产环境放开 |
| **判断** | 标题重复 → 必改；canonical 与预期地址不一致 → 必改；结构化数据里写了不存在的评分/价格 → 必删；robots 禁了全站却已上线 → 最高优先级修复 |
| **输出** | 索引资料（每页元信息 + sitemap.xml + robots.txt）+ 体检表 |
| **异常** | 页面是 SPA 且内容由 JS 渲染 → 说明收录风险，给预渲染或 SSR 方案；多域名并存 → 定一个主域，其余 301 |
| **依赖** | `scripts/seo_files.py` |
| **关系** | 上游 W4；结果进入 W7 预检 P08 |

## W6 · 无障碍与体积体检

| 项 | 内容 |
|---|---|
| **职责** | 用脚本把"能不能用"和"够不够轻"变成可核对的数字 |
| **输入** | 页面目录或构建产物目录 |
| **步骤** | 1. `audit_html.py --fail-on high`<br>2. 按 BLOCKER → HIGH → MEDIUM 顺序修<br>3. `budget_check.py`，看最大文件<br>4. 压图片、拆 JS、子集化字体<br>5. 重跑两脚本，直到无阻塞 |
| **判断** | 有 BLOCKER → 不可交付；体积超 20% 内可上线但列清单，超 50% 不可上线；只有 LOW → 记录不阻塞 |
| **输出** | 体检报告（`templates/audit-report.md`）+ 修复后的代码 |
| **异常** | 脚本报的像误报 → 先验证，再记入"已知误报"，不许静默忽略；用户不许改设计 → 折算成后果说明，让他决定；对比度算不出 → 给颜色对，让用户在浏览器确认 |
| **依赖** | `scripts/audit_html.py`、`scripts/budget_check.py` |
| **关系** | 上游 W4/W5；下游 W7 要求 BLOCKER 为 0 |

## W7 · 上线预检与部署

| 项 | 内容 |
|---|---|
| **职责** | 把"能上线"变成"能撤销的上线" |
| **输入** | 构建产物；部署平台；域名与证书；回滚方式 |
| **步骤** | 1. `deploy_preflight.py`，BLOCKER 清零<br>2. 定平台（`references/deploy-matrix.md`）<br>3. 配 DNS → 等生效 → 签证书 → 强制 HTTPS<br>4. 执行部署，逐条验证（首页/关键页/404/资源）<br>5. 写上线手册，含回滚命令与 72 小时观察表 |
| **判断** | BLOCKER >0 → 不给部署命令；无回滚演练 → 先发预览环境；境内服务器未备案 → 不可上线 |
| **输出** | 上线手册（`templates/runbook.md`）+ 部署与验证记录 |
| **异常** | 平台构建失败但本地成功 → 看平台日志，按日志改；域名不生效 → `dig` 查记录与 TTL，别反复改；证书失败 → 查 80 端口与 CDN 代理；密钥已泄漏 → 先吊销再改代码 |
| **依赖** | `skills/czl-site-ship/scripts/deploy_preflight.py`；平台 CLI/控制台 |
| **关系** | 上游 W6（阻塞为 0）；下游 W8；出问题回 W4/W6 |

## W8 · 上线后观察与回滚

| 项 | 内容 |
|---|---|
| **职责** | 在用户投诉之前发现问题；出问题时先止血 |
| **输入** | 上线手册；监控/日志入口；上一版产物或部署记录 |
| **步骤** | 1. 上线即刻验：首页、关键页、404、静态资源<br>2. +1 小时验：表单/联系入口能否收到<br>3. +24 小时看：5xx 比例、首屏时间<br>4. +72 小时看：收录提交、真机抽查<br>5. 异常则回滚，回滚后写复盘 |
| **判断** | 任一 5xx → 立即回滚；表单收不到 → 不回滚也先挂备用联系方式；错误率 >1% → 回滚；仅样式小瑕疵 → 记录，不回滚 |
| **输出** | 观察表 + 复盘（现象/影响/时间线/根因/防复发） |
| **异常** | 回滚失败 → 停手，先保住数据与访问，再定位；无法回滚 → 用上一版产物覆盖；证书过期 → 先续期，别动代码 |
| **依赖** | 平台历史部署；日志与监控 |
| **关系** | 上游 W7；结论回灌 W4/W6 形成修复项 |
