# 选型矩阵

选型的唯一标准：**谁维护，能维护多久。**

一个用不上框架的 5 页官网上了 Next.js，两年后升级依赖的人找不到，这就是选型事故。

---

## 一、决策树（照顺序问，第一个"是"就停）

```
1. 有没有登录 / 支付 / 实时数据 / 后台管理？
   ├─ 有 → 需要服务端运行时 → 见「需要服务端」一节
   └─ 没有 → 继续

2. 内容页数会不会持续增加（每周新增文章/产品）？
   ├─ 会 → 静态生成（SSG）+ Markdown，或接 CMS
   └─ 不会（固定 3–10 页） → 继续

3. 维护的人会改代码吗？
   ├─ 会 → 纯静态 HTML/CSS/JS；页面多了再上组件化
   └─ 不会 → 纯静态 + 每页一个文件，改文字就在那个文件里改
```

三条都走到"不会"的分支，结论就是：**手写静态站，不要构建工具。** 这不是落后，是把维护成本压到最低。

---

## 二、方案对照

| 方案 | 适用 | 构建 | 产物 | 首屏 | 上手成本 | 三年后还活着吗 |
|---|---|---|---|---|---|---|
| 纯静态 HTML/CSS/JS | 3–10 页展示站、落地页、作品集 | 无 | 源文件即产物 | 最快 | 最低 | 几乎不会坏 |
| 静态生成（SSG） | 内容持续增加、需要模板复用 | 一次构建 | 静态文件 | 快 | 中 | 依赖生态稳定，但要跟着升级 |
| SPA（Vite + 框架） | 后台、工具类应用 | 一次构建 | 静态 + JS 渲染 | 慢（首屏空白） | 中 | 需要长期维护 |
| SSR（Next/Nuxt） | 需要 SEO 的动态站、登录态页面 | 每次请求/增量 | 需 Node 运行时 | 中 | 高 | 升级成本最高 |
| CMS + 静态 | 非技术人频繁改内容 | 发布触发 | 静态文件 | 快 | 中 | 取决于 CMS 是否持续运营 |

"三年后还活着吗"这一列比性能更重要。选型时把它当第一优先级。

---

## 三、什么情况下不要用框架

- 页面 < 10 个，且内容不常变
- 维护者只会改文字
- 没有前端工程经验，也没有人能在半年后接手
- 部署环境受限（只能传文件，不能跑构建）

以上占两条，选纯静态。占三条，不要犹豫。

---

## 四、需要服务端时

| 需求 | 最小方案 | 说明 |
|---|---|---|
| 只收表单 | 静态页 + 表单服务（第三方或一个云函数） | 不为了收一封信养一台服务器 |
| 登录 + 数据 | 一体化框架（Next/Nuxt）+ 托管数据库 | 注意会话与权限，别把密钥放前端 |
| 文件上传 | 对象存储直传（预签名 URL） | 不要让文件经过应用服务器 |
| 定时任务 | 云函数定时触发 | 不要塞进 Web 进程 |

## 五、迁移路径（别一次做绝）

- 静态 → SSG：保留 URL 结构，只换构建方式，不换地址
- SSG → SSR：先只把需要动态的页面切过去，其余保持静态
- 任何迁移前：导出全部现有 URL，做 301 映射表

## 六、选型结论的写法

必须三句话，缺一句算没写：

```
选定：<方案>
理由：<和用户的三个约束怎么对上的>
放弃：<另一个方案>，代价是<具体代价>
```

反例（不算结论）：「用 Next.js 比较主流，生态好。」——没提约束，没提代价。
正例：「选定纯静态 HTML。理由：三页展示站、维护的人只改文字、只需传文件就能上线。放弃 SSG，代价是以后文章多了要手工加页面，约每月半小时。」
