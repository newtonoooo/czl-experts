# 工作流定义

六条工作流覆盖从"一句话需求"到"可交付文件"的完整链路。按需组合，简单需求不必全跑。

```
W1 分诊 → W2 建模 → W3 体检 → W4 渲染 → W5 复核 → W6 交付
              ↑         │
              └──── 返工 ┘
```

---

## W1 分诊 Triage

| 项 | 内容 |
|---|---|
| **名称** | 分诊（Triage） |
| **职责** | 把模糊需求收敛为可执行的制图简报，避免建模返工 |
| **输入** | 自然语言描述、文档/表格/代码、已有 `.mmd` |
| **依赖** | 无 |
| **输出** | 制图简报：类型、方向、主题、交付格式、假设清单、待确认项 |
| **下游** | W2 |

**执行步骤**

1. 判定信息形态：先后与分支→流程；状态迁移→状态机；实体属性→ER；对象继承→类图；多方交互→时序；工期→甘特；层级发散→思维导图；时间节点→时间轴；占比→饼图；双维度→四象限；分类数值→柱线。
2. 判定读者场景：文档→浅色纵向信息密；PPT→深色横向节点少；代码仓库→浅色+Mermaid。
3. 判定信息量：节点 >25 或层级 >7，先提拆分方案。
4. 输出简报，缺失项一次性提问（≤3 个）。

**判断条件**

- 只有目标没结构 → 先给一版标注"推断"的假设结构，再问是否调整。
- 需求不适合图表 → 直接说明理由并建议替代形式。
- 输入是 `.mmd` → 转 W3 的源码分支。

**异常处理**：信息严重不足且无法合理假设 → 只提 1 个封闭式问题，其余取默认值推进。

## W2 建模 Model

| 项 | 内容 |
|---|---|
| **名称** | 建模（Model） |
| **职责** | 把业务语言翻译成通过校验的 `model.json` |
| **输入** | W1 的简报 + 用户全部事实材料 |
| **依赖** | W1 |
| **输出** | `model.json` |
| **下游** | W3 |

**执行步骤**

1. 抽实体：能被独立指代、有明确职责的名词才建节点。
2. 定 id：语义化英文，禁止 `n1` / `A`。
3. 定关系：方向对不对？条件写没写？主路径还是异常路径（异常用 `dashed`）。
4. 定角色：primary / decision / data / external / success / danger / neutral。
5. 分组：同责任域 ≥3 节点时用 `groups`，组名写职责不写部门。
6. 压文案：节点标签 ≤12 字，边标签 ≤8 字，长文案下沉 `note` / `footnote`。
7. 落盘 `<slug>.model.json`。

**判断条件**

- 节点 >30 → 停止建模，先与用户确认拆分边界。
- 出现环（回退路径）→ 保留，回退边设 `dashed` 并在 footnote 说明。
- 数据类图表 → 数值逐项来自材料，缺项就问，不插值。

**异常处理**：字段写错 → 按 `dg check` 的「字段路径: 原因」逐条修，禁止绕过校验。

## W3 体检 Lint & Score

| 项 | 内容 |
|---|---|
| **名称** | 体检（Lint & Score） |
| **职责** | 渲染前拦住结构性问题 |
| **输入** | `model.json` 或 `.mmd` |
| **依赖** | W2 |
| **输出** | 体检结论 + 修复后的模型 |
| **下游** | W4（通过）或 W2（返工） |

**执行步骤**

1. `dg check model.json` — 结构合法性。
2. `dg review model.json` — 质量分与改进项。
3. 按分决策：≥90 直接放行；78–89 修掉 high 级；65–77 必须重构；<65 回 W2。
4. `.mmd` 输入：`dg check xxx.mmd` 报语法问题；通过则给版式与配色建议。

**判断条件**

- high 级问题（孤立节点、判断无分支、负工期等）一条都不许留。
- 分数 ≥78 但用户要求"信息全都要" → 可放行，但交付说明必须写清可读性代价。

**异常处理**：校验报错导致无法继续 → 回到 W2 修模型，不允许改渲染器绕过。

---

## W4 渲染 Render

| 项 | 内容 |
|---|---|
| **名称** | 渲染（Render） |
| **职责** | 一次生成全部交付格式 |
| **输入** | 通过体检的模型 + 主题与格式决定 |
| **依赖** | W3 通过 |
| **输出** | `.svg` / `.html` / `.mmd` / `.txt` / `.model.json` |
| **下游** | W5 |

**执行步骤**

1. 选主题：文档 `graphite`/`paper`；PPT `midnight`/`nordic`；打印 `paper`。
2. 执行 `dg render model.json --out <dir> --theme <name> --format svg,html,mmd,ascii`。
3. 校验产物存在、可打开、HTML 主题按钮可用。
4. 需要多套配色对比时加 `--all-themes`。

**判断条件**

- 贴 PPT/Word → 必须给 SVG。
- 发群/发邮件 → 给 HTML。
- 代码注释 → 给 ASCII。
- 二次编辑 → 给 MMD。

**异常处理**：`未知主题` / `模型校验未通过` → 按提示修参数或模型，不重复执行同样命令。

---

## W5 复核 Visual QA

| 项 | 内容 |
|---|---|
| **名称** | 复核（Visual QA） |
| **职责** | 检查机器指标看不到的观感问题 |
| **输入** | W4 产物 |
| **依赖** | W4 |
| **输出** | 复核结论（通过 / 返工项） |
| **下游** | W6（通过）或 W2/W4（返工） |

**执行步骤**

1. 比例：宽高比 >4:1 或 1:4 → 换方向重渲染。
2. 标签：是否截断、是否压箭头、是否超过两行。
3. 连线：长边是否绕行过远、是否穿节点、同层边是否挤在一起。
4. 分组：组框是否包错节点、组名与内容是否相符。
5. 配色：深浅底对比度、语义色是否用对。

**判断条件**：影响"读懂"必须返工；仅影响"好看"记录在交付说明由用户决定。

**异常处理**：无法用命令行验证的观感问题 → 用 `present_files` 打开 HTML 与用户共同确认，不得自行宣称"已确认无误"。

**返工优先级**：改模型（结构）→ 改参数（主题/方向）→ 最后才考虑改代码。

## W6 交付 Deliver

| 项 | 内容 |
|---|---|
| **名称** | 交付（Deliver） |
| **职责** | 文件、说明、修改方式一次给全 |
| **输入** | W4/W5 产物 + 简报中的假设清单 |
| **依赖** | W5 |
| **输出** | 文件 + 交付说明 |
| **下游** | 无（用户验收） |

**执行步骤**

1. `present_files` 展示 HTML（首选）与 SVG。
2. 交付说明固定四段：这张图说了什么 / 结构假设 / 文件清单 / 怎么改。
3. 附 `model.json` 修改指引。
4. 给嵌入建议（宽度、背景是否透明）。

**判断条件**：用户只要图不要说明 → 仍保留一句"改哪一行能改什么"。

**异常处理**：用户对结构有异议 → 只改模型重渲染，不重新描述需求。

## 路由表

| 用户说法 | 路径 |
|---|---|
| 画个流程图 / 审批流 | W1→W2→W3→W4 |
| 画表结构 | W1→W2(ER)→W3→W4 |
| 接口调用顺序 | W1→W2(时序)→W3→W4 |
| 检查这段 Mermaid | W3（源码分支） |
| 换个配色 / 主题 | W4 |
| 图太挤 / 看不懂 | W3→W2→W4 |
| PPT 用架构图 | W1(深色+LR+精简)→W2→W3→W4 |
| 数据做成图表 | W1→W2(数值须来自材料)→W3→W4 |
