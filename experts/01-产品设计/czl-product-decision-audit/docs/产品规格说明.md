# 产品规格说明

产品：产品决策审校专家 · 定盘（Setpoint）
包标识：`czl-product-decision-audit`
版本：1.0.0
作者：虫志龙

本文件是独立编写的产品需求规格，用于定义"做什么、为谁做、做到什么程度"，不描述参考产品的实现。

---

## 1 目标用户

| 用户 | 处境 | 最痛的一件事 |
|---|---|---|
| 1–3 年经验的产品经理 | 被要求"拿数据说话"，但没人教过怎么评证据 | 会开了，结论被一句"你这个数据哪来的"打回来 |
| 产品负责人 / 小团队 PM 头 | 同时向上向下解释，两边说法要一致 | 对老板和对工程说的话，经常对不上 |
| 创始人 / CEO（无专职 PM） | 自己写 PRD、自己排期、自己复盘 | 文档写了一堆，团队还是各干各的 |
| 技术负责人转产品 | 工程判断强，商业论证弱 | 方案很扎实，说不清值不值得做 |
| 独立开发者 | 一个人干完发现—定义—交付 | 没有第二个人来挑错，错误一路做到上线 |

## 2 使用场景（真实触发）

1. 周一要给老板一页纸，讲清为什么这个需求不做
2. 需求评审会上被问"成功标准是什么"，答不出来
3. 销售持续施压要某个功能，需要一份能公开的优先级依据
4. 季度复盘，指标掉了，几个部门各说各话
5. 竞品发了新版本，老板问"要不要跟"
6. PRD 写完，工程反馈"这不是需求，是想法"
7. 上线三个月，没人敢说这个功能该不该继续投
8. 要同时向高管、工程、客户解释同一个决定

## 3 要解决的问题

| # | 问题 | 现状表现 |
|---|---|---|
| P1 | 结论先有，证据后凑 | 需求文档里"用户强烈需要"，追问只有两条转述 |
| P2 | 口径不清 | 同一个"月活"在三个部门是三个数 |
| P3 | 没有反方 | 会上没人反对，事后一起复盘失败 |
| P4 | 交付断裂 | PRD 到验收之间靠口头，异常流程靠上线后补 |
| P5 | 无法止损 | 投入没有上限，做错了也没有退出条件 |
| P6 | 输出不可用 | 给了框架名词，落不成能发出去的材料 |
| P7 | 产能幻觉 | 5 人 12 周当作 60 人周，排出来的计划必然延期 |
| P8 | 同一事实多种说法 | 对客户说"即将上线"，对工程说"还没定"，被交叉询问时露馅 |

## 4 必要输入

**必需**

- 请求的原始表述（用户原话，不是概述）
- 决策截止时间

**按场景必需**

- 涉及判断真假：任意已有材料（反馈原文、工单、数据、截图、竞品链接）
- 涉及数字：指标名与当前值；能提供口径更好
- 涉及排期：候选清单、人数、周期长度
- 涉及对外表达：受众是谁、要对方做什么

**可选**

- 旧文档、已有 PRD、历史路线图
- 埋点或报表位置
- 已知的依赖方与承诺时间

## 5 预期输出

### 5.1 默认交付物：决策包

| 区块 | 内容 | 硬要求 |
|---|---|---|
| 1 结论 | 一句话 | ≤40 字，含动作、范围、时间；不得出现"建议进一步评估" |
| 2 证据等级与最弱环节 | 结论挂在什么等级，最弱一环，补强成本 | 必须有等级标记 |
| 3 反方与失效条件 | 最强反对意见 + 作废条件 | 至少一条可观测的失效条件 |
| 4 下一步与止损线 | 做什么、谁做、何时看、何时停 | 三要素齐全 |
| 5 待确认 | 未决问题 | ≤3 条，每条指明责任人角色 |

### 5.2 按场景的附加交付物

| 决策类型 | 附加交付物 |
|---|---|
| 立项判断 | 决策简报（门型、四问结果、如果一定要做的最小版本） |
| 规格化 | 规格书（八节）+ DoR 检查表 + AC→TC 映射 + 变更成本账簿 |
| 组合取舍 | 排序表 + 砍单清单与原因 + 三选一的上行方案 |
| 指标体检 | 口径卡 + 变化判定 + 分组检查 + 归因候选 + 可以说/不能说 |
| 需求取证 | 证据台账 + 频次表 + 反例检索说明 |
| 竞争取证 | 竞争取证表（来源类型/日期/套餐/是否实测）+ 跟或不跟的判定 |
| 对外表达 | 2–4 个受众版本，事实一致，密度不同 |
| 续投判定 | 四档判定 + 下线四步前置动作 |

### 5.3 输出形态

- 主体为 Markdown，可直接粘贴到文档工具或会议材料
- 表格用于对比；叙述用段落
- 数字必带口径与周期
- 不含占位符、不残留"[待补充]"

## 6 通用处理步骤

```
接收请求
  ↓
判断：决策 还是 执行？执行 → 直接给执行方案，不套框架
  ↓
G1 分诊：定门型 → 清材料 → 四问检验 → 三选一出口（做 / 补材料 / 不做）
  ↓（做）
G2 证据：拆断言 → 评等级 → 找最弱环节 → 检索反例 → 给结论上限
  ↓
G3 口径：口径卡 → 波动带 → 样本充分性 → 口径漂移 → 辛普森 → 归因候选
  ↓
G4 对抗：失效条件 → 事前验尸 → 反方最强论点 → 止损线 →（续投时）四档判定
  ↓
G5 交付：DoR → 规格 → 验收映射 → DoD → 变更账簿 → 受众渲染
  ↓
输出决策包 + 附件；结尾给待确认与下一步
```

每一步的判断条件与异常处理，见对应 `skills/*/SKILL.md`。

## 7 工具能力与技术接口

### 7.1 必需能力

| 能力 | 用途 |
|---|---|
| 读取本地文本/CSV/Markdown | 台账、候选清单、口径卡、指标序列 |
| 运行 Python 脚本 | 三个随包工具 |
| 生成 Markdown | 全部交付物 |
| 外部检索（可选） | 竞品事实核实，必须带日期 |

### 7.2 随包工具接口

| 工具 | 命令 | 输入 | 输出 | 退出码 |
|---|---|---|---|---|
| `evidence_check.py` | `ledger.csv [--conclusion-grade] [--purpose] [--json] [--strict]` | CSV 台账 | 错误/提示清单 | 0 通过 / 1 有错 / 2 用法或文件问题 |
| `metric_guard.py card` | `cards.csv` | 口径卡 CSV | 缺失字段、含糊措辞、去重/排除缺失 | 同上 |
| `metric_guard.py baseline` | `值序列 [--k]` | 逗号分隔或 CSV 列 | 中枢、稳健波动、正常带、信号判定 | 同上 |
| `metric_guard.py ab` | `--control N K --treat N K` | 两组样本量与转化数 | p 值、差值区间、MDE、所需样本、结论 | 同上 |
| `metric_guard.py simpson` | `segments.csv` | 分组 exp/ctl 数据 | 分组表、合计、反转判定 | 0 未反转 / 1 反转 / 2 用法 |
| `portfolio_fit.py` | `backlog.csv --headcount --weeks --utilization --history` | 候选清单 | 产能、排入/砍单、脆弱项、吞吐比对 | 0 装得下 / 1 装不下 / 2 用法 |

### 7.3 依赖

- Python 3.9+，仅标准库（math / csv / json / argparse / zlib / struct / difflib）
- 无网络依赖，无第三方包，无数据库
- 不写入用户文件系统（除用户明确要求生成文档时）

## 8 质量要求

| 维度 | 要求 | 检验方式 |
|---|---|---|
| 结论可站住 | 至少一条可观测失效条件；结论等级不高于最强证据 | `evidence_check.py` + 人工复读 |
| 不编造 | 无来源的内容必须标 X 并写成假设；竞品事实必须带日期与来源类型 | 抽查全部数字与外部断言 |
| 可执行 | 每条下一步有动作、责任人角色、时间点 | 逐条检查第 4 区块 |
| 口径可复算 | 所有数字带定义、时间窗、系统 | 口径卡检查 |
| 形态可用 | 无占位符；表格只用于对比；可直接粘贴 | 通读 |
| 一致 | 多受众版本结论指向同一动作 | 并排比对 |

## 9 速度与稳定性要求

- 单一决策包：一次对话内产出，不跨会话
- 证据超过 15 条时建议改用台账 + 脚本，避免遗漏
- 材料不足时**优先快而准地说明不足**，不产出长篇低置信内容
- 不因材料缺项而中断任务；缺项写入"待确认"，同时给出补材料的最小方案

## 10 非目标（明确不做）

1. 不做通用文案写作、营销文案、周报美化
2. 不做项目管理排期表、甘特图、任务分配系统的实现
3. 不替代用户研究：不做访谈设计执行、不发问卷、不生成虚构用户声音
4. 不提供法律意见、财务审计、投资建议、医疗建议
5. 不承诺"零风险"方案；不按用户要求删除风险段落
6. 不替用户向他的上级论证一个已定结论（会转为压力测试）
7. 不做竞品数据的长期抓取与监控（只做单次取证，强制标日期）
