# G3 口径：这个数字到底在说什么

## 什么时候用

- 会上有人问"为什么掉了/涨了"
- 两个部门对同一个指标给出不同数字
- A/B 跑完了要定结论
- 要对外汇报某个指标
- 指标口径最近改过（换了埋点、换了系统、换了算法）

## 为什么这一闸不能省

产品评审里最常见的假争论，不是观点不同，是**同一个词指不同的数**。

一个"月活下降 6%"背后可能是七种完全不同的情况：

1. 真的少人用了
2. 埋点版本升级，漏报了一部分设备
3. 定义从"登录"改成了"有核心行为"
4. 上个月有活动，这个月没有（季节性）
5. 某个渠道被下架
6. 去重规则从设备改成账号，多设备用户被合并
7. 在正常波动带内，什么都没发生

**在排除 2/3/6 之前，讨论 1 是浪费会议时间。** 顺序很重要：先口径，再波动，再归因。

## 第一步：口径卡

任何一个要进结论的数字，先写出六件事：

| 字段 | 要写到什么程度 |
|---|---|
| 定义 | 一句话说清"算什么"，别人照着能重算 |
| 分子 | 具体事件/记录 |
| 分母 | 具体人群/记录；绝对值指标写"不适用" |
| 时间窗 | 自然日/自然月/滚动 30 天/注册后 N 天，必须明确 |
| 来源系统 | 哪张表、哪个后台、哪个报表 |
| 去重与排除 | 按什么去重；排除哪些（退款、内部账号、测试、爬虫） |

缺任何一项，这个数字只能当**参考**，不能当**证据**。

写完自检一句：**换一个人按这张卡去查，能不能查出同一个数？** 不能就是没写清。

`scripts/metric_guard.py card` 会机械检查这些字段，并标出"活跃用户""视情况""待定"这类没写清的措辞。

## 第二步：波动带

任何指标都有噪声。周环比 2% 的变化，在多数产品里毫无意义。

做法：取最近 12–20 期，算中位数和稳健波动（MAD），得到正常带。落在带内 → 写成"在正常波动内"；连续 3 期同向超出 → 才算趋势。

```bash
python scripts/metric_guard.py baseline 412,401,398,420,405,410,388 --k 2.5
```

为什么用中位数和 MAD 而不是平均值和标准差：**平均值会被上一次的异常值污染。** 上次做活动冲高，平均线被拉高，之后几周都会被误判为"下滑"。

判定口径要写进汇报材料。写"下降 6%"是不合格的；写"下降 6%，超出近 20 周正常带（±0.9%），连续 2 周"才合格。

## 第三步：样本是否够

两个地方最容易糊：

**一是百分比。** 11 个用户里涨了 4 个，不是"提升 12%"，是"11 人里多了 4 人"。样本低于 30 不给百分比，低于 8 只给个例。

**二是 A/B。** 看三个数：p 值、差值区间、最小可检出效应（MDE）。

- 显著（p<0.05）且区间不含 0：方向可信
- 不显著：不要说"有提升趋势"，要说"没测出来"，并给出每组需要的样本量
- 实测差异小于 MDE：说明这次实验对这么小的效应本来就没能力判断

```bash
python scripts/metric_guard.py ab --control 10000 512 --treat 10000 583
```

**不显著不等于没效果**，只等于"这次没测出来"。这两句在会上的分量完全不同，说错会被懂行的人抓住。

## 第四步：口径漂移

所有趋势判断的前提是：两个时间点的数，是同一个东西。

每次做同比/环比之前，先问三句：

1. 埋点或报表逻辑，这两个时间点之间改过吗？
2. 系统迁移过吗？（换库、换 SDK、换第三方）
3. 去重口径改过吗？

改过就必须**断开趋势线**，在图上标明"口径变更，前后不可比"。把两个不可比的数画成一条上升曲线，是产品汇报里最严重的失真，而且很难被当场发现。

处理方法：
- 有能力重算 → 用新口径回溯历史，重算一遍
- 不能重算 → 分段看，各自和自己比
- 都不能 → 只做定性描述，不给趋势

## 第五步：辛普森反转

合计数字方向对了，不代表每个分组都对。典型场景：新流量结构变化（移动端占比升高），把两个分组的不同表现混成一个看起来平稳的合计。

```bash
python scripts/metric_guard.py simpson fixtures/segments_simpson.csv
```

只要分组方向与合计方向相反，**合计数字就不能对外用**。会上要讲分组，不讲合计。

日常检查三个分组维度：**新老用户、平台/端、渠道来源**。这三个最容易出现结构变化。

## 第六步：归因候选（不是归因结论）

找到变化之后，别急着说原因。给一份候选清单，每条写"如果要成立，需要看到什么"。

| 候选原因 | 若要成立，应看到 | 现在的证据 | 状态 |
|---|---|---|---|
| 埋点漏报 | 受影响设备集中在某个版本 | 版本分布未查 | 待查 |
| 季节性 | 去年同期也降 | 去年同期降 4% | 部分支持（C） |
| 竞品分流 | 流失用户提到竞品 | 无 | 无证据 |
| 定价变更 | 变更后新用户转化下降 | 新用户降 14%，老用户持平 | 支持（A） |
| 正常波动 | 在正常带内 | 超出带 | 排除 |

**"部分支持""无证据""排除"三种状态都要写。** 只写支持结论的那一行，是选择性举证。

## 输出：指标体检单

```
## 指标体检单

### 口径
| 指标 | 定义 | 时间窗 | 系统 | 去重/排除 | 可否复算 |

### 变化判定
| 指标 | 本期 | 上期 | 变化 | 正常带 | 判定 |
判定只能写四种：真实变化 / 在正常波动内 / 口径变更不可比 / 样本不足

### 分组检查
| 维度 | 合计方向 | 分组方向 | 是否反转 |

### 归因候选
（按上表，含"排除"的行）

### 可以说与不能说
可以说：___
不能说：___
```

最后一块是本技能的交付重点。用户拿着它去开会，被追问时知道边界在哪。

## 异常

| 情况 | 处理 |
|---|---|
| 用户给不出口径 | 先按他描述反推一个定义，请他确认。确认不了就标"口径未确认"，所有结论降为参考 |
| 数据里有明显异常值（0 或极端大） | 先查是不是埋点或补数造成，不要直接删。删数据是最后手段，且必须记录 |
| 用户已经写好了"因为 A 所以 B"的汇报 | 不要直接改，先做候选清单，把他的单一归因放进去对比 |
| 指标本身定义有争议（如"活跃"） | 把争议写进材料，不要替公司定标准；给两套口径各自的数 |
| 用户要"预测下季度" | 不给点预测。给区间 + 关键假设 + 假设失效的信号 |
