# G5 交接：让工程不用回头问你

## 什么时候用

- 需求过会通过，要交给工程
- 工程反馈"这不是需求，是想法"
- PRD 写完但评审会上被逐条挑
- 需求中途被加东西，想留个账

## 检验标准只有一条

**把文档给一个没参加过讨论的工程师，他能不能开始做事，并且知道什么算做完。**

不能，就不是交付物。跟文档多长没关系。

## 第一步：DoR（定义就绪）

进排期之前必须齐的八项。缺一项就不该进，进去了也会在开发中途返工。

| # | 项 | 合格标准 |
|---|---|---|
| 1 | 用户场景 | 写清谁、在什么情况下、要完成什么。不是"提升体验" |
| 2 | 现状 | 现在用户怎么解决的，痛点在哪一步 |
| 3 | 范围 | 明确做什么，也明确不做什么 |
| 4 | 成功标准 | 一个可测指标 + 目标值 + 观测时间点 |
| 5 | 验收标准 | 至少覆盖正常、异常、边界三类 |
| 6 | 依赖 | 上下游系统、其他团队、第三方，各自的承诺时间 |
| 7 | 数据与埋点 | 需要哪些事件、字段、报表；谁埋 |
| 8 | 设计 | 关键界面或交互说明；空态、错态、超限态都覆盖 |

**第 8 项的空态、错态、超限态是最高频的返工源。** 只画了正常流程的设计稿，开发到一半一定会来问"没有数据的时候显示什么"。

## 第二步：规格书结构

八个部分，每部分有精度要求：

| 部分 | 必须写到什么程度 | 常见不合格 |
|---|---|---|
| 1 背景与问题 | 一段话说清现状和缺口，带一个 B 级以上证据 | 全是行业趋势 |
| 2 目标与非目标 | 非目标至少 3 条，每条写为什么不做 | 只有目标 |
| 3 用户与场景 | 具体角色 + 触发条件 + 频次 | "用户"两个字 |
| 4 功能范围 | 主流程分步写；边界条件列表 | 一句话描述整个功能 |
| 5 规则与逻辑 | 判断条件、优先级、冲突处理、默认值 | "系统自动处理" |
| 6 状态与异常 | 空、错、加载、无权限、超限、并发 | 只写正常流 |
| 7 验收标准 | 每条对应一个可执行的测试用例编号 | "功能可用" |
| 8 数据与观测 | 埋点事件名、字段、口径；上线后看哪个报表 | 上线后再想 |

**第 5 项是规格书和想法之间最大的分水岭。** "系统自动匹配最优"不是规则，是愿望。要写：匹配哪些字段、冲突时按什么排序、匹配不到怎么办、用户能不能改。

## 第三步：验收标准映射到测试

每条验收标准必须能变成一个测试用例。格式：

```
AC-03 | Given 用户已导入 500 条以上记录 | When 点击导出 | Then 返回异步任务，页面提示"正在生成，完成后通知"
TC-03 | 构造 600 条记录 → 触发导出 → 断言：接口返回 202，任务状态为 pending，30 秒内收到站内信
```

规则：

- 一条 AC 对一条 TC，不要多对一（多对一说明 AC 写得不够具体）
- 每条 AC 至少包含：前置条件、动作、可观测结果
- **异常路径的 AC 数量应不少于正常路径的 1/3**。少于这个比例，说明异常没想过
- 验收标准里不允许出现"友好""流畅""快速""合理"这类词，除非同时给了量化定义

## 第四步：DoD（定义完成）

DoR 管"能不能开始"，DoD 管"算不算做完"。团队的 DoD 通常包括：

- 代码合并、通过评审
- 单测覆盖关键分支
- 验收标准全部通过（对应 TC 全绿）
- 埋点已上线并验证有数据
- 文档更新（帮助中心 / 内部 wiki）
- 灰度或回滚方案就绪
- 相关方已知会（客服、销售、运营）

**"功能开发完"不等于完成。** 没有埋点就没有观测，没有通知就没有人会用。

## 第五步：变更成本账簿

需求变更是常态，问题是变更不带价格。开一个账：

| 日期 | 变更内容 | 提出人 | 增加人周 | 挤掉了什么 | 决定 |
|---|---|---|---|---|---|
| 09-12 | 导出增加自定义字段 | 销售 | +2.5 | 原定的筛选优化 | 接受，筛选优化延后 |
| 09-18 | 支持导出 PDF | 客户 A | +4 | 无（拒绝） | 拒绝，转下季度评估 |

三条规则：

1. **每次变更都要写"挤掉了什么"。** 没有挤掉任何东西的变更，说明计划本来就有水分
2. **变更累计超过原估 30% 时，重新过一遍 G1。** 这已经不是原来那个需求了
3. **拒绝的变更也要记。** 半年后有人问"为什么没做"，账上有答案

## 第六步：和工程的握手

交规格时主动说清三件事，可以减少一半的来回：

1. **哪些地方我还没想清楚**（诚实列出来，比被问出来好）
2. **哪些地方可以商量**（技术实现方式、部分交互细节）
3. **哪些地方不能动**（合规要求、数据口径、验收阈值）

**"都可以商量"和"都不能动"一样糟。** 前者让工程不敢决策，后者让工程失去空间。

## 输出格式

```
## 规格书：{功能名}

### 0 一页摘要
问题 / 范围 / 不做什么 / 成功标准 / 预计人周

### 1 背景与问题（证据等级：__）
### 2 目标与非目标
### 3 用户与场景
### 4 功能范围（主流程 + 边界）
### 5 规则与逻辑（判断表）
### 6 状态与异常（状态表）
### 7 验收标准（AC → TC 映射表）
### 8 数据与观测（事件表）

## 附：DoR 检查表（逐项打勾）
## 附：变更成本账簿
```

第 0 节是给评审会用的，后面七节是给工程用的。**两者不能合并**——评审会看不了七节，工程不能用一页摘要开工。

## 异常

| 情况 | 处理 |
|---|---|
| 用户只有一句话想法，要你写完整规格 | 先回 G1 做分诊。想法阶段写规格，写出来的都是虚构细节 |
| 用户要求规格里不写异常流程（"先做正常流"） | 接受，但要求在规格里注明"异常流程待定，上线前必须补"，并把这条列入 DoD |
| 设计与规格冲突 | 以规格为准改设计；若设计更合理，改规格并记录原因 |
| 工程说"做不了" | 不要争，要问：是能力不够、时间不够，还是需求本身有逻辑矛盾。三种情况的处理完全不同 |
| 涉及第三方能力 | 写清对方的能力边界和 SLA，注明"依赖对方承诺，未验证" |
