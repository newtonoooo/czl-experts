# G4 对抗：先自己打一遍

## 什么时候用

- 方案要上会，尤其是"大家都同意"的时候
- 老板已经表态支持（这时最危险）
- 上线三个月，该不该继续投
- 一个结论你越看越顺眼

**最需要这一闸的信号，是"这个方案没有明显问题"。** 没有明显问题通常意味着没人认真找过。

## 一、失效条件

每条结论都要配一句"什么情况下它作废"。写法固定：

> 如果 ___（可观测的事实）在 ___（时间范围）内出现，则本结论不成立，应改为 ___。

例子：

| 结论 | 失效条件 |
|---|---|
| 批量导出值得做 | 若上线 30 天内使用该功能的付费账号少于 3%，则说明需求被高估，应停止后续迭代 |
| 涨价的流失可控 | 若涨价后 60 天内月流失率上升超过 1.5 个百分点，则应回退并改为分层定价 |
| 卡点在引导流程 | 若修复引导后激活率提升不足 5%，则说明卡点不在引导，之前的投入方向错误 |

**判定标准的三个要求**：

1. 可观测（有埋点或能查到，不靠感觉）
2. 有时间边界（什么时候看）
3. 有阈值（多少算不成立）

只写"如果效果不好就停"等于没写。

## 二、事前验尸

假设已经过去六个月，这件事彻底失败了。写出最可能的三个死因。

不要写"市场变化""执行不到位"这种放之四海皆准的话。产品失败的死因高度集中在这六类：

| 死因 | 具体表现 | 事前可查的信号 |
|---|---|---|
| **没人需要** | 上线后没人用，或只有最初提的那几个客户用 | 提需求的人是否就是使用者；有没有自建替代方案 |
| **用不起来** | 有人需要但门槛太高，完成率低 | 步骤数、必填项、是否需要培训 |
| **算不过账** | 有人用但不带来收入或留存 | 使用者与付费者的重合度 |
| **被替代** | 用户用别的办法解决了（Excel、人工、竞品） | 替代方案的成本有多低 |
| **组织不接** | 功能上线但没有配套流程、培训、考核 | 谁负责推、有没有人真的会用 |
| **活不下来** | 依赖的第三方接口/数据/合作方变化 | 依赖项是不是单一来源 |

**每一类写一句"如果要发生，现在应该已经能看到什么"。** 能看到但被忽略的信号，才是真正的风险。

六类里通常会命中一到两类。命中的那两类，就是要在方案里放监控和退出条件的部分。

## 三、反方最强论点

不是找一个反对者来吵，是**自己把对方最强的版本写出来**，然后看它站不站得住。

写法：三段

1. **对方最强的论点**（用对方会用的语言，不用贬义词转述）
2. **它的证据基础**（对方手里有什么）
3. **它成立需要什么前提**（哪个前提最可能不成立）

例：

> **反方**：现在做批量导出是在给即将流失的客户做定制，做完他们照样走，钱花在了最不该花的人身上。
> **证据基础**：这 3 条工单来自两家已经在比价的客户（销售侧信息）。
> **成立前提**：这两家客户确实已在评估替代方案。若其中一家刚续约，反方就不成立。

如果反方的最强版本都站不住，你可以更放心；如果站得住，方案要么改，要么加条件。

**禁止做法**：把反方写成"有人可能会觉得……"然后一句话打掉。这是自我安慰，不是对抗。

## 四、止损线

**没写止损线的方案不许交付。** 止损线三要素：

| 要素 | 写什么 | 例 |
|---|---|---|
| 投入上限 | 最多花多少（人周/钱/时间） | 最多 12 人周，不超过一个季度 |
| 检查点 | 什么时候看 | 上线后第 30 天、第 90 天 |
| 判定信号 | 看到什么就停 | 第 30 天使用率 < 3%，或相关工单未下降 |

三条必须同时具备。缺投入上限 → 会无限追加；缺检查点 → 没人回头看；缺判定信号 → 停了也说不出理由。

**止损线要在开工前写，并且写在文档最前面，不是附录。** 事后补的止损线一定是为继续做找理由。

## 五、续投判定

功能上线三个月后，这个问题必须有明确答案：加大投入 / 维持 / 冻结 / 下线。

按四档判定，看三个数：

| 判定 | 条件（满足两条以上） | 动作 |
|---|---|---|
| 加大投入 | 使用率高于同类功能中位；使用者的留存显著高于未使用者；有明确的下一步需求 | 排入下一周期 |
| 维持 | 使用率在低位但稳定；有一批稳定用户；维护成本低 | 只修 bug，不加功能 |
| 冻结 | 使用率持续下降；无新增需求；维护成本上升 | 停止迭代，保留可用 |
| 下线 | 使用率接近 0；有能力替代；维护成本高于价值 | 给迁移期 + 通知 + 数据导出 |

**下线的四个前置动作**，缺一个都会变成事故：

1. 通知受影响用户（提前期至少 30 天）
2. 提供替代路径或数据导出
3. 内部公告说明原因（不写"优化调整"这种空话）
4. 记录决策，注明当时的判断依据

## 六、偏差清单

开会前对照一遍，中了两条以上就要格外小心：

| 偏差 | 在产品决策里的样子 | 对抗动作 |
|---|---|---|
| 沉没成本 | "都做了 8 人周了，不能停" | 只问：从现在起再投 4 人周值不值，不提过去 |
| 确认偏误 | 只找支持自己的数据 | 强制做反例检索 |
| 锚定 | 被第一个报价/第一个方案锁住 | 要求至少两个完全不同量级的方案 |
| 损失厌恶 | 不敢下线，怕被追责 | 算"继续维护"的成本，并写进对比 |
| 社会证明 | "竞品都做了" | 问：做了之后我们的哪个指标会变 |
| 可得性 | 因为最近一个大客户投诉就改路线图 | 问：这类客户占多少收入 |
| 权威 | "老板说要" | 找老板的原话和目标，找目标而不是找指令 |

## 输出：对抗报告

```
## 对抗报告

### 失效条件
如果 ___，本结论不成立，应改为 ___。

### 事前验尸（六个月后失败）
死因 1：___ ｜ 现在能看到的相关信号：___
死因 2：___ ｜ 现在能看到的相关信号：___
死因 3：___ ｜ 现在能看到的相关信号：___

### 反方最强论点
论点：___
证据基础：___
成立前提：___
我的回应：___

### 止损线
投入上限：___  检查点：___  判定信号：___

### 结论是否改变
未改变 / 改变为 ___ / 加条件后成立：___
```

最后一栏必须明确写。**对抗做完结论不变是正常结果，但必须说明"被攻击后仍然成立的原因"。** 不写这一句，对抗就等于没做。

## 异常

| 情况 | 处理 |
|---|---|
| 用户认为对抗是"拖慢进度" | 说明成本：一次返工通常等于三轮对抗。给他一个 20 分钟版本（只写失效条件 + 止损线） |
| 用户已经无法接受方案被否 | 不做价值判断，只写"如果 ___ 则 ___"，把选择权还给他 |
| 方案风险确实很低（内网工具、可回滚） | 压缩到两行：失效条件 + 检查点。不要为了流程完整而写满六类死因 |
| 涉及安全或资金 | 对抗必须包含"最坏情况会损失什么"，并明确谁承担 |
