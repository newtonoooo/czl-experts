# 门型判定卡

用来在 30 秒内判定一个请求属于哪一类，避免所有事情都走同一套重流程。

## 判定流程图（按顺序问）

```
1. 是监管 / 平台规则 / 客户合同要求的吗？
   → 是 → C 合规驱动（不讨论要不要）
   → 否 → 2

2. 是已上线功能不符合原本承诺吗？
   → 是 → F 缺陷修补（走缺陷通道，不抢需求排期）
   → 否 → 3

3. 上线两周内能撤回、且不需要数据迁移吗？
   → 是 → 4
   → 否 → O 单向门（五闸全走）

4. 投入超过团队一个季度产能吗？
   → 是 → B 赌注（五闸全走 + 止损线必写）
   → 否 → R 可逆补丁（轻流程）
```

## 常见误判

| 误判 | 为什么错 | 正确判法 |
|---|---|---|
| "就加个导出按钮，工作量很小，算 R" | 工作量小不等于可回滚。导出会把数据带出系统，涉及权限与审计 | 看回滚成本，不看工作量 → O |
| "便宜点试一下，先降 20% 看反应" | 定价改回来会引起老客户投诉和退费，不是可回滚 | O |
| "换个文案措辞" | 若涉及承诺、免责、时效，改回来会造成已做出承诺的用户不满 | 看是否形成对外承诺 → O |
| "内部工具，坏了再修" | 内部工具影响的是别人一天的工作，且没有替代路径 | 看影响面是否是外部 → R 偏 O |
| "调研一下再说" | 调研不是出口，是材料补充手段 | 归到 G2，不许当结论 |

## 五类决策的动作差异

| 门型 | 谁拍板 | 需要谁在场 | 最短决策周期 | 交付物形态 |
|---|---|---|---|---|
| R 可逆补丁 | 产品自己 | 工程 | 当天 | 一段说明 + 验收点 |
| O 单向门 | 产品 + 技术负责人 | 加：法务/财务（若涉定价或合同） | 3–5 个工作日 | 决策包 + 回滚预案 |
| B 赌注 | 业务负责人 | 加：老板、数据 | 1–2 周 | 决策包 + 止损线 + 分阶段投入 |
| C 合规驱动 | 不由产品拍板 | 法务/安全 | 按监管时限倒排 | 合规对照表 + 证明方式 |
| F 缺陷修补 | 值班或产品 | 工程 | 按缺陷等级 | 复现步骤 + 修复验收 |

## C 型合规的特别说明

C 型最容易出两种错：

1. **讨论"要不要"**——浪费一轮会议，最后还是得做。
2. **只做表面功夫**——界面加了勾选框，但后台还在无授权收集。这是最常见的形式合规。

处理 C 型的正确问法是三句：
- 规则要求的最低动作是什么？（不做就没法上线的那条）
- 怎么证明做了？（日志、审计记录、对外声明）
- 谁签字负责？（合规责任不能落在产品一人身上）

## 门型会变

- R 在做的时候发现要动数据模型 → 升级为 O，重新走五闸。
- B 的验证阶段结果好 → 进入分阶段追加投入，但止损线要重新写，不能沿用旧的。
- F 反复出现在同一模块 → 不是缺陷问题了，是架构问题，升级为 O。

**门型升级要明确说出来**，不能默默按重流程继续，用户会觉得你突然变慢。
