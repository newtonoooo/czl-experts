## 1. 产品定位

一个**产品决策的产出系统**，不是文档代笔工具。

输入是"一件还没想清楚、但已经有人在催的事"；输出是一套**彼此对得上、能被追问、能被叫停**的决策包。

判断标准只有一条：这份决策包拿进会议室，会不会被一个认真的人一句话问倒。

### 1.1 它是什么

- 把模糊诉求压成可立项的题目（立案卡）
- 把每条结论钉到出处上（证据分级）
- 把需求写成可施工、可验收的规格
- 把计划装进真实人周，并写清砍掉什么
- 把成功定义成可计算的指标
- 交付前把五份文档对齐，找出断链

### 1.2 它不是什么

- 不是"一键生成 PRD"的模板填充器
- 不是竞品数据库（不内置任何竞品资料）
- 不是 BI 工具（不连接你的数据仓库）
- 不是法律/财务/投资意见提供者

## 2. 目标用户

| 用户 | 典型处境 | 最需要的能力 |
|------|----------|--------------|
| **产品经理（1–3 年）** | 被要求两周内出一份 PRD，但没做过完整链路 | 结构化立案 + 验收标准写法 + 排产 |
| **产品负责人 / 总监** | 手上 10+ 候选需求，团队产能固定，要向老板解释砍单 | 产能装箱 + 砍单清单 + 高管汇报 |
| **创业公司创始人** | 没有产品团队，自己兼产品，决策凭直觉 | 证据分级 + 止损线 + 反方意见 |
| **业务/运营转产品** | 会写方案但不会写验收，交付后反复返工 | 可测验收标准 + 一致性闸 |
| **独立开发者 / 一人公司** | 要判断一个功能值不值得做 | 立案卡档位判定 + 最低成本取证动作 |

## 3. 使用场景（真实工作流）

### 场景 A：季度规划会前一周

**处境**：11 个候选需求，团队 6 人 13 周，老板要一份"能做完"的计划。
**输入**：需求清单、团队人数、周期、上季度交付记录。
**期望输出**：committed 清单 + 砍单清单（含交代话术）+ 承诺率 + 每项止损线。
**判定成功**：会上没人问"这个排期怎么算出来的"。

### 场景 B：需求评审被质疑

**处境**：你写了一份 PRD，工程问"这个需求从哪来的"，你答不上来。
**输入**：现有 PRD、客户反馈记录、竞品截图。
**期望输出**：带 EVD 编号的证据台账 + 补了依据的规格 + 明确标为假设的条目。
**判定成功**：每条 P0 需求都能指到一条 A/B 级证据或显式假设。

### 场景 C：指标异常复盘

**处境**：MAU 涨 9%，付费转化掉 12%，明天要开会。
**输入**：两期指标数据、埋点口径说明、分群数据。
**期望输出**：口径卡 + 分母检查结论 + 辛普森反转检查 + 可检验归因假设。
**判定成功**：会上给出的解释带"若 X 成立应观察到 Y"的验证条件，而不是故事。

### 场景 D：竞品突然上线同类功能

**处境**：竞品上了你们的核心功能，还更便宜，老板问"要不要跟"。
**输入**：竞品公开页面、定价、你们的成本结构、客户分层。
**期望输出**：证据台账（公开信息 + 抓取日期）+ 差异化判断 + 两个季度动作 + 停止条件。
**判定成功**：结论里同时有"打哪里"和"什么情况下不打"。

### 场景 E：向三种受众汇报同一件事

**处境**：同一份结论要分别给高管、工程、设计讲。
**输入**：已完成的决策包。
**期望输出**：三版汇报，数字完全一致、叙事各不相同。
**判定成功**：三份文档里的同一指标值一致，且各自回答了该受众真正关心的问题。

## 4. 要解决的问题

| 编号 | 问题 | 现状 | 本产品如何解决 |
|------|------|------|----------------|
| P1 | 题目没想清就开工 | 需求方催得紧，直接进开发 | 立案卡五要素，缺两项就停下来问 |
| P2 | 结论没有出处 | "大家都知道""行业都这样" | 每条事实标 EVD 编号 + A/B/C/D/X 等级 |
| P3 | 验收标准不可测 | "体验流畅""性能要好" | AC 必须含数值/界值/状态，脚本校验 |
| P4 | 排期是排序不是装箱 | RICE 分数排完就交差 | 人周算法 + 依赖装箱 + 承诺率 |
| P5 | 砍需求不敢说 | 全塞进去再写"有一定风险" | 砍单清单必填"失去什么/何时回来/怎么交代" |
| P6 | 指标口径不清就归因 | 数掉了先编故事 | 口径卡 + 分母检查 + 波动带 + 辛普森检查 |
| P7 | 五份文档互相矛盾 | 各写各的，没人对齐 | 编号贯通 + `chain_check.py` 八项检查 |
| P8 | 方案没有退出机制 | 风险写"可控" | 每个承诺必填止损线 |

## 5. 必要的输入与预期输出

### 5.1 最小输入（可启动）

| 输入 | 必需性 | 缺失时的处理 |
|------|--------|--------------|
| 一句话诉求 | 必需 | 无法启动，先问 |
| 目标用户/角色 | 强建议 | 用选项式提问补，仍缺则按行业默认假设并标注 |
| 团队人数与周期 | 排产必需 | 停下来问，不假设"资源充足" |
| 现有证据材料 | 可选 | 走"假设模式"，全链路标 D 级 |
| 现有指标数据 | 指标环节必需 | 标注"基线未知"，给取证动作 |

### 5.2 输出清单

| 文件 | 内容 | 消费者 |
|------|------|--------|
| `00-决策简报.md` | 结论、代价、风险、待决策项 | 决策者 |
| `01-证据台账.csv/.md` | 主张、来源、等级、时效、假设清单 | 复核者、后续迭代 |
| `02-需求规格.md` | 目标、场景、需求池、AC、Non-goals | 工程、设计 |
| `03-产能排产.csv/.md` | 人周、依赖、状态、止损线、砍单清单 | 项目管理、老板 |
| `04-指标口径表.md` | 口径卡、护栏、读数节奏 | 数据团队 |
| `05-汇报包.md` | 高管/工程/设计三版 | 汇报人 |
| `99-一致性报告.md` | 断链与数字冲突明细 | 交付验收 |
| `meta.json` | 闸门记录、脚本调用记录 | 审计 |

## 6. 通用处理步骤（六段链）

| 阶段 | 执行者 | 核心动作 | 判断条件 | 失败处理 |
|------|--------|----------|----------|----------|
| S1 立案 | 主理人 | 五要素填空 + 档位判定 | 待确认项 ≥2 则停 | 用选项式提问补，最多 3 问 |
| S2 取据 | 证据官 | 拆问题 → 找源 → 判级 → 补分母 → 找反证 | 事实陈述无 EVD 编号则不通过 | 降级为假设 + 给取证动作 |
| S3 成文 | 需求架构师 | 九节结构 + REQ/AC 编号 | AC 不可测则不通过 | 重写 AC，补数值与界值 |
| S4 排产 | 产能规划师 | 人周测算 → 依赖装箱 → 砍单 → 止损线 | P0 装不下则阻断 | 给三选一（砍范围/加人/延期） |
| S5 度量 | 指标口径师 | 口径卡 + 护栏 + 读数节奏 | 比率类缺分母则不通过 | 退回补口径 |
| S6 汇报 | 主理人 | 三版改写 + 一致性校验 | 脚本 error > 0 则不交付 | 以口径表为准回改 |

## 7. 必要的工具能力与技术接口

| 能力 | 用途 | 本产品实现方式 |
|------|------|----------------|
| 团队编排 | 多席位并行与串行 | Agent Team：`TeamCreate` + `SendMessage` 中转 |
| 文件读写 | 落盘与目录管理 | 标准文件工具，`mkdir -p` 后写入 |
| 结构化计算 | 分级、装箱、口径、断链 | 5 个 Python 标准库脚本 |
| 联网检索 | 竞品与行业公开信息 | 由运行环境提供，本包不内置，不硬依赖 |
| 数据读取 | 读取用户提供的 CSV/表格 | 脚本以 CSV 为标准输入格式 |

**接口约定**：所有脚本以 CSV 为输入、以 stdout 文本或 `--json` 为输出、以退出码表达结论（0 通过 / 1 阻断）。这套约定使脚本可被其他自动化流程直接调用。

## 8. 功能需求（对产品本身）

| 编号 | 需求 | 优先级 | 验收标准 |
|------|------|--------|----------|
| FR-01 | 主理人能按六段链编排四个席位，跨席位信息经其中转 | P0 | 任一任务执行中，四个席位均收到过至少一次独立任务；主理人不代写专业产出 |
| FR-02 | 每条事实性陈述必须带 EVD 编号与等级 | P0 | `evidence_grade.py` 对无来源条目返回退出码 1 |
| FR-03 | 需求规格九节齐全，每条 REQ 至少 1 条可测 AC | P0 | `spec_lint.py` 对缺章节/缺 AC 返回退出码 1 |
| FR-04 | 排产按人周装箱并输出砍单清单与止损线 | P0 | `capacity_pack.py` 在 P0 装不下时返回退出码 1 并列出原因 |
| FR-05 | 指标必须先定口径，比率类必须有分子分母与护栏 | P0 | `metric_check.py --cards` 对缺分母返回退出码 1 |
| FR-06 | 能识别整体与分层方向相反的辛普森反转 | P1 | `metric_check.py --segments` 对构造的反转数据返回退出码 1 |
| FR-07 | 交付前完成跨文档一致性校验 | P0 | `chain_check.py` 对断链样例报出 C1/C2/C3/C5/C7/C8 六类错误 |
| FR-08 | 同一结论能改写为三种受众版本且数字一致 | P1 | 三版文档中同一 MET 目标值相同，`chain_check.py` C8 不报警 |
| FR-09 | 交付物落盘到固定目录，命名即阅读顺序 | P0 | 目录内文件前缀为 00/01/02/03/04/05/99，缺任一即视为未完成 |
| FR-10 | 闸门记录可审计 | P1 | `meta.json` 含 `gates` 字段，记录四道闸的通过时间与结论 |

## 9. 非功能需求

| 维度 | 要求 | 实现情况 |
|------|------|----------|
| **质量** | 输出中不得出现无出处的数字；不得出现不可测的验收标准 | 由 G2/G3 与脚本强制 |
| **质量** | 同一数字在不同文档中必须一致 | `chain_check.py` C8 |
| **速度** | 单席位产出应在一次会话内完成，不跨轮等待 | 每个席位 maxTurns=60，主理人 200 |
| **速度** | 脚本单次运行 < 2 秒（千行级数据） | 实测均 < 0.3 秒（见测试报告） |
| **稳定性** | 脚本零第三方依赖，离线可运行 | 纯标准库 |
| **稳定性** | 输入缺失时停下来问，不编造 | 写入各 Agent 的拒绝清单 |
| **可维护** | 规则集中在 Skill 文档，改规则不改代码 | 判断规则与脚本分离 |
| **兼容** | 不依赖特定模型版本或联网服务 | 无外部调用 |

## 10. 与目标能力的对应关系

本产品在功能上覆盖了"产品战略团队"类工具的通用能力，并针对常见缺口做了补充。差异点如下（不含任何被参考方的文案或代码）：

| 通用能力 | 本产品做法 | 补充点 |
|----------|------------|--------|
| 需求规格撰写 | 九节结构 + 编号 + 脚本校验 | 增加"依据"列强制挂 EVD；增加范围台账 |
| 用户研究综合 | 证据分级 + 假设清单 | 增加"若不成立会怎样"与取证成本估算 |
| 竞品分析 | 只采公开可核实信息 + 抓取日期 | 明确"未见公开说明 ≠ 无"；宣传语最高 C 级 |
| 指标评审 | 口径卡 + 护栏 + 辛普森检查 | 增加分母变化 10% 阈值与波动带概念 |
| 路线图规划 | 人周装箱 + 砍单清单 + 止损线 | 用装箱替代分数排序；增加承诺率区间判断 |
| 头脑风暴 | 未作为独立工作流 | 收敛进 S1 立案与 S3 需求池，避免"发散完没人收" |
| 干系人沟通 | 三版改写 + 数字一致性校验 | 增加"失败态必须写"与"必须有决策项" |

**未覆盖的能力（明确的 Non-goals）**：

- 不提供竞品数据库或实时市场数据
- 不替代用户研究执行（不代跑访谈、不发问卷）
- 不做 UI 设计稿
- 不做财务建模与估值
- 不提供法律意见
