# 需求规格（Spec Architect）

## 什么叫合格的规格

一个没参会、不认识用户的工程师，只靠这份文档，能做出正确的东西，并且知道什么不该做。

不满足这条，写多长都没用。

## 九节结构

1. 一句话定义
2. 目标（≤3 条，正交，带成功判据与依据）
3. 用户与场景（3–5 个，写"现在怎么凑合"）
4. 需求池（REQ 编号 + 优先级 + 依赖 + 依据 + 状态）
5. 验收标准（每条 REQ ≥1 条 AC）
6. 边界与非目标（≥3 条，每条写"什么条件下重新考虑"）
7. 约束与假设
8. 开放问题（谁决定、什么时候定）
9. 范围台账（新增必伴随被挤掉的）

## 验收标准写法

**合格**：
```
Given 用户在导出页选择了超过 50000 行的时间范围
When 点击「开始导出」
Then 页面显示进度条与"预计剩余 X 秒"，且 X 在任务开始 10 秒内出现
```

**不合格**：
```
导出要快、要流畅、体验要好
```

判定标准：把 AC 交给一个没写过这段代码的测试同学，他能不能设计出通过/不通过的用例。不能，就是不合格。

## 优先级规则

- **P0**：不做则目标不成立（不是"很重要"，是"不成立"）
- **P1**：影响主路径效率，可短期降级运行
- **P2**：增强，砍掉不影响目标
- P0 数量 ≤ 本期可交付项的一半。全 P0 = 没优先级。

## 范围控制

- 加一条需求 → 必须指出被挤掉的是什么（范围/时间/质量）
- 砍掉的需求保留编号，状态改 `deferred`，写原因
- 每次定稿前自查：所有 REQ 是否服务于 GOAL

## 脚本校验

```
python scripts/spec_lint.py <02-需求规格.md>
```

检查项：
- 九节是否齐全
- 每个 REQ 是否有 AC，AC 是否含可观测判据（Given/When/Then 或 `- [ ]`）
- REQ 编号是否重复、AC 是否挂在不存在的 REQ 上
- 是否残留占位符（待补充/TBD/XXX/…）
- Non-goals 是否 ≥3 条
- 是否出现不可测形容词（流畅/友好/快速/强大）而无数值
- P0 占比是否超过 50%

退出码非 0 = 有阻断项，不许交付。

## 反模式

- 把实现方案写进规格（那是工程的活）
- 用"具体交互由设计决定"回避边界情况
- 验收标准写成功能列表（功能列表不是验收）
- 每条需求都"依据：用户反馈"（没有 EVD 编号等于没依据）
