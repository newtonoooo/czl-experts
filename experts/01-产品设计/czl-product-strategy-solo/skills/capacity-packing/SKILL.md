# 产能装箱（Capacity Packing）

## 为什么不用 RICE 分数排序

分数能告诉你谁排前面，不能告诉你**装得下几个**。团队 43 人周的产能，你给 11 个需求打完整数，第 6 名之后全是幻觉。

排序不花成本，装箱才花成本。所以这里只做一件事：把人周真的装进容器。

## 算法

```
理论人周 = 人数 × 周数
可用人周 = 理论人周 × 专注系数        # 默认 0.65；有历史实测用实测
缓冲     = 可用人周 × 0.15
可承诺   = 可用人周 − 缓冲             # 硬上限
```

专注系数怎么定：拿上季度"计划人周 / 实际交付人周"算。没有历史数据就用 0.65 并显式标注为假设。

## 装箱顺序

1. 依赖优先（上游先装）
2. P0 先装，同级按"每 0.5 人周对目标的贡献"排序
3. 单项 ≤ 可承诺的 40%，超过就切片
4. 装不下整条砍，不缩水工期
5. 每项写止损线

## 输出

`03-产能排产.csv` + `03-产能排产.md`（含产能测算表、装箱结果、砍单清单、超载冲突、关键路径）

## 承诺率

```
承诺率 = committed 人周 / 可承诺人周
```

- < 0.60：排太松，浪费产能，说明要么需求没想清，要么估算虚高
- 0.75–0.85：健康
- > 0.85：无余量，任何线上问题都会击穿交付日，标高风险

## 砍单清单怎么写才不是甩锅

不合格：
```
REQ-07 自定义模板 —— 资源不足，延期
```

合格：
```
REQ-07 自定义模板（原 P1，4 人周）
砍掉后失去：3 个大客户提过，销售 Q4 无法承诺定制能力
何时回来：Q1 若 RM-01 交付后剩余 ≥5 人周
怎么交代：给提出方一个可验证的替代——本期提供 5 套预置模板，覆盖 80% 场景
```

## 脚本

```
python scripts/capacity_pack.py --backlog <backlog.csv> --people 6 --weeks 13 [--focus 0.65] [--buffer 0.15] [--json]
```

backlog.csv 字段：`id,req_id,title,pw,priority,depends_on`

脚本会做：产能测算、依赖拓扑排序、装箱、承诺率、超载告警、砍单清单，并检测"依赖指向被砍项"这种隐性断链。

## 反模式

- 用"加加班"消化缺口（加班不是产能，是借款）
- 把 P0 全塞进去再写"有一定风险"
- 估算按"最理想情况"给（那叫愿望，不叫估算）
- 排产表里没有止损线（等于没有退出机制）
