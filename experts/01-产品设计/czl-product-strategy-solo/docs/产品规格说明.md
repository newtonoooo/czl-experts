## 1. 产品定位

一个**单专家形态的产品决策产出系统**。

与团队版的区别不在能力清单，在**协作形态**：团队版用 5 个 Agent 分工，本产品用 1 个 Agent 顺序轮换 5 顶帽子。交付物结构、编号体系、闸门规则、校验脚本完全相同。

判断标准：这份决策包拿进会议室，会不会被一个认真的人一句话问倒。

### 1.1 它是什么

- 把模糊诉求压成可立项的题目（帽 A 立案）
- 把每条结论钉到出处上，并附一条反证（帽 B 取据）
- 把需求写成可施工、可验收的规格（帽 C 成文）
- 把计划装进真实人周并写清砍掉什么（帽 D 排产）
- 把成功定义成可计算的指标（帽 E 度量）
- 交付前把五份文档对齐，写出三条最强否决理由（帽 F 汇报）

### 1.2 它不是什么

- 不是"一键生成 PRD"的模板填充器
- 不是竞品数据库（不内置任何竞品资料）
- 不是 BI 工具（不连接数据仓库）
- 不是法律/财务/投资意见提供者
- 不是团队版的替代品——重大不可逆决策仍建议交叉审

## 2. 目标用户

| 用户 | 典型处境 | 为什么选单人版而不是团队版 |
|------|----------|---------------------------|
| **独立产品经理** | 一个人负责一条产品线，没有团队可商量 | 不需要协调成本，开箱即用 |
| **创业公司创始人** | 兼产品，决策快，但容易自己骗自己 | 有强制反证与红队段落兜底 |
| **业务/运营转产品** | 会写方案不会写验收 | 九节结构与脚本校验把标准固定住 |
| **需要快速出包的人** | 明天就要开会，等不了多 Agent 编排 | 单上下文连续执行，无中转开销 |
| **独立开发者 / 一人公司** | 判断一个功能值不值得做 | 立案卡档位判定 + 最低成本取证动作 |

## 3. 使用场景

### 场景 A：明天就要交方案

**输入**：一句话诉求 + 若干客户反馈截图
**过程**：帽 A 立案 → 帽 B 取证（多数为 D 级）→ 帽 C 规格 → 帽 D 排产 → 帽 E 口径 → 帽 F 汇报
**输出**：一套完整决策包，首页标明"基于假设，取证后需重算"
**判定成功**：会上没人问"这个数字哪来的"

### 场景 B：季度排产被质疑

**输入**：11 个候选需求、6 人、13 周
**输出**：committed 清单 + 砍单清单（含交代话术）+ 承诺率 + 每项止损线
**判定成功**：能当场答出"为什么这 5 件、不是那 6 件"

### 场景 C：指标异常复盘

**输入**：两期数据、口径说明、分群数据
**输出**：口径卡 + 分母检查 + 辛普森反转检查 + 可检验归因假设
**判定成功**：给出的解释带"若 X 成立应观察到 Y"

### 场景 D：竞品突然上线同类功能

**输入**：竞品公开页面、定价、自家成本结构
**输出**：证据台账（标抓取日期）+ 差异化判断 + 两季动作 + 停止条件
**判定成功**：结论里同时有"打哪里"和"什么情况下不打"

## 4. 五顶帽子协议（本产品的核心机制）

| 帽 | 岗位 | 输入 | 动作 | 判断 | 产出 |
|----|------|------|------|------|------|
| A | 立案官 | 用户诉求 | 五要素填空 + 档位判定 | 待确认 ≥2 则停 | `00-立案卡.md` |
| B | 证据官 | 立案卡 | 拆问题 → 找源 → 判级 → 写反证 | 无 EVD 编号不进后续 | `01-证据台账.csv/.md` |
| C | 需求架构师 | 立案卡 + 台账 | 九节规格 + REQ/AC 编号 | AC 不可测则不通过 | `02-需求规格.md` |
| D | 产能规划师 | 规格 + 人数周期 | 人周测算 + 装箱 + 砍单 | P0 装不下则阻断 | `03-产能排产.csv/.md` |
| E | 指标口径师 | 成功判据 + 排产 | 口径卡 + 护栏 | 比率缺分母则退回 | `04-指标口径表.md` |
| F | 参谋本人 | 全部文件 | 三版汇报 + 一致性校验 + 红队段落 | 脚本 error > 0 不交付 | `05-汇报包.md` 等 |

### 4.1 换帽铁律（替代"另一个人来审你"）

| # | 规则 | 作用 |
|---|------|------|
| 1 | **文件隔离**：换帽前上一帽产出必须落盘，下一帽只读文件 | 防止"我记得我说过"被当证据 |
| 2 | **换帽标记**：每次换帽写 `meta.json` 的 `hats` 记录 | 让过程可审计 |
| 3 | **反证义务**：每条 A/B 级结论写一条"什么数据能推翻它"，写不出降 C | 替代外部质疑 |
| 4 | **数字双录**：同一关键数字在两帽独立写一次，由 C8 比对 | 抓"拍脑袋"的数字 |
| 5 | **脚本裁决**：自评分歧以脚本为准 | 防止自我宽容 |

### 4.2 单人自审三对冲（帽 F 必写）

1. **红队段落**：三条最强否决理由，每条附"什么数据能证实它"
2. **数字对账表**：所有关键数字及其出现位置，不一致的必须解释
3. **假设暴露清单**：所有 D/X 级假设，每条写"若不成立哪些结论会塌"

## 5. 功能需求（对产品本身）

| 编号 | 需求 | 优先级 | 验收标准 |
|------|------|--------|----------|
| FR-01 | 单 Agent 按 A→F 顺序完成六段链，每帽产出独立落盘 | P0 | 交付目录含 8 类文件，缺任一视为未完成 |
| FR-02 | 换帽记录可审计 | P1 | `meta.json` 含 `hats` 数组，每项含 hat/inputs/outputs |
| FR-03 | 每条事实性陈述带 EVD 编号与等级，且 A/B 级有反证候选 | P0 | `evidence_grade.py` 对无来源条目返回退出码 1 |
| FR-04 | 需求规格九节齐全，每条 REQ ≥1 条可测 AC | P0 | `spec_lint.py` 对缺章节/缺 AC 返回退出码 1 |
| FR-05 | 排产按人周装箱，输出砍单清单与止损线 | P0 | `capacity_pack.py` 在 P0 装不下时返回退出码 1 |
| FR-06 | 指标先定口径，比率类必须有分子分母与护栏 | P0 | `metric_check.py --cards` 对缺分母返回退出码 1 |
| FR-07 | 能识别整体与分层方向相反的辛普森反转 | P1 | `metric_check.py --segments` 对反转数据返回退出码 1 |
| FR-08 | 交付前完成跨文档一致性校验 | P0 | `chain_check.py` 对断链样例报出 C1/C2/C3/C5/C7/C8 |
| FR-09 | 决策简报必须含三条最强否决理由 | P0 | 结构检查项：`00-决策简报.md` 含"否决"段落 |
| FR-10 | 单专家形态不得含 teamInfo/members 字段 | P0 | `tests/run_tests.py` 校验通过 |

## 6. 非功能需求

| 维度 | 要求 | 实现情况 |
|------|------|----------|
| 质量 | 不得出现无出处数字、不可测验收 | 由 G2/G3 与脚本强制 |
| 质量 | 同一数字在不同文档一致 | `chain_check.py` C8 |
| 速度 | 无跨 Agent 编排开销，单轮内推进 | 单 Agent，maxTurns=120 |
| 速度 | 脚本单次运行 < 2 秒（千行级） | 实测 0.37–0.41 秒（含解释器启动） |
| 稳定性 | 零第三方依赖，离线可运行 | 纯标准库 |
| 稳定性 | 输入缺失时停下来问，不编造 | 写入拒绝清单 |
| 可维护 | 规则在 Skill 文档，改规则不改代码 | 判断与实现分离 |
| 兼容 | 不依赖特定模型版本或联网服务 | 无外部调用 |

## 7. 与团队版的取舍（诚实说明）

| 维度 | 团队版 | 单人版 | 取舍 |
|------|--------|--------|------|
| 速度 | 慢（编排 + 中转） | 快 | 单人胜 |
| 对抗性 | 强（别人审你） | 中（自己审自己，靠三对冲） | 团队胜 |
| 上下文一致性 | 需靠文件同步 | 天然一致 | 单人胜 |
| 并行取证 | 可并行 | 串行 | 团队胜 |
| 成本 | 5 个 Agent 的 token | 1 个 | 单人胜 |
| 适用 | 大额、不可逆、需交叉验证 | 日常、快速、单人负责 | 按场景选 |

**结论**：单人版不是团队版的降级版，是**不同场景的另一种形态**。日常出包用单人，重大决策用团队。
