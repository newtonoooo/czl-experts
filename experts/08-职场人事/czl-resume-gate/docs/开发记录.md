## 一、起点与边界

**起点**：接到需求——做一个简历优化类专家，公开发布并商业化。

**边界**（明确写下来，避免过程中走偏）：

1. 目标专家目录**只读**，用于功能观察，不复制其文件、不纳入其代码或提示词。
2. 现有专家的版权状态未知（其 README 提及源自某开源仓库的 clawbot skill，但未提供许可文件）。**不确定就不使用**。
3. 不复用其头像、宣传文案、品牌名。
4. 新包放独立目录，不覆盖任何原文件。

**执行**：全过程只对目标目录执行了 `find`、`ls`、`cat`（读 plugin.json / README / agents/*.md），未做任何写入。

## 二、设计决策（按发生顺序）

### D1 差异化的切入点

市面上的简历工具都在做"评分 + 润色 + 定制 + 导出"四件事。照抄这四件事没有产品意义，只能靠文案区分。

找差异时问了一个问题：**简历为什么会被淘汰？** 答案不是"写得不好"，而是三次不同性质的筛选：

- 机器只看能不能解析；
- 人眼只看六秒能不能抓到重点；
- 面试官只看能不能被追问。

于是把评分从"简历的组成"（内容/结构/语言/ATS/影响力）改成"谁在筛"（机器/人眼/面试官），分值 30/40/30。**这是本产品的骨架，其余设计都从这里长出来。**

### D2 分数怎么用

既然分数是模型打的，两次评分之间的差就没有客观意义。所以明确规定：**分数只用于排优先级，禁止向用户承诺"从 62 提到 88"**，报告里改成"致命项从 3 条降到 0 条"。

### D3 重写框架为什么不用 STAR

STAR 是面试叙事框架，用在简历的一句话上会撑不住（一条要点写不下情境+任务+行动+结果）。改用 AORE 四格：动作—对象—结果—**证据**。

关键在第四格。市面上的改写建议通常到"结果"就停，结果是"提升了 30%"这种没有口径的数字。加一格"证据"（归属 + 口径），专门治两个高频病：数字没来由、团队成果写成个人成果。

### D4 数据缺口的三级处理

最容易出问题的地方：用户说"记不清了"，模型顺手编一个"合理"的数。这会让人在面试第三轮、背调、试用期汇报时崩掉。

定三级规则：**事实 / 推演 / 待补**。推演只允许用"份额、比例、范围、周期"这类结构量（团队 6 人我负责 2 个模块 → 1/3 模块），**禁止推效果量**（增长多少、省了多少钱）。推不出来就写 `【待补：…】`，并给一条退路（用规模替代效果）。

### D5 为什么自己写 .docx 生成器

导出是刚需，但 python-docx 需安装、pandoc 需外部程序。测试环境里 pip 无网络，装不上；即便装上，多一个依赖就多一个商业分发时的许可确认成本。

于是直接用 `zipfile` 拼 OOXML：`[Content_Types].xml` + `_rels/.rels` + `document.xml` + `styles.xml` + `docProps/*`。约 250 行，零依赖。

顺带做了两个 ATS 友好的决定：项目符号用 `•` + 悬挂缩进而不是 Word 自动编号（复制或解析时不丢），表格拍平成单列（表格是解析重灾区）。

### D6 词表匹配的边界写进报告

`jd_match.py` 只能判断"写了没写"。测试中弱简历因为技能栏罗列了 SQL/Python/Tableau，匹配度 60%，强简历 68%——差距远小于真实水平差距。

没有去掩盖这个缺陷，而是在报告顶部固定写一句提示，并在测试报告里如实记录。**工具的能力边界应该写在工具里，而不是靠使用者自己发现。**

### D7 输出纪律：一次最多 6 条

初期设计想过输出 40+ 项清单。否掉了：用户改不动。改成按严重度排前 6 条，每条带"证据 + 改法"，并规定致命项优先于总分。

## 四、开发期缺陷记录

真实修过的 7 个问题（测试报告第 4 节有详细表格），其中三个值得记下来当作经验：

1. **NFKC 归一化的连带伤害**：为了统一全角数字，对全文做了 NFKC，结果把全角 `｜` 转成了 `|`，导致"使用了表格"的误报。教训是：归一化只对需要归一化的字段做，不要整篇。
2. **数字拼接破坏边界**：先把全文数字抽出来拼成一个长串再找手机号，11 位窗口在长串里滑动，同一个号码被数出 5 次。教训是：正则要带着上下文匹配，不要先剥离再匹配。
3. **词表匹配里空格是隐形的敌人**："A/B 测试"和"a/b测试"在字符层面不同，多词术语（Power BI）同样。统一去掉空白后再比对，问题消失。
