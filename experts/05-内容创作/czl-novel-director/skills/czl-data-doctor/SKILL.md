# 诊断：追读漏斗与改稿工单

## 职责边界

只做一件事：把"数据不好"翻译成"第几章、哪个环节、怎么改"。

**不做**：不预测数据、不承诺改了就好、不建议刷量或调整发布时间来"优化指标"。

## 输入

必需：每章阅读数（第 1 章到当前章）。
可选：每章读完人数、单章字数、上架/推荐时间点。

三种来源都能接：
- 用户贴后台截图 → 手工录成 CSV
- 用户贴表格 → 转 CSV
- 用户口述"第一章一万二，第二章九千" → 录成 CSV

CSV 格式：

```
chapter,reads,finish
1,12480,7310
2,9021,5120
```

## 步骤

### 第 1 步：算

```bash
python skills/czl-data-doctor/scripts/funnel.py --csv data.csv --json-out qc/funnel.json
```

三个核心数：
- **相邻章追读率**：下一章阅读 / 本章阅读。这是"看完这章还想点下一章"的最直接代理。
- **首章留存**：第 N 章阅读 / 第 1 章阅读。看整本书的漏斗宽不宽。
- **完读率**：读完人数 / 阅读人数。有这项才能区分"没点开"和"点开没看完"。

### 第 2 步：定位

脚本按"低于中位数的缺口"排序给掉点。**取前三个，不要一次改十个。**

区分两种掉法：

| 形态 | 说明 | 先查哪 |
|---|---|---|
| 单章断崖（一章掉 20% 以上，前后正常） | 这一章本身出了问题 | 该章开头三段、该章是否换了视角/时间线、是否有大段设定说明 |
| 连续缓降（每章掉一点，持续五章以上） | 不是某一章的问题，是结构问题 | 压力是否失效、矛盾是否升级、主角目标是否模糊 |
| 第一章就低 | 书名/简介/第一章不匹配 | 先查简介承诺与第一章实际内容的落差 |

### 第 3 步：归因（按章所在位置）

| 位置 | 典型原因 | 对应动作 |
|---|---|---|
| 第 1—3 章 | 没有具体异常、规则没兑现、主角被动 | 回 `czl-chapter-forge` 重排开篇三章 |
| 第 4—10 章 | 爽点兑现太慢、同一种打脸重复 | 加一次"预期落空"或换压力来源 |
| 第 11—30 章 | 支线跑偏、配角压主角、矛盾不升级 | 砍支线，把主角拉回主线 |
| 第 30 章以后 | 压力失效、目标丢失、伏笔不收 | 补一个"更大的对手"，或提前收两条伏笔 |

**归因必须落到可验证的东西**：不是"节奏有问题"，而是"第 7 章全章没有推进主线，主角在查一件与主线无关的事"。

### 第 4 步：出工单

工单五列，一行一个动作，不许写"优化节奏"这种不可执行的项：

| 章 | 位置 | 现在是什么问题 | 改成什么 | 验收标准 |
|---|---|---|---|---|
| 7 | 开头三段 | 主角醒来 + 环境描写，没有任何异常 | 直接从"他发现门锁被换过"开始 | 第一句出现具体异常 |
| 7 | 中段 | 追查支线，与主线无关 | 砍掉，改为与主线对手正面接触 | 本章目标推进主线 |
| 8 | 章末 | 结尾是感慨 | 换成信息缺口式钩子 | 最后一句读者想知道答案 |

### 第 5 步：回灌

工单交给 `czl-chapter-forge` 执行改稿，改完走 `czl-voice-tune` 体检，再 `czl-continuity-keeper` 重新入档。**工单不许只出不做。**

## 判断条件

| 情况 | 处理 |
|---|---|
| 用户只给"追读掉了"，没有数据 | 要数据。给不出就说明无法定位，只能给通用体检（转 `czl-voice-tune`） |
| 数据只有 1—2 章 | 不够看趋势，明确说"样本不足"，只能对比首章留存 |
| 数据口径混用（一会儿人数一会儿次数） | 先统一口径再算，不统一就不算 |
| 掉点在第 1 章，且用户是新书 | 新书首章数据受推荐量影响，先排除曝光因素再归因 |
| 用户要求"帮我把数据做好看" | 拒绝。说明这只解释现象，不做数据包装 |

## 输出

```
qc/funnel.json      计算明细
07-诊断.md          掉点排序、归因、工单表
```

`07-诊断.md` 结构固定：

```
# 数据诊断（第 X—Y 章）
## 结论一句话
## 三个关键数（追读中位数 / 首章留存 / 完读率）
## 掉点排序
## 归因
## 改稿工单（表）
## 本次不改的部分（写明为什么不动，避免下次重复讨论）
```

## 异常处理

- **脚本算不出**（章数不足、格式不对）：回显脚本报错原文，让用户改数据格式，不猜。
- **用户数据跨越了断更期**：在报告里注明断更区间，该段数据不可比。
- **数据与"感觉"冲突**（用户觉得某章很好但掉得最狠）：以数据定位、以文本归因为准，两者都写进报告，不迁就感觉。

## 依赖

`scripts/funnel.py`（纯标准库）。演示数据见 `samples/funnel_demo.csv`。

## 与其他工作流的关系

上游：`czl-continuity-keeper`（章节清单与字数）。
下游：工单回到 `czl-chapter-forge`（改稿）与 `czl-voice-tune`（复检）。

## 脚本

两个脚本，分工不同：

| 脚本 | 管什么 | 输入 |
|---|---|---|
| `scripts/funnel.py` | 逐章漏斗：相邻章追读率、掉点排序 | 每章阅读数（CSV） |
| `scripts/rescue.py` | 整体指标：吸量/追读/完读/章均完读/时长分级 + 30 天表 | 一组指标值 |

```bash
python scripts/funnel.py --csv data.csv            # 先定位到章
python scripts/rescue.py --metrics 吸量=300,追读=28,完读=7 --track 都市 --plan 救书表.md
```

`rescue.py` 的 30 天表不是"每天都改"，而是**改一次、看一次**交替：定位→改→观察→改→观察→改结构→观察→补钩子→观察→复盘。改完不留观察期，数据动了也分不清是哪一处带来的。

**口径声明**：`rescue.py` 里的三档线是通用经验值，**不是任何平台的官方红线**。换平台先核对当期公示，再改 `--thresholds` 的 JSON。脚本只回答"哪一项最拖后腿、先后顺序怎么排"，不预测能不能上推荐。
