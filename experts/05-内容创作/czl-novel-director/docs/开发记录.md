## 1 开发路径

本次不是改造现有专家，是从需求侧重新建了一套东西。四条原则贯穿全程：

1. **只继承职责，不继承表达。** 参考了六个同类专家"做了哪些环节"，所有文案、提示词、工作流定义、文件命名全部重写。
2. **凡是能被数出来的，都交给脚本。** 这一点是六个竞品共同的缺口，也是本产品的位置。
3. **凡是不能被数出来的，明确写"交人工判断"，不假装有标准。**
4. **凡是无法确认权利的，一律不进包。** 参考包里的真实作者风格库、来源不明的句式库、二进制打包引擎，全部排除。

## 3 平台缺陷排查：专家图标不显示的原因

用户在把自制专家导入新的 WorkBuddy 后，选中专家时列表与对话头部的小图标不显示，退化成名字首字。逐层核对后确认有三条独立原因，其中两条是包本身可修的，一条是客户端行为。

### 3.1 头像路径在压缩包里找不到 → 退化成文字

客户端导入 zip 时，用 `resolveAvatarFromExpertZip(zip, 插件根目录, manifest.avatar)` 解析头像：

- `avatar` 以 `http(s):` 或 `data:` 开头 → 直接使用；
- 否则去掉开头的 `./` 与 `/`，按 `${插件根目录}/${相对路径}` 或 `${相对路径}` 两个候选去 zip 里查条目；
- 查到 → 转成 `data:image/png;base64,...` 内联；
- **查不到 → 直接把那个相对路径字符串原样当头像地址返回**（必然裂图，界面回退成首字）。

所以只要 zip 里多套了一层目录、大小写不一致、或文件根本没被打进去，图标就一定没有。

**本包的处理**：`avatar` 写 `avatars/expert.png`，zip 顶层就是插件根目录，条目名与字段逐字符一致，打包后单独校验（见 `docs/测试报告.md` T-07）。

### 3.2 文件不是真 PNG / 不是正方形 → 解码失败

扫描已安装专家时发现两个真实坏样本：

| 样本 | 实际情况 |
|---|---|
| `wechat-miniprogram-expert/avatars/expert.png` | 文件头 `FF D8 FF E0`，是 JPEG 改了扩展名 |
| `wechat-viral-writer/avatars/expert.png` | 346×348，非正方形 |

前者严格解码会失败；后者在方形裁切容器里会变形或被拒。

**本包的处理**：头 8 字节校验为 `89 50 4E 47 0D 0A 1A 0A`，尺寸 512×512，色彩类型 2（RGB 无 Alpha），位深 8。

### 3.3 本地专家的头像字段被写空 → 列表回退首字

这是客户端行为，不是包能改的。在应用包中可以读到这样的分支：

```
displayDescription: p.displayDescription ?? {...},
tags: p.tags ?? [],
avatar: '',                    // ← 本地自定义专家的兜底对象里，头像恒为空串
expertType: 'agent',
expertRootDir: undefined,
isCustomExpert: true,
marketplace: 'my-experts',
source: 'custom'
```

即：当一个专家被识别为"本地 my-experts、非云端同步"时，构造出的对象 `avatar` 为空字符串。列表渲染拿不到图，只能显示名字首字。另一条路径 `mapUserExpert` 用的是 `avatar: e.avatar ?? ''`——只有走云端同步、记录里带 avatar 的专家才有图。

**这条包无法绕过。** 能做的三件事：
1. 把 3.1、3.2 两条彻底做对，让"能读到图"的分支一定成功；
2. 头像体积压到 2.4 KB，避免 base64 内联后超出注册表字段长度；
3. 在 `docs/使用说明` 里写清：导入后在专家列表里若仍显示首字，属客户端本地专家头像未回填，不影响功能使用。

### 3.4 结论

| 现象 | 归属 | 能否由包解决 |
|---|---|---|
| 导入后图标变文字，且 zip 内有头像文件 | 客户端 `avatar:''` 兜底 | 否 |
| 导入后图标变文字，zip 内头像缺失或路径不符 | 打包方式 | 是，本包已保证 |
| 导入后图标裂图或变形 | 图片格式/尺寸 | 是，本包已保证 |

## 4 关键设计决策

### 4.1 为什么用七个 skill 而不是一个大 SKILL

参考包里最重的两个把全流程塞进单文件（1836 行、104 KB）。这样做的代价是：任何一次使用都要整篇载入，任何一处修改都要重新理解全文。

七个 skill 的切法按"产物"切，不按"话题"切——每段都以一个可交付文件收口，所以能单独加载、单独替换、单独测试。

### 4.2 为什么人味体检要出分数和等级

只给指标清单，用户不会看。给一个分数，用户会问"为什么是 62 分"；追问的时候，诊断就发生了。

分数只用于同一本书内部的横向比较，不用于跨书比较——这一点写进了 `czl-voice-tune` 的说明，避免用户拿分数当质量证明。

### 4.3 为什么"体检不过不许入档"要写成硬约束

参考包里确实写了大量"请检查"。其中番茄爆款更进一步，带了 22 个可执行脚本，质检还给退出码。但它们共同的做法是：**脚本跑完打印结果，结果不进任何共享状态。** 一旦某章跳过体检，后面每一章的对照基线都是脏的，而作者不会知道——因为没有东西记得"上一章到底过没过"。

这是本产品把判定写进 `state.json` 的理由：不是"我要比它有脚本"，而是"脚本的结论要留下来，并且能拦住下一步"。

把顺序写死：`写正文 → 体检出 json → commit 读 json → 不合格则 stale=true → lint 阻断`。四个脚本串成一条链，跳不过去。

### 4.4 为什么阈值可配置

不同题材的合理分布不同（战斗章短句多、心理章长句多）。阈值写死在代码里，用户第一次用就会觉得"这工具不懂我的书"。所以 `voice_scan.py` 支持 `--thresholds`，默认值写在一处，便于整体调整。

### 4.5 头像为什么换过两版

1.0.0 用的是代码渲染的几何标记（七道递增竖条）。当时的理由是规避生成图角标、格式精确可控。

1.1.0 改回虚拟人物插画，原因是产品定位问题：**这个专家的价值是"有人在替你把关"，不是一个抽象符号。** 图标是用户对"谁在干活"的第一印象，几何图形传达不出"有人"，只会被读成一个统计报表的图标。

改版后仍保留 1.0.0 的两条原则：角标必须裁掉、尺寸与体积必须精确可控。实现方式从"自己画"改成"生成 + 纯标准库处理"（`tools/png_tool.py`），处理链每一步都可复现。详见第七节。

## 7 头像：规格、处理链与合规

### 7.1 规格核对

平台规范与本人既定口径（见 `czl-draft-qc` 项目风险清单 R6，2026-10-26 核实）：

| 项 | 要求 | 本包实测 |
|---|---|---|
| 边长 | 512×512 | 512×512 |
| 格式 | PNG | 真 PNG，魔数 `89 50 4E 47 0D 0A 1A 0A` |
| 色彩类型 | — | 2（RGB 无 Alpha） |
| 体积 | ≤ 500 KB | 213 KB（base64 后约 284 KB） |
| 包体 | ≤ 20 MB | 99 KB |
| zip 首层 | 须为专家目录 | 唯一顶层目录 `czl-novel-director/` |
| 生成工具角标 | 须裁去并披露 | 已裁去；README / LICENSE / 平台展示文案三处披露 |

### 7.2 处理链（三步，全部可复现）

```
生成 1024×1024
  → 裁剪 (40,0,980,940) 940×940，去掉右下角工具角标
  → 面积平均缩放至 512×512
  → 每通道保留 6 位（降熵压缩，肉眼不可见）
  → 编码为 RGB PNG，zlib level 9
```

对应命令：

```bash
python tools/png_tool.py resize <母图.png> avatars/expert.png \
  --box 40,0,980,940 --size 512 --posterize 6
```

三档降色实测：不降色 455 KB → 6 位 213 KB → 5 位 135 KB。取 6 位，因为 5 位时深色外套与背景交界处开始出现可见色阶断层。

### 7.3 为什么体积要压到 300 KB 以内

客户端导入 zip 时会把头像转成 `data:image/png;base64,...` 内联（见第 3 节）。455 KB 的图转出来约 607 KB 的字符串，写进注册表字段有长度风险，也会拖慢导入。压到 213 KB 后 data URL 约 284 KB，落在安全区。

### 7.4 母图留档

1024 原图存于 `src-assets/`，**不随包分发**（`tools/build.py` 排除该目录）。作用是创作过程证据：能证明 512 版本是从更大尺寸处理来的，而非直接下载或改色。

### 7.5 形象设计说明

| 要素 | 取值 | 理由 |
|---|---|---|
| 人物 | 二十八岁左右女性编审 | 与既有产品「朱笔」（男性编辑）区分，避免同一作者的多个专家撞脸 |
| 神态 | 平静、专注、不笑 | "不废话"的状态，不是"亲切" |
| 服装 | 暖白高领 + 深墨蓝立领外套 | 无西装、无老花镜、无稿纸堆——刻意避开"资深"的刻板符号 |
| 道具 | 平板（屏上是上升折线）+ 一叠散开稿纸 + 胸前朱红钢笔 | 三件分别对应"看数据""看稿子""改稿"，正好是产品的前中后段 |
| 配色 | 暖白 / 深墨蓝 / 朱红 | 与产品文档配色一致；朱红是唯一强调色，停在钢笔与折线上 |
| 背景 | 纯深墨蓝 + 极淡网格 | 小尺寸下不抢人，网格暗示"结构" |

**没有做的事**：没有加皱纹、没有加银发、没有加眼镜、没有用西装领带。这几样是"资深"最省事的表达，也是最容易变成"疲惫"的表达。

## 8 平台清单校验：上传被拒后反推出的三条硬规则

1.2.0 上传时被校验器拒绝，报两条：`tags 须固定 3 个，当前 4 个`、`defaultInitPrompt.en 必须与 quickPrompts[0].en 一致`。

拿本地 61 个已上架专家的 `plugin.json` 做统计，规则比报错里写的更严：

| 字段 | 实测分布 | 结论 |
|---|---|---|
| `tags` | 0 个（5 个样本）或 **3 个**（56 个样本），无其他取值 | 固定 3 个 |
| `tags[].zh` 长度 | 2—8 字 | 标签要短 |
| `quickPrompts` | 0 个（5 个）或 **3 个**（55 个），仅 1 个样本为 6 | 固定 3 个（报错里没提，但同样会拦） |
| `quickPrompts[].zh` 长度 | 8—138 字 | 太短不像指令，太长卡片显示不全 |
| `defaultInitPrompt` vs `quickPrompts[0]` | **56/56 完全一致**，零例外 | 不是"意思相同"，是逐字符相同 |

所以 1.2.0 的两处违规实为三处（tags 4 个、quickPrompts 4 个、默认提示与首条措辞不同：一处写 `First tell me`、一处写 `First check`）。

修法：`defaultInitPrompt` 直接由 `quickPrompts[0]` 赋值，不再手写第二份文案——**两份文案就一定会有分歧，这是结构问题，不是手误**。同时把这条写进 `tools/selftest.py` 的 T-20，以后改清单先跑自检，不等平台报错。

**教训**：平台校验器的报错是逐条返回的，报两条不等于只有两条。拿已上架样本反推约束，比逐次试错快得多。
