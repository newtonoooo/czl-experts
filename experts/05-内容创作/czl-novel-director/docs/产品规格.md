## 一、目标用户与实际使用场景

| 用户 | 真实场景 | 现在怎么做 | 卡在哪 |
|---|---|---|---|
| 想开书的网文新人 | 有脑洞，不知道能不能写、写什么 | 翻攻略、看别人的书 | 选题靠感觉，前三章写完没人告诉他对不对 |
| 已签约的连载作者 | 日更 4000—6000 字，写到三四十章开始乱 | 自己建 Excel 记人物 | 称号、时间线、伏笔一多就吃书，读者在评论区抓错 |
| 数据下滑的中段作者 | 追读掉了，编辑说"节奏问题" | 到处问人 | 不知道具体哪一章哪一段要改 |
| 完本/切书后想重开的人 | 旧稿 20 万字，想接着写或重写 | 重读一遍旧稿 | 上下文太长，模型记不住，接上去人设就变了 |
| 短篇/短剧投稿者 | 想写盐选、短剧剧本 | 参照别人的爆款 | 结构改不像，节奏拖 |

**共同点：他们不缺"怎么写"的道理，缺"我这稿子现在到底哪儿不对、下一步动哪里"。**

## 二、要解决的问题（按优先级）

1. **规则不可验收**：知道"别写太工整"，但不知道自己的稿子工整到什么程度。→ 需要跑一遍就出数字的体检。
2. **长篇必漂移**：人物称号、能力上限、时间线、伏笔到期，靠记忆必然出错。→ 需要可校验的档案。
3. **重入困难**：隔几天回来接不上。→ 需要一句话回答"写到哪、欠什么、下一步"。
4. **数据与正文两张皮**：知道追读率低，不知道改哪一段。→ 需要把指标落成工单。
5. **开篇试错成本高**：前三章决定生死，但没有低成本的候选比较机制。→ 需要"三个开篇方案 + 判定表"而不是一稿定生死。

## 三、必要输入与预期输出

### 输入（最小可用）
- 一句话方向即可开写（如"末世女主，不要感情线"）。
- 更好：题材 / 平台 / 篇幅 / 视角 / 基调 / 禁忌 / 交付形态 七项里给到 3 项以上。

### 输出（按任务形态）

| 任务 | 交付物 | 存放位置 |
|---|---|---|
| 选题定位 | 赛道判断 + 3 个卖点命题 + 书名候选（含判定理由） | `01-定位.md` |
| 故事架构 | 世界观规则表、人物卡、大纲（卷—章两级）、开篇三章设计 | `02-架构.md` |
| 章节正文 | 每章一个 md，附写作包与体检结果 | `chapters/ch-XXX.md` |
| 人味体检 | 指标表 + 逐条定位到句的修改清单 | 控制台输出 + `qc/` |
| 连续性台账 | `state.json` + 伏笔表 + 人物称号表 | `.nproj/` |
| 数据诊断 | 漏斗拆解 + 归因 + 改稿工单 | `07-诊断.md` |
| 投稿交付 | 简介三版、标签、样章、全本汇编 | `export/` |

## 四、通用处理步骤（全流程）

七个阶段，每个阶段有明确入口、产物和放行条件：

```
① 侦察 market-scout      赛道 / 读者 / 卖点 / 书名
        ↓ 放行：卖点命题一句话说得清
② 架构 story-architect   世界观规则 / 人物 / 金手指约束 / 卷章大纲 / 开篇三章
        ↓ 放行：每条规则可判定、每个伏笔有到期章
③ 铸造 chapter-forge     写作包 → 正文 → 章末钩子
        ↓ 放行：本章目标达成 + 钩子落地
④ 调音 voice-tune        人味体检 → 定位到句 → 改
        ↓ 放行：体检指标全部在阈值内
⑤ 台账 continuity-keeper 提交正文、登记事实、更新伏笔与时间线
        ↓ 放行：档案无冲突，状态文件可重入
⑥ 诊断 data-doctor       追读/完读漏斗 → 归因 → 工单（有数据才走）
        ↓ 放行：工单能落到具体章
⑦ 交付 delivery-pack     简介 / 标签 / 样章 / 导出 / 短剧改编
```

**关键设计：④ 和 ⑤ 是强制回边。** 任何一章正文写完，必须先过体检再入档；入档后若体检发现新问题，档案标记为"待复核"，不允许继续写下一章。

需要说清的是：**"有脚本"这件事不是本产品的独有优势**，同组里番茄爆款带 22 个脚本，质检、节奏、钩子、数据看板都能跑。本产品的差异不在"有没有检查"，而在**检查结果进不进账本、能不能拦住下一步、阈值能不能整体校准**。这三条见第八节。

**分支路径**
- 只想要开篇：① → ② → ③（前三章）
- 旧稿接管：⑤ 先重建档案 → ⑥ 诊断 → ③ 续写
- 只改稿：④ 单跑，不建档
- 只想聊设定：② 只读，不写文件

## 五、工具能力与技术接口

| 能力 | 实现 | 说明 |
|---|---|---|
| 文件读写 | 宿主 Read / Write / Edit | 全部落盘为 UTF-8 Markdown 与 JSON |
| 项目档案 | `skills/czl-continuity-keeper/scripts/nproj.py` | 纯标准库，无第三方依赖，可离线 |
| 文本体检 | `skills/czl-voice-tune/scripts/voice_scan.py` | 纯标准库，确定性输出，同稿两次结果一致 |
| 结构核查 | `skills/czl-continuity-keeper/scripts/lint_project.py` | 检查缺章、伏笔到期、称号漂移、字数区间 |
| 数据核算 | `skills/czl-data-doctor/scripts/funnel.py` | 由章阅读数算追读率/完读率，不联网 |
| 联网取材 | 宿主 WebSearch | 仅在 ① 赛道侦察与 ⑦ 平台规则核对时使用，可用则用，不可用则降级为"标注未核实" |

**不依赖**：任何 MCP、任何 pip 包、任何外部 API。Python 3.9+ 标准库即可。

## 六、质量、速度、稳定性要求

| 维度 | 要求 | 怎么保证 |
|---|---|---|
| 质量 | 交付的正文必须过体检；不得把"大纲"当正文交付 | ④ 强制回边 + 字数由脚本实数，不由模型自报 |
| 质量 | 长篇不漂移 | ⑤ 台账 + lint 脚本，冲突即阻断 |
| 速度 | 单章交付不超过一次对话轮次内完成 | 上下文按需加载，不整库读入；参考文件按阶段拆到各 skill |
| 速度 | 不重复问已知信息 | 缺省值写进定位文件"当前假设"，直接开工 |
| 稳定性 | 无 Python 时降级 | 交付可复制的正文 + 结构化交接包，明确标注"未落盘/字数未核" |
| 稳定性 | 脚本失败不静默 | 报错原文回显，不把失败标成通过 |
| 可维护 | 单个 skill 可独立替换 | 七个 skill 各自闭环，互不 import |

## 七、明确不做

- 不做真实作者风格模仿（姓名权 + 实质性相似风险）。
- 不做"保证爆款/保证签约/保证过审"的承诺。
- 不做自动投稿、自动刷榜、模拟读者刷数据。
- 不做封面生成（可给要求清单，出图交给平台工具）。
- 不内嵌任何第三方作品的语料、句式库、风格库。

## 八、与现有专家的机制层差异（含劣势）

### 8.1 机制对照（2026-10-29 二次核对后修正）

初版这张表把爽文专家写成"无门禁、无缺章检测、无伏笔到期"，是错的。核对其 `novel_project.py` 第 116–117 行有 `require(review.passed is True)` 与 `blockers == []`，其项目协议也写明"首次缺章处给 gap""next_chapter 取最早待修/缺失章节"、终审"阻止缺章、过期链、核心伏笔未解决"。**在"门禁 + 台账"这条路上，它是走得最远的竞品，本产品不是首创。**

修正后的真实对照：

| 机制 | 网文主编 | 长篇总编 | 番茄爆款 | 爽文专家 | 本产品 |
|---|---|---|---|---|---|
| 可执行脚本 | 1（加密+依赖 jieba） | 0 | **22** | 1 | 8 |
| 统一状态文件 | 无 | 有 | 无 | 有 | 有 |
| 判定结果写回状态 | 无 | 部分 | 无 | **有**（模型填写 review.passed） | 有（脚本计算 verdict） |
| 判定阻断下一步 | 无 | 无 | 无 | **有**（commit 前 require） | 有（commit 读报告 + lint 阻断） |
| 跨章项目级核查 | 无 | 部分 | 无（单文件） | **有**（缺章 gap、依赖链、终审） | 有（7 项，多出称号漂移与磁盘一致性） |
| 伏笔到期制 | 无到期章 | 有承诺账本 | 有台账骨架 | **有**（due_chapter + 终审阻断） | 有，到期未收即阻断 |
| 判定由谁做出 | 模型 | 模型 | 脚本（阈值固定） | **模型自述** | **脚本计算** |
| 阈值外置可校准 | 无 | 无 | 仅总分线 | 无 | **有**（`--thresholds`） |
| 正负样本回归 | 无 | 无 | 无 | 无 | **有**（T-08 验证区分度与确定性） |
| 体检粒度 | 章级 | 章级 | 章级 / 整篇 | 段级（source_paragraph） | 段级 + 句级（含原文片段） |
| 明文可审计 | 否（pack 加密） | 是 | 是 | 是 | 是 |

### 8.2 真正的差异（2026-10-29 第四轮补齐后）

补齐动作见 8.4。补齐之后，差异仍是三条，但每一条都比之前硬：

1. **判定的来源：脚本算，还是模型自述。**
   现有产品里门禁最硬的是爽文专家，但它的 `review.passed` 由模型填写，协议自认"是声明不是自动评价"。本产品的 `verdict` 全部由脚本计数得出，同一份稿跑两次必须同分。

2. **阈值可校准、可回归，且样本不足时拒绝给建议。**
   新增 `calibrate.py`：正负样本各 3 份起，先算当前阈值的分离间隔，再逐项扫参**让间隔最大化**，输出可直接喂给体检脚本的 JSON。当前语料实测间隔 +28、准确率 100%，扫参后 +32。竞品的阈值写死在代码里，最多改一条总分线。

3. **体检与节奏都定位到章、段、句，且给原文片段。**
   番茄的节奏诊断到章级，爽文的审查到段级（`source_paragraph`），本产品的 `voice_scan` 到句并附原文，`pacing` 给逐章星级与张力曲线。

### 8.4 仍未补齐的劣势（更新后）

| 劣势 | 差在哪 | 影响 |
|---|---|---|
| 运营侧功能缺位 | 无收益测算、全勤测算、排期、赛道雷达、IP 评分 | 想一站式做完"写+运营"的用户，仍应选番茄 |
