## 三、各自的强项与可继承的经验（职责层面）

**网文主编（novel-workshop-pro）**
- 强在知识密度：一条主流程串起十余个阶段，章节写作前先把"风格—构思—设定—大纲—记忆"逐层压实，写作后再走评分、自检、去 AI 味、润色。
- 强在把"写作要求"变成可判定的硬规则（哪些句式禁止、哪些必须为 0），而不是风格建议。
- 强在离线可复现：自带一个不联网的去 AI 味处理脚本，同一份稿子跑两次结果一致。
- 弱在：单文件 1836 行 + 145 份参考，加载成本极高；唯一可执行件是离线去 AI 引擎（改写型，非诊断型），且引擎本体加密在 `engine.pack` 里、依赖 jieba，无法审计；没有项目状态文件；内置了真实作者风格库（详见第六节风险）。

**长篇连载总编（serial-novel-editor）**
- 强在工程化：一套斜杠命令 + 统一目录约定（outlines / chapters / references / export）+ 一个状态文件 + 事实账本，"只读审查不写文件""不得创建超范围文件"这类边界写得明确。
- 强在上下文控制：按意图查表只读必要参考，不一次性读完整个库——这是长文本场景最省上下文的设计。
- 弱在：命令多、入口散，新用户不知从哪条开始；31 份参考之间没有依赖顺序说明。

**番茄爆款（tomato-best-seller-novel）**
- 强在平台机制被拆成可执行指标：推荐机制、追读率/完读率漏斗、章末钩子、救书 SOP。
- 强在把"数据不好"翻译成"第几章第几段该怎么改"。
- **强在带 22 个脚本**，是本组里工具化程度最高的：稿件质检（带总分线与退出码）、节奏六维、AI 味清除、钩子密度、九指标数据看板 + 30 天救书表、四大台账校对、大纲生成、书名打分、选题打分、IP 改编评估、排期与全勤测算。**这一点必须承认：它不是纯知识库。**
- 弱在：脚本之间没有共享状态，22 个工具各自为政，跑完不进账本，下一轮对话接不上；台账校对按单文件 + 关键词表，跨章项目级问题（缺章、伏笔到期、登记与磁盘不一致）查不出；阈值写在脚本里，只能改总分线，无法整体校准；知识与工具绑死番茄口径，换平台即失效。

**爽文小说专家（shuangwen-novel-expert）**
- 强在模块化：规划→节拍→成稿→修订→档案 五个 skill 各管一段，职责边界干净。
- 强在档案可信：章节正文做哈希、依赖前章指纹、改一个字就报完整性错误，导出只认最新版——这是六个竞品里唯一真正防"改稿后账本失真"的做法。
- 弱在：偏短篇与开篇，长篇的运营与数据环节几乎空白；对"写得不好看"只有审查声明，没有可量化的文本体检。

**小说故事创作专家（novel-creator）**
- 强在 Brief 六要素的收口：动笔前先问清类型、篇幅、视角、基调、禁忌、交付形态。
- 弱在：10 个文件，纯方法论，没有脚本、没有状态文件，长篇必漂移。

**著书书（book-co-creator）**
- 强在长文档工程：分层审校、锚点锁、多场景包。
- 弱在：面向书籍/白皮书，不是网文；且内含第三方 skill 与许可证目录，直接复用会带入他人的分发条件。

## 四、缺口（2026-10-29 复核后的修正版）

**先说一句自我修正**：本文初稿写的是"六个竞品都没有可验收的执行层"。复核脚本清单后发现这句话是错的——番茄爆款带 22 个脚本，稿件质检、节奏六维、钩子密度、九指标数据看板都是可执行的，还给了退出码。**初稿把"我读到的是知识库"当成了"它就是知识库"，这是我读漏了 `scripts/` 目录。**

修正后，真正的缺口是这五条：

1. **工具跑完不进账本**
   番茄的 22 个脚本各自独立，跑完打印结果，没有任何一个写回统一状态。同一份稿子今天跑出 78 分、明天跑出 81 分，没人记得上一次是多少；第 40 章写作时不读第 3 章的体检结论。**工具是"用完即弃"的，不是"累积"的。**

2. **跨章核查的覆盖面不全（不是"没人做"）**
   爽文专家的协议已覆盖缺章 gap、前章依赖链、终审伏笔未收——这一点它做得比本产品早期判断的更完整，必须写明。真正的空缺在另外两类：**磁盘与登记是否一致**（登记的 3200 字，磁盘上是 2800 字）、**同章内同一人物的称号漂移**。番茄的台账则是单文件 + 关键词表，跨章项目级问题压根查不到。

3. **判定与执行之间是断的**
   番茄的门禁是"退出码 1 + 一段优化提示词"，属建议循环，跳过它继续写没有任何东西会拦；爽文的门禁是真的（commit 前 `require(review.passed)`），但那个 `passed` 是**模型自己填的**，协议里也自认"是专家审查声明而不是自动文学评价"。两条路各缺一半：一条缺硬门禁，一条缺可复现的判定。

4. **阈值不可校准**
   阈值写死在脚本里，最多改一条总分线。换题材（战斗章 vs 心理章）就失准，用户无法整体调；也没有正负样本自检来证明"这组阈值真的分得开"。

5. **去 AI 味只给改法，不给可复核的量化口径**
   现有做法要么是生成改写提示词（再交给模型重写，结果不可复现），要么是加密引擎直接改字（无法审计）。缺一份"跑同一份稿两次，数字必须一样"的体检表。

另有一条不算缺口但值得记：**单文件巨石**——最重的两个把全流程塞进一个 SKILL，任何一次使用都要整篇载入。

## 五、新产品要占的位置

不做"再来一个更全的知识库"，做**六个竞品都没做的那一层：可验收的执行层**。

一句话定位：把"写得好不好"从主观判断，变成跑一遍就有数字、有定位、有改法的体检报告。

三条差异：
1. **规则可执行**：写作规则全部落成脚本可核对的项（句式连排、破折号密度、比喻密度、段长分布、伏笔到期、称号漂移），交付前必须出报告。
2. **档案可重入**：一个状态文件回答"写到哪、欠什么、下一步"，隔多久回来都能接上。
3. **数据回灌正文**：把追读/完读的漏斗结论，落成"第几章第几段改什么"的具体工单，写回下一章写作包。

## 六、版权与许可风险（先于开发记录，避免误用）

| 对象 | 观察 | 结论 |
|---|---|---|
| 网文主编的 `references/digital-authors/` 与 20 余份 `style-*.md` | 以真实在世作者姓名建立的"数字人记忆库"与风格蒸馏文件 | **不可用**。以真实作者姓名做风格复制，涉及姓名权与实质性相似风险，商业分发风险高 |
| 网文主编的 `番茄/起点/晋江/七猫 TOP 作者手搓句式.md` | 自称"按平台语感整理" | **不可用**。来源不可考，无法确认是否为他人作品摘编 |
| 网文主编 `scripts/deai/engine.pack` | 二进制打包，无源码 | **不可用**。无法审计，不可商业再分发 |
| 著书书内含的 `fbs-bookwriter`、`anti-distill` | 第三方 skill，带独立 LICENSE / package.json | **不可直接复用**。需逐个核实许可证是否允许商业再分发 |
| 文爆爆的 `license/` 四份许可证 | 说明作者已引入第三方组件 | 说明该包为拼装产物，**不可整体作为参考实现** |
| 各专家的头像 PNG | 品牌图像 | **不可复用**。新产品头像独立生成 |
| 各专家的提示词与工作流文案 | 受著作权保护的表达 | **不可抄写改写**。新产品按功能重新撰写 |

已确认可用：平台推荐机制、追读率/完读率的计算口径、黄金三章为什么有效的传播学解释等属于**事实与通用方法**，可用自己的话重写；通用写作技法（因果链、场景目标、人物弧光）属于公共领域方法论。
