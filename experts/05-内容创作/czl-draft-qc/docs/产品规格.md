# 朱笔 · 产品规格说明

版本：3.3.0　　编写：虫志龙　　日期：2026-10-26
系列：尺素（Chisu）第一支笔

> 本文件是"要做什么"的定义。2.0 与 1.x 的根本差别在一个字：**窄**。

## 一、定位

**一句话**：一个关键词进去，一篇能发的公众号稿子出来。

四个阶段串成一条链：
- **选题层**：关键词 → 联网搜热点 → 五种角度出 5 个候选 → 脚本查重 → 用户选 1
- **成稿层**：选定角度 → 骨架（可校验承重）→ 初稿
- **质检层**：八项指标体检 → 分诊 → 定点重写 → 复检闭环
- **形态层**：按固定排版规范套版（五套配色随机一套）→ 配图（下载到本地）→ 合规自检 → 交付 HTML + 图片上传清单

**不做什么**（写在这里是为了防止以后膨胀）：
排期、文风建模、数据复盘、批量生成标题。这些属于尺素系列其他成员。

**排版做但只做一半**：套用固定规范生成 HTML，不做原创视觉设计。要新风格必须先改规范，不属本产品范围。

**为什么要收窄**：1.x 版本承诺了七件事，等于没有承诺。开放平台质量检测的第一维度是"任务完成度——每个专家只承诺一件具体、可交付的事"。收窄不是减法，是过审与定价的前提。

## 二、目标用户

| 用户 | 场景 | 他现在怎么办 |
|---|---|---|
| 单人自媒体作者 | 稿子写完，周五晚上要发，没人把关 | 发给朋友看，朋友说"挺好的" |
| 小团队主笔 | 稿子被老板说"读着有点飘" | 凭感觉改，改三遍还在原地 |
| 代运营 | 客户稿子质量参差，要一个客观标准 | 只能自己逐字看，看完也说不出问题在哪 |
| 内容负责人 | 需要向上解释"为什么这稿要改" | 拿不出依据，只能说"感觉不行" |

共同点：**他们已经有一篇稿子了**。这是本产品与"写作助手"的核心区别。

## 三、需要解决的问题

| 编号 | 问题 | 本产品怎么解决 |
|---|---|---|
| P1 | 判断"稿子好不好"只能靠感觉 | 八项指标打分，每分可追溯到公式 |
| P2 | 知道"像 AI 写的"但说不出哪里 | 元叙述/总结句标签/同构短句，定位到句序 |
| P3 | 改稿没有依据，改完不知道有没有变好 | 改前后两次脚本数字并排 |
| P4 | 不知道这稿该救还是该重写 | 分诊三选一（局部手术/保留重写/推倒重来） |
| P5 | 改稿容易越改越假 | 只改被标记的句子，优先删不换词 |
| 排好了粘到公众号就掉样式 | 按全内联规范渲染，再用 linter 把黑名单反过来查一遍 |

## 四、输入与输出

### 输入

| 必须给 | 缺失时 |
|---|---|
| 稿件全文（UTF-8，≥300 字） | 不足 300 字给"样本偏小"提示；无全文无法工作 |
| （可选）发布场景 | 默认按"公众号图文"处理 |
| （可选）不能改的部分 | 如必须保留的引用、必须提到的产品 |

### 输出

| 输出 | 形态 | 合格标准 |
|---|---|---|
| 体检报告 | 终端文本 / JSON | 每项分数可追溯；硬伤指到句序 |
| 分诊结论 | 三选一 + 理由 | 理由必须能被原稿验证 |
| 修改对照 | 三列表 | 每处能说清"改后靠什么解决" |
| 前后对比 | 两次分数并排 | 必须是真跑出来的 |

## 五、处理步骤

```
W0 选题：关键词 → 联网搜 → 热点/常销分类 → 五角度出 5 个 → 脚本查重 → 5 张卡片 → 用户选
                                                                        │
W1 骨架：按角度选骨架模式 → 5—9 节点（每个须有"读者得到"）→ 脚本校验 ←──┘
                              │ 不通过则砍节点
W2 初稿：按骨架写，写糙不写满
W3 体检：跑脚本拿数字 → 硬伤优先
W4 改稿：分诊 → 定点重写 → 复检（连续两轮不过则退回 W1）
W5 排版与配图：规范渲染 → 图片下载与清单 → 合规自检（exit 0 才算交付）
     ※ 定稿即执行，不询问"要不要排版"
```

**关键判断点**：
- 硬伤 ≥1 → 判"需修"，不看总分
- 段落可任意调序而阅读不受影响 → 骨架问题 → 推倒重来
- 连续两轮复检不过 → 停止润色，回退到结构层

## 六、技术实现

| 能力 | 实现 | 依赖 |
|---|---|---|
| 八项指标 | 自研正则 + 统计（句切分、段落切分、CV、词表命中） | Python 标准库 |
| 硬伤判定 | 六类阈值规则 + 位置回溯 | 标准库 |
| 标题机械校核 | 六维加权评分 | 标准库 |
| 选题打分 | 五维加权 + 两两字面相似度查重（bigram Jaccard） | 标准库 |
| 热点检索 | WebSearch 联网，三组查询（官方口径/民间讨论/数据变化） | 系统内置搜索 |
| 骨架校验 | Markdown 结构解析 + "读者得到"必备字段检查 | 标准库 |
| 排版渲染 | 自研 Markdown 方言解析 + 内联样式生成（680px、全 table 骨架、九组件、五套配色） | 标准库 |
| 图片下载 | 魔数校验 + 尺寸解析 + 来源记录 + Markdown 标记生成 | `urllib`，需网络 |
| 图片清单 | 按出现顺序汇总：文件/尺寸/体积/所在章节/缺失与外链告警 | 标准库 |
| 配色选择 | 五套低饱和配色，默认随机、可指定、可复现 | 标准库 random |
| 排版合规自检 | 黑名单正则 + 结构检查（表格/圆点/字体/容器） | 标准库 |
| 语义补位 | 模型判断（歧义、真伪、信息量） | 无脚本，靠推理 |

**明确不做**：AI 生成概率检测（黑箱、误判高、不可解释）、第三方 NLP 分词库（安装成本与许可风险）、OCR/爬虫（合规风险）。

## 七、质量、速度、稳定性

| 维度 | 要求 | 达成 |
|---|---|---|
| 质量 | 坏样本与好样本必须显著区分 | 44 vs 98.9 |
| 质量 | 每个数字可追溯到公式 | `references/rules.md` 与脚本一一对应 |
| 速度 | 5000 字以内单次运行 <1 秒 | 实测 <0.3 秒 |
| 稳定性 | 空文件/超短文本/编码异常不崩溃 | exit 2 + 中文错误提示 |
| 安全 | 稿件不上传第三方 | 全部本地处理 |

## 八、明确不承诺

- 不承诺阅读量、涨粉、转化率
- 不承诺"能过 AI 检测"（检测本身不稳定，且不等于质量）
- 不判定"这段是不是 AI 生成的"——只描述特征
- 不代替事实核查、法律审查、专业领域审核
- 质检分数是启发式测量结果，不是权威认定（已写入 LICENSE 4.5）

## 九、与 1.x 版本的关系

1.x（原「稿尺」）是一个覆盖七件事的复合包；2.0 只保留质检与改稿，其余四个技能已迁出到产品线暂存区，作为后续专家的原料。

**已迁出**：draft-foundry（→ 墨裁）、editorial-radar（→ 砚台）、voiceprint-lab（→ 文风建模）
**保留**：quality-gate（quality_gate.py + title_score.py）
**2.1.0 重新纳入**：publish-kit（按实战规范重写）。
**3.0.0 扩为全链路**：新增 topic-radar（选题）；draft-foundry（成稿）从暂存区迁回。理由是这三个阶段服务的是同一篇稿子，用户不会拿了选题就走。

这不是删功能，是给功能找对位置。详见 `docs-产品线/专家系列规划.md`。
