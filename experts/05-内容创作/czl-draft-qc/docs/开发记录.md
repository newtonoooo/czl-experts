### 关键技术决策（阶段一）

**决策 1｜不做"AI 检测器"，做"特征测量器"**

放弃的：给稿子打一个"AI 生成概率"。原因：中文长文困惑度判定误判率高，且用户拿到"87% 像 AI"之后仍然不知道改哪里。

采用的：八项可指认特征，每项都能定位到具体句子。代价是无法回答"这稿是不是 AI 写的"——所以在 SKILL.md 里写明这个边界，把问题转成"哪些地方读起来像机器写的"。

**决策 2｜硬伤优先于总分**

测试时发现：刻意写的 AI 腔样本，句长变异系数 0.63，节奏项拿满分 20/20。原因是它把长句和短句清单混在一起，句式反而"丰富"了。只看总分会被骗。

所以设计硬伤机制：六类硬伤任一命中直接判"需修"，不看分数。

**决策 3｜中文数量词必须单独统计**

第一版只数阿拉伯数字 `\d`。跑真人样本时，一篇满是"四十来岁""十二页""两万多张"的稿子，"具体信息"项只拿 2.1/5，被判"没有具体信息"——完全错了。加中文数量词正则后升到 5/5。

这是本次开发中唯一一次**指标本身出错**（不是阈值问题），记在此以免重犯。

**决策 4｜推送默认演练**

草稿箱是对外操作，写错标题摘要的修复成本高于重新生成。所以默认只打印 payload，真实推送必须 `--push --yes` + 环境变量凭据。

**决策 5｜骨架检查用脚本，不用感觉**

`outline_check.py` 只查一件事：每个节点有没有一行"读者得到："。看起来简单，但拦住的是最常见事故——写到第三段发现和第五段说的是同一件事。骨架阶段发现成本 5 行，初稿阶段发现成本重写 1000 字。

**决策 6｜模板不能用二级标题写说明文字**

第一次跑 `outline_check.py` 检查自己的模板，报出 3 个"必须修"——因为模板里的"基本信息""填不出来的节点怎么办"用了 `##`，被当成节点。修正方式不是放宽脚本（会漏掉真问题），而是改模板：说明性内容用加粗，只有真节点用 `##`。

## 二、阶段二：重新定位与品牌重建（v2.0）

### 触发原因

1. **审核要求"一个专家只承诺一件事"**。v1.0 承诺七件事，质量检测第一维度就是任务完成度，这是实质过审风险。
2. **`name` 上架后不可改**。当时尚未上架，是唯一可以调整标识的窗口。
3. **单包无法定价分层**。七件事一档价，拆开后可以有引流款、主力款。

### 做了什么

**改名（品牌层）**

| 项 | 旧 | 新 |
|---|---|---|
| 花名 | 稿尺（Gaochi） | 朱笔（Zhubi） |
| 职业 | 公众号内容运营顾问 | 公众号内容运营专家 |
| 标识 | `gaochi-content-ops` | `chisu-draft-qc`（2.1.1 起为 `czl-draft-qc`） |
| 系列 | 无 | 尺素（Chisu） |

选「朱笔」的理由：三个字不能解决的问题，两个字解决了——**"朱笔"是一个动作（批），不是一件器物（尺）**。批改、批注、朱批，都是"在已有文本上做记号"，正好是本产品的本质。而"稿尺"是名词，读起来像工具型号。

**标识的二次调整（2.1.1）**：开发者要求所有专家标识以 `CZL` 开头。因平台与校验脚本都要求 name 全小写，实际落地为 `czl-`。这不影响展示层——用户看到的是花名「朱笔」，标识符只在系统内部与路径中使用。系列名「尺素」保留在展示层，与标识前缀分层，互不干扰。

选「尺素」作系列名的理由：古人称书信为尺素。"尺"承原名，"素"指素绢，合起来是"写给读者的那封信"——正好是公众号的隐喻。文气足，但不装。

**收窄（产品层）**

- 定位从七件事收为一件事：给已写完的稿件做质检并改到能发。
- 四个技能迁出（`draft-foundry`、`editorial-radar`、`publish-kit`、`voiceprint-lab`），暂存至产品线目录，作为「墨裁」「砚台」「版心」的原料。
- 判定框架由"四把尺子"改为"三把尺子"：结构尺、语言尺、**事实尺**。取消定位尺（属其他专家职责），新增事实尺——这是收窄带来的意外收获：范围小了，反而能把"事实核查"这件脚本做不了的事说清楚。
- 工作流由五条改为四条：W1 体检 / W2 分诊 / W3 定点重写 / W4 交稿前。
- 新增"只做一件事：明确的边界"表，列出六类不处理的需求，遇到直接拒绝。

**技术处理**

- 重建目录与标识（`czl-draft-qc`），重命名 `agents/*.md`。
- 两个脚本内的品牌字符串（报告标题、docstring）同步替换。
- 新增 T10 用例：扫描包内是否残留旧名，确保品牌一致性。
- 新增 T11 用例：校验 `plugin.json` 的 skills 清单与 `skills/` 目录完全一致，防止迁出后配置残留。

### 一个没做的取舍

**没有删除 1.x 的四个技能**，而是迁到 `docs-产品线/_待发布技能/`。理由：这四个技能共约 1200 行文档 + 4 个脚本，是后续三个专家的全部原料。删掉等于把系列化的地基砸了。

迁出而非删除，也意味着它们不再计入本包的技能注册（T11 验证过），不会稀释"只做一件事"的定位。

### 阶段的教训

**收窄比扩张难。** 1.x 写的时候很顺，因为每加一个能力都是"更全"；2.0 删的时候很别扭，因为每个被删的能力都有脚本、有文档、有测试。但用户不会因为"功能多"付费，只会因为"这件事你做得比我自己好"付费。

## 二之二、阶段三：排版返工（v2.1.0）

### 触发

用户看完旧渲染器的产出，原话是"这个专家形成的公众号排版太丑"。

他说得对。旧 `render_preview.py` 是 390px 容器 + 极简样式：没有章节条、没有卡片、没有配色体系，正文就是灰底白纸上的黑字。功能上"能渲染"，视觉上就是一封纯文本邮件。

更关键的是：**它不知道公众号编辑器的过滤规则**。样式一粘就掉，掉完比不排还难看。

### 做法：不是重写样式，是换成一套有约束的规范

用户提供了一份他自己在多个账号上验证过的《公众号 HTML 排版规范》。这份规范的价值不在配色，在三件事：

1. **黑名单**：明确列出 grid / flex / position / transform / 伪元素 / 负 margin / calc / var / 渐变 / 阴影在公众号里会怎样翻车，每条都有替代方案。
2. **布局只用三件套**：块级 + `table` + `inline-block`。这一条把"想用 flex 做时间轴"的冲动直接堵死，也是那份规范里"时间线翻车"的复盘结论。
3. **自检清单**：10 条可以逐条勾的交付前检查。

所以我做的不是"调样式"，是把规范翻译成两个东西：

- **`render_wechat.py`**：把规范里的 Token 与九个组件写死进代码，输入只是 Markdown + frontmatter。写手不需要懂 CSS，按语法写，出来的就是规范的样子。
- **`check_wx_html.py`**：把黑名单反过来变成检查器。这是我认为最有价值的一步——**规范写在文档里没人看，写进脚本里每次都会跑**。

### 一个真 bug：自检工具自己没被检查

字体 fallback 检查的逻辑是"每个 `font-family` 必须以 serif / sans-serif 收尾"。写完自测，正常稿子 0 FAIL，看着挺好。

但用负样本一跑，`font-family:'Noto Serif SC'`（明显没有 fallback）竟然没被抓到。

原因是正则写成了 `[^;\"']+`——**排除了单引号**。而样式值里的字体名普遍用单引号包裹（`font-family:'Noto Serif SC',serif`），正则一遇到 `'` 就匹配失败，整条规则从未生效，永远静默通过。

修正为只排除双引号后，负样本从 7 项 FAIL 变成 8 项。

**这是本次开发最重要的一条教训**：自检工具必须用负样本验证。否则"全绿"可能只是"没检查"——这比没有检查更危险，因为它会让人放心。

### 收窄与扩张的第二次权衡

2.0 刚刚把产品收窄成一件事，2.1 又加回排版。这是不是自相矛盾？

我的判断是**不是**，理由是公众号的发布形态决定的：不发 HTML 就发不出去。排版不是"附加服务"，是"交付形态"。所以主 Agent 里写的是"这是同一件事的两头，不是两件事"。

但边界同步收紧了：**只套版，不做设计**。要新风格必须先改规范，那不属于本专家。这条写进了 Agent 的边界表（"帮我设计一个全新的版式风格 ❌"）。

**如果以后又有人问"能不能自定义配色"**——答案是不行，让他改规范文件。这条界线守不住，产品就会重新变成一个 CSS 生成器。

## 二之三、阶段四：把工具串成一条链（v3.0.0）

### 用户的原话

> "这个专家缺少选题技能……客户只要写个关键词，他就能搜索当前热点话题，生成 5 个选题主题，然后让客户选择一个主题或者重新选题，然后生成公众号文章。"

这句话描述的是**一条链**，不是三个功能。所以我做的不是"加两个技能"，是把 Agent 的主干从"一篇文章的后半段"改成"一篇文章的全过程"。

### 难点一：5 个选题其实是 1 个的 5 种说法

这是选题环节真正的病。模型一口气生成 5 个，往往长这样：

> 中考体育怎么练 / 体育选考怎么选 / 暑假怎么安排训练 / 考前一周怎么调整 / 受伤了怎么办

看着五个，全是一个角度：怎么做。用户拿到的信息量约等于一篇。

**两个解法叠起来用**：

1. **强制五角度**：事实 / 影响 / 反常识 / 方法 / 判断，各出一个，不许重复。写进 `references/angles.md`，每个角度给"一句话识别"和"最怕写成什么"。
2. **脚本查重**：`topic_score.py` 两两算字面相似度（bigram Jaccard），≥0.45 判重，**exit 1 不许交付**。

第 2 条是关键。原因在于：**让模型自己判断"这五个够不够不一样"，它永远会说是。** 只有把判断交给一个不带自我偏好的脚本，它才会真的淘汰自己刚生成的东西。

### 难点二：热点必须真搜，不能凭记忆

这是最危险的地方。模型的训练数据里有一堆"中考体育改革"，它完全可以在不联网的情况下编出五个像模像样的选题——**每一个都可能是两年前的旧闻**。

所以 `SKILL.md` 第一条写死：**先搜再想**，用 WebSearch 至少三组查询（官方口径 / 民间讨论 / 数据变化），并给每条信息标时间。`references/hotspot-playbook.md` 里定了五条热点标准和"假热点的四种长相"（旧闻翻炒、单条爆料、标题党放大、地域错位）。

还写了最狠的一条边界：**搜不到就直说搜不到，改出常销题，绝不把旧闻包装成"最近"。**

### 难点三：又一次量词表翻车

第一版 `topic_score.py` 把"体育选考**三项**，哪**一项**最不值得练"判成"具体性 0 分"——它明明有一个非常明确的选择指向。

原因是量词表只收了 `个/年/月/日/岁/块/份/人/天/篇/次/条/所/校/科/分`，没有 `项`。

修正：量词表补 `项/门/种/类/步/张/届/名/位/组/场/套/期/本/页/章`，并新增 `CHOICE` 规则（哪一/哪个/哪种/该不该/要不要/值不值）作为"选择指向"加分。该题 67 → 81 分。

**这已经是同一个坑第二次了**（上次是字体 fallback 漏了单引号）。两次的教训一样：**启发式规则永远在用词表覆盖度换准确率，样本里没覆盖到的说法，就会误判成"没有"**。所以每条规则都要用负样本撞一遍。

### 定位的第三次调整

- 1.x：七件事（宽）
- 2.0：一件事（窄）
- 2.1：加排版（"一件事的两头"）
- 3.0：一条链（选题→成稿→质检→排版）

看起来像翻烧饼，但有一条线没断：**每个版本做的事，都是围绕"一篇稿子"**。1.x 的问题是同时干了不同篇的事（排期、复盘）；3.0 的三个环节服务的是同一篇。

判断标准写进 CHANGELOG 了：**用户会不会拿了这一环就走？** 不会——他拿了选题必然要稿，拿了稿必然要改。所以是一条链，不是三个产品。

但也有代价：口径变宽了。卡片写"内容运营专家"，实际做的仍是单篇文章，不做排期、文风建模、复盘。这条边界没动，Agent 的边界表里逐条列着。

## 二之四、阶段五：不再问，直接排（v3.1.0）

### 用户的两句话

> "所有的内容都确定后，不要问要不要接着排成能直接粘进公众号后台的 HTML？直接排版生成 HTML 文件。"
>
> "最好再在网上下载一些相关图片，直接在 html 文件中加入，显得文章更好看。"

第一句是**流程问题**：我把"排版"当成了一个需要用户确认的选项。但用户拿到一堆 Markdown 根本发不出去——排版不是可选项，是交付物的组成部分。

第二句是**能力缺口**：文章有图确实好看，但公众号有个硬限制——外链图片粘到后台必裂。

### 关于"不问"这件事

我原来的 W5 写的是"内容定稿后询问是否排版"。这个设计的出发点是"不要替用户做决定"，但用错了地方：

- **该问的**：选题要不要换角度、这段要不要删、事实对不对。
- **不该问的**：要不要把成果交付出去。

判断标准写进 Agent 了：**这件事是不是把成果交付给用户所必需的？是，就做，不问。**

原话也写进去了：「禁止问"要不要排成 HTML"」。

### 关于图片：为什么不按用户说的"直接加进 HTML"

用户要的是"直接在 html 文件中加入"，这句话有两种实现：

1. **外链**（`<img src="https://...">`）—— 在浏览器里完美，粘到公众号**必裂**。微信会拦第三方图片。
2. **下载到本地 + 相对路径** —— 本地预览正常，粘到后台图片位置为空，但文件还在，用户手动上传即可。

第 1 种看着最省事，实际是给用户埋雷：他粘过去以为好了，发出去才发现一堆裂图。

所以选第 2 种，并补了一个东西：**图片上传清单**。这是这次开发里最实用的一件小事——

粘完正文，图片位置是空的，用户需要知道"哪张图插在哪"。如果只有一堆 `images/01_1.jpg`，他得回头数段落。有了清单：

| # | 文件 | 尺寸 | 体积 | 插在哪 | 说明 |
|---|---|---|---|---|---|
| 1 | `images/01_1.jpg` | 1200×800 | 240 KB | 第一节 | 初三教室全景 |

照着传就行。

### 图片这条链上的三个判断

1. **不下载就等于没做。** 只给外链等于把问题推给用户，而且是他发现不了的问题（本地看着好好的）。
2. **不校验就等于埋雷。** 下载下来的可能是 HTML 错误页、可能是 12MB 的原图。所以 `fetch_images.py` 查图片魔数、读尺寸、限体积、记来源。
3. **不提醒版权就等于挖坑。** 网上搜到的图不等于能用。脚本会写 `SOURCES.txt` 记来源，清单里单列版权提醒，Agent 的注意事项里写"来源不明的宁可不用"。

### 一个没做的东西

`--embed`（base64 内嵌）做了，但**没设成默认**。原因：把图片编码进 HTML 后文件会涨到几 MB，微信编辑器不一定接受，粘贴也可能卡。理论上能省掉手动上传，但没实测过——**没实测的东西不能当默认方案**。这条也写进了 README 的已知限制。

## 二之五、阶段六：规范升版（v3.2.0）

### 触发

用户更新了他自己那份《公众号 HTML 排版规范》，加了 5 套配色，然后说"你把这些规范修改到专家包中"。

我先做了 diff，发现**改动比"5 套配色"大得多**，有三处：

1. 新增 §4「配色方案库（5 套）」
2. **布局philosophy 变了**：上一版写"普通块级 + table + inline-block"，这一版写"外层 table + 容器 table + 每个区块一个 `tr>td`"
3. 字号从 14.5px 提到 17px、左右留白 24 → 32px、图片从"上传素材库"改成"下载到本地 assets/"

如果只加 5 套配色，产物就跟规范脱节了。所以这次是**按新规范重写渲染层**，而不是打补丁。

### 为什么随机是对的做法

规范里其实写着"同一篇/同一系列尽量固定一套，别中途换色"。用户要的却是随机。

这两件事不矛盾，因为**颗粒度不同**：规范说的是"篇内"和"系列内"，用户说的是"篇与篇之间"。所以落地成：

- **篇内**：绝对只一套（随机发生在整篇级别）
- **篇间**：默认随机，制造变化
- **可锁定**：frontmatter 写 `theme:`，同一系列想统一就写死

随机还有一层实际作用：一套配色用久了，读者在信息流里先认出颜色再认出内容。五套轮换能缓一下，但轮换过头就成了没有识别度——所以给了 `theme:` 这个刹车。

### 三个组件是规范里早就写了、我却没实现的

上一轮我按规范做了时间轴、数据表、编号清单、提示块，但 §6 里的金句卡（6.7）、数据卡（6.8）、来源框（6.10）一直没实现。这次补上，因为换配色之后**这三个组件最能把配色的差别显出来**：

- 金句卡是主色整块，一眼看出这套是什么色
- 数据卡是浅底 + 强调色大数字，两色对撞
- 来源框是白底细边，把正文与出处分开

顺带加了 `## ! 标题`（重点章节换强调色方块）和 `tag2`（第二个描边标签）——都是规范里有的写法。

### 换配色马上踩到的坑：写死的色值

旧渲染器有两处没走 token：主标题 `#222`、提示块 `#5a564c`。

a-ink（墨绿）下看不出来，因为 `#222` 跟它本来就近。但换成 e-graphite（石墨青），标题会是死黑，跟正文 `#23282A` 撞；提示块会发灰，跟浅底不搭。

**这类 bug 的特点是不会报错、不会崩，只是变丑一点点。** 加进测试的方式是直接断言：渲染产物里不许出现 `#222;`、`#5a564c`、`#333333`（T31）。这比"看起来还行"可靠。

### 第二个坑：table 拼接多了一个闭合

`full_table()` 是个自带 `</table>` 的完整 table 生成器。我在表格和时间轴两处把它当"开标签"用，后面又追加了行和另一个 `</table>`——结果是"空 table + 多余闭合"。

浏览器会容忍这种错误，所以肉眼看不出来。发现方式是**数标签**：对产物做 open/close 计数，table 15 开 17 闭，立刻暴露。

修正后 15/15、tr 46/46、td 78/78、p 34/34、colgroup 2/2。这条也写进了测试思路：**HTML 结构错误肉眼不可靠，靠计数。**

### 关于"随机"这件事的一个边界

我没有做成"按文章气质智能选色"。想过，但结论是**不该做**：

- 气质判断是主观的，脚本按关键词猜"这篇是情感文"经常猜错
- 猜错的代价比随机高：随机只是"颜色不合口味"，猜错是"系统误解了我的文章"

所以只做了两级：随机（默认）+ 指定（用户说，或 Agent 从用户明确表述里提取）。Agent 侧留了一句"用户明确说了这是亲子情感文/政策解读，可以按气质挑"——**依据必须来自用户的话，不来自猜测**。

### 3.2.1 职业名被平台驳回

上架时驳回原因：`profession.zh` 在同类资产中必须唯一，而「公众号内容运营专家」已被占用。

这不是第一次撞名了。2.1.3 从「公众号稿件质检顾问」改成「公众号内容运营专家」时，我的理由是"头衔宽一点、介绍守住能力"，当时没考虑**唯一性**这个约束。**平台的地方就那么大，越通用的词越早被占满。**

新名「公众号图文创作与质检专家」的取舍：

- 必须带不常见组合 → 「创作 + 质检」这个并列在同类里很少见
- 「创作」对应选题与成稿，「质检」对应八项指标与去 AI 味，两个词都指向真做过的能力
- 放弃的两个方向：`稿件质检与排版`（藏了成稿，少一半客源）、`单篇图文创作`（"创作专家"太通用，大概率再撞）

**教训**：给专家起职业名，不能按"最大程度概括能力"来起，要按"在同行列表里唯一"来起。两者冲突时，先保证唯一，再把覆盖面放进 `displayDescription`。

## 二之六、阶段七：账号交还给用户（v3.3.0）

### 用户的要求

> "公众号名称要让用户自己写。去除某个具体账号的相关内容，不要让 AI 直接生成的文档和它有任何关系，
> 要和用户的公众号内容和方向相关。还有就是要体现成稿排版能力。"

第一条是**产品边界问题**，不是文案问题。之前整个包的默认值是"某个具体的号 + 升学领域"，
意味着任何人装上它，写出来的第一篇文章都带着别人的口音。

### 我清的是两类东西，用户只说了一类

用户说的是"账号名"，但只删账号名不够。样本文章写的是升学、读者是家长、地点是本地，
这些同样会把人带到不属于他的领域。所以：

| 类型 | 处理 |
|---|---|
| 账号名 | 落款、规范组件示例、脚本注释全部改为占位 |
| 落款 slogan | 改为"换成你自己的一句话定位" |
| 样本题材 | 从升学改成中性的"小店观察"，与任何领域无关 |
| 技能示例 | 选题例子从"中考体育"改成"早高峰通勤" |
| 规范溯源 | 规范副本里那句"来自某某账号几十篇实战"改为"来自多账号实战" |
| 规范 §8 | 原本直接写着某账号的语气规则 → 改为"语气由使用者提供"，原句降级为填写示例 |

最后一条值得单独说：`typography-spec.md` §8 里那段语气要求，本质上是在替使用者定人设。
排版规范可以统一，**语气不能统一**。所以改成"这一项由使用者提供"，并把原句标为示例。

### 新增的关卡：开工前先问账号

主 Agent 加了一节「开工前，先拿到账号的两件事」：公众号名称 + 账号方向。并写死"没有任何默认值"。

判断标准是**能不能自己编**：
- 账号方向：可以问，不能猜——猜错了整篇都白写
- 账号名：不能编。**读者会照着去搜，搜不到就是骗人。** 所以规则是"不知道就留空，落款不出，比编一个强"

这一条同时落到了三个技能里：draft-foundry 的第零步、publish-kit 的落款硬规矩、markdown-dialect 的字段说明。
只写在主 Agent 里不够——技能被单独调用时，规则就丢了。

### 职业名的第三次调整

`公众号图文创作与质检专家` → `公众号成稿质检与排版专家`。

用户要"体现成稿排版能力"。用「成稿」替掉「创作」，是因为"创作"容易读成"帮我写作文"，
"成稿"在出版语境里更准：从有骨架到能发的那一步。再把「排版」补进去，三个动作就齐了。

能力介绍也跟着从"从一个关键词出发…"改成"按你账号的方向…"。原来那句的毛病是
**默认了谁都从关键词起步**——但很多人是带着稿子来的。现在先讲账号，再讲动作。

### 一个自查工具带出来的问题

新增测试 T32/T33 直接断言"包内 0 处旧账号名""可见文件 0 处领域预设"。第一次跑就红了——
CHANGELOG 里我引用了用户原话，把那个号名写进去了。

这说明一件事：**"全包清零"这种要求，靠人眼看是不可靠的**。我改了 11 个文件之后自认为清干净了，
结果变更日志里还留着一处。所以这类要求必须落成断言，而且要包含 CHANGELOG 这类"看起来无关"的文件。

T33 留了两个例外并写清了理由：CHANGELOG 与开发记录要保留原词以便追溯改了什么；
quality-gate 与 topic-radar 的回归样本是带评分断言的固定数据，换词会动分数。

## 三、头像的生成与处理

### 第一版（v1.0—2.1.1）：年轻顾问

按角色描述构建 prompt：中年内容顾问、圆框眼镜、深灰亚麻衬衫、手持木折尺与红色批改笔、米色纸纹背景。

视觉隐喻对应"量而不是夸"——尺用来量，红笔用来批。

### 第二版（v2.1.2）：现代年轻编辑

中途试过一版"资深编辑"（银发、细纹、折角批注稿纸），被用户否掉，理由是"不要老登头像"。这个否决是对的，值得记下来：

**我当时把"有经验"理解成了"年纪大"。** 但头像要传达的不是年龄，是**状态**——这个人手上有活、判断快、不废话。年龄只是传达这个状态的一种手段，而且是最笨的一种：加皱纹、加白发，得到的不是"经验"，是"疲惫"。

最终版换了三个信号：

1. **配色先立住**：墨绿高领直接用产品排版规范的主色 `#1F5A50`。头像和文章版式是同一套视觉，用户点进来会认得出是一家的。
2. **道具代替资历**：一手红笔（在改）、一手平板加两页打印稿（在看）。不说"我审过很多稿"，让手上有东西。
3. **神态收着**：不笑、不皱眉、不对视镜头做强势表情。就是"你说吧，我听着"的平静。

去掉的符号：老花镜、手写稿堆、西装领带、书架。这四个是"专家"刻板印象的标配，同时出现会显得像培训机构讲师。

**一句总结**：年轻不等于没经验，老不等于有权威。头像要解决的是"信不信这个人能干活"，不是"这个人干了多少年"。

## 四、遇到的问题与解决

| 问题 | 现象 | 解决 |
|---|---|---|
| 头像体积超限 | 512×512 PNG 554 KB | 6 bit 通道量化，279 KB |
| 无图像库 | Pillow 不存在，`Add-Type` 被拦 | 自写纯标准库 PNG 处理工具 |
| 渲染 HTML 标题重复 | 推送内容含 `<h1>`，公众号显示两次标题 | 提取正文时剥离开头 h1 |
| 排期同周两篇日期相同 | 像同一天发两篇 | 同周第二篇 +3 天 |
| 文风区间显示 `0.41 – 0.41` | 四舍五入后两端相同 | 比较格式化字符串而非浮点 |
| 标题打分 100 分时"短板=强项" | 六维全满 min==max | 比值 ≥0.98 时显示"—" |
| 改名后旧名残留 | 脚本报告标题仍打印"稿尺" | 全文替换 + 新增 T10 自动检查 |

## 五、原创性说明与证据链

1. **文件时间戳**：包内所有文件创建于 2026-10-26 同一会话内。
2. **脚本风格一致**：两个脚本共用同一套写法（`clamp`、中文 docstring、退出码 0/1/2、`argparse` 用法段），同一次写作的痕迹。
3. **样本自写**：`bad_sample.md`、`good_sample.md`、`titles_demo.txt` 均为本次撰写。
4. **文档交叉引用**：`docs/产品规格.md` 的问题编号 P1—P5 与 Agent 的四条工作流一一对应。
5. **测试日志**：`docs/test-run-log.txt` 是同一次真实运行的输出，非事后编写。
6. **无外部代码**：T9 验证包内无第三方 Python 依赖；`LICENSE` 第三节逐项声明。
7. **改名可追溯**：`CHANGELOG.md` 的 2.0.0 条目记录了旧名到新名的完整映射，改名不等于冒充新品。

**需要说明**：方法论（如"删句子而不是换词""读者得到是什么"）属于通用写作常识与编辑经验，不主张独占；可主张的是指标定义、公式权重、脚本实现与文档表达。
