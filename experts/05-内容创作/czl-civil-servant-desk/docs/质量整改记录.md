# 质量整改记录（两轮）

**产品**：案头 · 公务员工作助理（`czl-civil-servant-desk`）
**评测结果**：v1.0.0（2026-10-27 提交）→ 低质量；v1.1.0（2026-10-29 提交）→ 低质量，同一句反馈"沙箱评测中表现未达审核标准"。
**v2.0.0**：2026-10-30 重构。

---

## 一、第二次被拒后改的判断

第一轮我按"提示词没写好"改：换默认语、把追问改成推断、加降级话术。**第二次反馈一字不差**，说明问题不在某句话，而在**包的形态**。三条结构性判断：

| # | 判断 | 依据 | 后果 |
|---|---|---|---|
| 1 | **启动注入量过大，稀释核心行为** | 4 个技能 + 1 个 agent 合计 **22,063 字符**（≈11,000 汉字）在用户说话前就压进上下文 | 模型容易在"读文件/走流程"上打转，首轮不出稿 |
| 2 | **脚本压在主路径上** | 5 个脚本，"跑 review_gate/build_docx"出现在多个环节；沙箱无 Python 或工作目录不同即失败 | 要么断流，要么编造"已按国标排版" |
| 3 | **回复模板过重** | 强制五块：正文/自检/待确认/文件与命令/下一手 | 读起来像填表；"文件与命令：未生成文件"对用户是噪声，评测易判"模板化、无实质" |

## 二、v2.0.0 改了什么

| 项 | v1.1.0 | v2.0.0 | 变化 |
|---|---|---|---|
| 技能数 | 4 | **1**（`doc-craft`） | -3 |
| 启动注入量 | 22,063 字符 | **7,892 字符** | **-64%** |
| 脚本数 | 5（技能目录内，主路径） | **2**（`bin/`，明确"可选"） | -3 |
| 回复结构 | 五块固定 | **稿件 + ≤4 行核校备忘** | 去掉两块噪声 |
| 首轮规则 | "先写，再问最多 3 个问题"（留了口子） | **首字即标题；不许先提问**；缺口用【待补】 | 由"允许"改为"禁止" |
| 自检外抛 | 把问题列给用户 | **自己改完再交** | 责任归位 |
| 文件数 | 46 | **14** | -32 |
| 体积 | 770 KB | **约 200 KB** | -74% |

### 具体动作

1. **合并技能**：把岗位档案、文种骨架、承接映射、模板库、五轮审校、版式参数压成 1 个 `doc-craft`，只保留"角色层没有的细节"（22 文种骨架、审校二十条、精确版式、承接五列、答问六块、词表）。
2. **角色层重写**（5.4 KB）：三条铁律（首字即标题／不编事实／不谎报）→ 四步出稿 → 文种速查表 → 上级文件三步 → 八条语言规矩 → 十条致命项自查 → 交稿形态。
3. **脚本降级**：`bin/docx_export.py`、`bin/docx_check.py` 标注"可选"；没有 Python 就交稿面格式＋版式参数，并明说未生成。删掉 `task_extract.py`（拆任务改由模型直接做，反而更准）。
4. **删掉标签式块**：不再有"文件与命令""下一手"等固定栏目；下一步建议压成末尾一句。
5. **自检升级**：`bin/selftest.py` 从 12 项改为 15 项，新增"启动注入量 ≤16KB""三条硬规则在位"——把这次踩的坑做成回归项。

## 四、如果第三次仍不过

按可能性排序的下一步：

1. **砍掉技能**：把 `doc-craft` 也并进角色层，做到"零技能、单文件"。注入量再降到 ~9KB。
2. **默认引导语再降一档**：只给"文种 + 一句事由"，排除"信息量过大导致跑偏"。
3. **加格式硬约束**：要求首行必须是 `# 标题` 形式或 `<公文>` 包裹，牺牲灵活性换确定性。
4. **换评测面**：把 `quickPrompts` 三条全部换成"一句话就能出完整稿"的最短任务，减少变量。
5. **考虑改为 Team 型**（多角色分工），但会显著抬高注入量与延迟，只在前四条无效时尝试。
