## 一、起点：对目标专家的功能研读

开发前完整读取了本机已安装的目标专家包 `xiaohongshu-operations-expert`，共 **34 个文件**。逐类读完之后，只提取**功能需求**，不提取表达。

### 读到的文件与用途

| 文件 | 读了什么 | 用在什么地方 |
|---|---|---|

| `license/agency-agents.LICENSE` | MIT 许可证原文 | 用于确认其适用范围仅限于该包所引用的开源项目；本产品未使用该项目代码，故不附带 |

### 记录一条：不做批量改名的原因

目标专家的提示词方法论改编自 `msitarzewski/agency-agents`（MIT）。MIT 允许修改与商用，但要求保留版权声明。也就是说，**改名后重新分发是可行的，但必须保留原声明**。用户已明确不要走这条路，且要求"重新开发"，所以本项目走的是独立实现：需求来自功能研读，表达全部重写，不使用其任何文本。

这样处理的好处是：不需要判断"改写多少才算不侵权"，也不需要在包里附带一份自己并不使用的许可证。

## 二、差距分析：原专家哪里不够

以下每一条都对应本产品的一个具体设计，不是泛泛而谈。

| # | 原专家的问题 | 证据（读到的内容） | 本产品的处理 |
|---|---|---|---|
| 1 | **路由指向空文件** | `skills/xiaohongshu/SKILL.md` 的意图路由指向 `setup-xhs-mcp`、`xhs-login`、`post-to-xhs`、`xhs-search`、`xhs-explore`、`xhs-interact`、`xhs-profile`、`xhs-content-plan` 共 8 个子技能，包内无任何对应文件 | 七道工序全部落成真实文件；`selftest.py` 逐项校验文件存在性，缺一个就 FAIL |
| 2 | **强依赖外部服务** | 同一文件写明：MCP 工具不存在时"只提示用户运行 `/setup-xhs-mcp`，禁止用其他工具替代" | 全链路零外部依赖。需要平台数据时接受用户手抄或截图 |
| 3 | **质检只有文字建议** | agent 提示词里的 KPI（互动率 5%+、收藏率 8%+、分享率 2%+）是**目标值**，不是判定方法 | 落成 41 条可执行规则，输出命中句与改法，退出码可串流水线 |
| 4 | **无发布前合规检查** | 通读其 agent MD 与 xiaohongshu SKILL，未涉及绝对化用语、功效暗示、站外导流、虚假体验 | 合规闸 + 6 组词表 + 专章 + 替换写法库 |
| 5 | **复盘缺方法** | 有 KPI 目标，没有"数据不好时断在哪一级"的诊断路径 | 四级漏斗 + 用账号自身中位数做基线 + 只给一个动作 + 强制写验证方式 |
| 6 | **去 AI 味工具不适配中文** | `humanizer` 的词表与例句全部来自英文维基页面（"stands as a testament"、"em dash overuse" 等），且规避 curly quotes 这类英文排版问题 | 重写为中文笔记语境的 12 条（替读者总结、每段都有功能、三段排比、结尾升华、空洞形容词密度等），并落成正则 |
| 7 | **营销库与场景不匹配** | 23 个模块是英文 B2B/SEO/CRO/邮件序列，与小红书笔记生产无关 | 不引入。体积与相关度都不划算，且该目录未附许可证文件（见风险清单 R-05） |
| 8 | **无文件产物** | 交付物是对话里的文本 | 六张表 + 两张词表 + 三个脚本，交付物是文件 |
| 9 | **无平台具体约束** | 未涉及标题 20 字上限、封面 3:4、标签 8 个上限、折叠前 3 行 | 全部写进规范，并由脚本判定 |
| 10 | **无节拍概念** | "每周 3–5 篇"是频率建议，没有"同素材要拉开、每周要留白"的节拍规则 | 排期工序 + 脚本自动拉开 5 天间隔、非静默告警 |

## 三、设计决策（含被否掉的方案）

| 决策 | 选择 | 被否的方案与原因 |
|---|---|---|
| 产品形态 | **内容生产线**（七道工序） | 否掉"运营顾问"：顾问给的建议无法判定对错，交付物不可验证 |
| 依赖策略 | **零外部依赖** | 否掉接 MCP / 接浏览器自动化：装不上就用不了，商业产品的失败面太大 |
| 质检形态 | **规则 + 证据句 + 退出码** | 否掉"模型自评"：不可复现，用户无法复核 |
| 复盘基线 | **账号自身近 10 篇中位数** | 否掉行业平均值：跨类目差异几倍，对单篇无判断力 |
| 标题方法 | **留空型 + 可核对的量** | 否掉"情绪化标题模板"：模板会立刻同质化，且无法解释为什么有效 |
| 素材方法 | **三问（具体物/对照/代价）** | 否掉"卖点提炼法"：卖点视角写出来必然是广告 |
| 标签 | **3+3+2，共 8 个** | 否掉"堆热词"：短期曝光，长期账号标签混乱 |
| 排期 | **留白 + 同素材间隔 5 天** | 否掉"填满 30 天"：填满等于放弃 30 天里所有热点机会 |
| 名字 | 产品式命名（爆款笔记车间） | 否掉拟人花名：用户要求"名称突出内容制作"，产品名比人名更能说明品类 |
| 目录语言 | 技能内部用 ASCII 文件名 | 中文文件名在跨平台 zip 与解包时存在编码风险，商业分发不划算；标题写在文件内部 |
| 出稿顺序 | **先标题封面，后正文** | 否掉"先写正文"：标题定不下来，正文写了也白写 |

## 四、创作过程留痕

按实际执行顺序记录，可用于说明"独立开发"这一事实：

1. **功能研读**：扫描原包 34 个文件，读 plugin.json、agent MD、SKILL.md、humanizer、marketing-skills 索引、LICENSE、README。
2. **需求转写**：写 `docs/产品规格.md` 的第一至四节（用户、场景、问题、输入输出）。
3. **方法设计**：定"五段两闸""四个判断器""七道工序"，并把每条判断写成可执行的判据（带"不通过怎么办"）。
4. **目录初始化**：用 WorkBuddy 官方 `init_expert.py` 生成骨架，再逐文件替换为实际内容。
5. **主提示词**：写 `agents/czl-xhs-note-workshop.md`（三条硬规矩、五段两闸、四个判断器、路由表、异常处理、交付前十问）。
6. **工序与参考**：7 个 workflow + 8 份 reference，共 15 个文件，逐份写输入检查与判据。
7. **模板**：6 张表，其中 T4 笔记卡定义成可被脚本解析的结构（`## 标题候选 / ## 封面 / ## 正文 / ## 首评 / ## 标签`）。
8. **词表**：`compliance_terms.json`（6 组，按法规类别自行归纳）、`ai_tone_patterns.json`（12 条，带正则与改法）。
9. **脚本**：`note_lint.py`（41 条规则）、`build_calendar.py`（排期与间隔约束）、`selftest.py`（18 项自测）。全部纯标准库。
10. **样例与调试**：写 `good-note.md` / `bad-note.md` / `topics-demo.csv`，跑脚本迭代修正 3 处缺陷（见下节）。
11. **头像**：生成、裁掉水印、缩放到 512×512。
12. **测试**：`selftest.py` 18 项、`validate_expert.py` 校验。
13. **文档**：规格、记录、测试报告、风险清单、展示文案、文件清单。
14. **注册与打包**：`register_expert.py` → `package_expert.py`。

### 调试中修掉的三个真实缺陷

| # | 现象 | 原因 | 修法 |
|---|---|---|---|
| 1 | 标签数被识别为 0 | Markdown 标题正则允许 `#` 后无空格，导致 `#护手霜 #手部护理` 被当成一级标题 | 改为要求 `#{1,6}\s+`，符合 CommonMark；行首 `#标签` 不再误判 |
| 2 | 机器味证据句显示成 `这里我要多说一句要`（拼接错位） | `re.findall` 带分组时返回元组，拼接收到了分组而非整段 | 改用 `re.finditer` + `group(0)` 取全匹配 |
| 3 | 排期输出「素材来源」整列为空 | 选题矩阵的列名是「素材命中」，排期脚本只认「素材来源」 | 列名做别名兼容（素材来源 / 素材命中 / source） |

这三个缺陷都不是设计问题，是**跑起来才暴露的实现问题**——也是为什么测试必须真实执行，不能只写"预计通过"。

## 六、每个组件的职责

| 组件 | 职责 | 不负责什么 |
|---|---|---|
| `agents/czl-xhs-note-workshop.md` | 定规矩、定方法、定路由、定异常处理 | 不写具体工序细节（在 workflows 里） |
| `SKILL.md` | 工序总表、依赖关系、全局约束、索引 | 不重复方法细节 |
| `workflows/00–06` | 每道工序的输入检查与判据 | 不写通用方法论（在 references 里） |
| `references/01–08` | 方法论与对照改法 | 不写流程（在 workflows 里） |
| `templates/T1–T6` | 交付物格式 | 不写方法 |
| `data/*.json` | 机器可判定的词表与规则 | 不做判定（由脚本执行） |
| `scripts/*.py` | 判定与生成 | 不做创作 |
| `docs/*` | 规格、记录、测试、风险、文案 | 不参与运行时 |

分层原则：**规则在 data，判定在 scripts，方法在 references，流程在 workflows，格式在 templates。** 改词表不用改代码，改流程不用改词表。
