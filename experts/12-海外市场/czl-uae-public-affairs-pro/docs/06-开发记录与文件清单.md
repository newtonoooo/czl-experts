## 一、功能分析（对目标能力域的研究，不含其文案）

为确认"这个产品到底要解决什么"，先对目标能力域做了一次功能拆解，得到 7 个能力簇与 6 个共性缺口。分析只记录**功能结论**，不保留原文表述。

### 1.1 目标能力域拆解

| 能力簇 | 实际在做什么 | 本产品的对应实现 |
|---|---|---|
| 政府关系 | 讲清机构、层级、沟通方式 | W3 三层决策链 + 推进表 + 反腐败检查 |
| 政策解读 | 把政策翻译成"对我什么影响" | W1 监管域定位 + 规则清单 + 来源分级 |
| 监管合规 | 列出适用规则与所需动作 | W1 + W5 风险量化 |
| 行业协会 | 说明商会与协会的作用 | W3 影响层主体表（7 类主体，含正确/错误用法） |
| 舆论与社会责任 | 舆情监测与 CSR | W4 红线体检 + W6 危机快车道 |
| 媒体与危机 | 媒体生态与应对 | W6 分级 + 0–72h 动作表 + 双语声明模板 |
| 双边与地缘 | 中阿关系与区域风险 | W1 域 11（制裁/出口管制）+ W5 声誉外溢维度 |

### 1.2 识别到的 6 个共性缺口（本产品的改进点）

| # | 缺口 | 本产品的处理 |
|---|---|---|
| 1 | 七酋长国"要求分列"但无强制机制，容易退化成"阿联酋一般情况" | 设为**铁律第 1 条** + Q1 闸门检查项 + 矩阵表模板强制填 |
| 2 | 只有定性风险描述，无法排序、无法上会 | 五维打分模型 + 可执行脚本 + 阈值动作表 |
| 3 | 缺少受理环节，信息不全也直接给结论 | W0 + 12 项简报字段 + 三档闸门（PASS/ASK_ONCE/ASSUME_AND_FLAG） |
| 4 | 未区分"同国不同辖区"（本土/普通自由区/金融自由区/离岸） | 手册 01 第一节"先分层，再比较" + W2 判断条件 G2 |
| 5 | 信息源无分级、无时效标注 | 四级来源（A/B/C/D）+ 标注格式 + 12 个月时效规则 |
| 6 | 缺少可直接使用的交付物 | 4 份模板 + 5 种形态选择表 + 篇幅上限 |

> 说明：以上为功能层面的借鉴与改进，属于通用问题解决思路；未复制任何提示词、章节结构或文档表述。

## 二、设计决策记录

| 决策 | 选择 | 理由 | 放弃的方案 |
|---|---|---|---|
| 产品形态 | Agent 型单角色 | 公共事务判断高度依赖上下文连续性，多角色拆分会割裂判断链 | Team 型（3–5 角色）—— 会增加协调成本，且用户真正要的是一个能拍板的判断 |
| 工作流数量 | 7 条（W0–W6） | 覆盖"受理→情报→分列→路径→沟通→量化→危机"完整链路，且每条可独立触发 | 3 条（过粗，无法定位问题）/ 12 条（过细，用户记不住） |
| 知识承载方式 | 方法论手册 + 官方核验协议 | 避免版权风险（不搬他人整理文本）+ 避免时效风险（不写死条文） | 内置法规知识库（版权+时效双重风险） |
| 风险表达 | 五维 0–100 分 + 等级 + 主导维度 | 可排序、可比较、可复算；分数变化能验证缓释动作是否有效 | 纯定性（无法上会）/ 概率预测（无数据支撑，属虚假精确） |
| 脚本语言 | Python 标准库 | 零依赖、零许可风险、跨平台、可被 AI 直接调用 | 引入 pandas/numpy（体积与许可成本）/ Node（需运行时） |
| 交付物 | 4 份模板 + 3 种输出模式 | 用户真实需求是"能上会/能发出去"，不是"看分析" | 单一长报告模板 |
| 头像 | 扁平矢量人物 + 七边形符号 + 天际线 | 与"七酋长国 + 政企沟通"的产品内核一致；年轻干练，区别于常见"中年顾问"形象 | 纯文字徽标（信息量低）/ 真实照片（肖像权风险） |
| 目录结构 | `.codebuddy-plugin` + `agents` + `skills` + `avatars` + `docs` + `tools` | 严格对齐官方规范，同时把开发文档与工具留在包内便于维护 | 把所有内容塞进 agents/（不可维护） |

## 四、头像与图标问题的诊断记录

**问题描述**：把既有专家包导入到另一台 WorkBuddy 后，选中该专家时，输入框上方/卡片的小图标没有显示图片，而是退化成一个文字（名称首字）。

**诊断方法**：读取客户端 `app.asar` 中的专家服务实现，定位头像解析链路。

**关键发现**（技术事实）：

| # | 发现 | 代码依据（行为描述） |
|---|---|---|
| 1 | 本地目录解析：`avatar` 先去前导 `./`，再相对专家根目录 `path.resolve`；文件必须存在且位于根目录内，否则返回**空串** | `resolveAvatarUrl(avatar, expertRootDir)` |
| 2 | 头像大小上限为 **5,242,880 字节（5MB）**，超过则返回空串并打警告 | 常量 `ge = 5242880` |
| 3 | 从 zip 预览导入时：只在 zip 条目中**精确匹配** `${顶层目录}/${avatar}` 或 `${avatar}`；匹配不到就**原样返回相对路径字符串** | `resolveAvatarFromExpertZip(zip, topDir, avatarPath)` |
| 4 | 元数据目录 `.codebuddy-plugin` 与 `.workbuddy-plugin` 均被支持 | 目录候选数组 `[".codebuddy-plugin", ".workbuddy-plugin"]` |
| 5 | 专家 ID 校验规则：仅允许 `[a-zA-Z0-9._-]`，拒绝 `.`、`..`、含斜杠 | `isValidExpertId` / `isUnsafeDirName` |

**结论（按可能性排序）**：

1. **最可能：导入后出现双层嵌套目录**（如 `xxx/xxx/.codebuddy-plugin/...`）。此时 manifest 能通过后缀搜索找到，专家能显示，但 `avatar` 相对"外层根目录"解析失败 → 返回空串 → 前端回退显示名称首字。**这与"专家能用、只是图标变文字"的现象完全吻合。**
2. 次可能：zip 内条目路径与 manifest 推导的顶层目录不一致（手工压缩时多包一层、或目录名与 `plugin.name` 不同），触发发现 3 的"原样返回相对路径"分支 → 前端拿到 `avatars/expert.png` 这类相对 URL → 404 → 回退文字。
3. 已排除：图片损坏（实测 PNG chunk 完整、含 IEND）、尺寸不符（512×512）、超过大小上限（301.6KB ≪ 5MB）、路径含非 ASCII 字符。

**本产品的处置**：
- `avatar` 统一写 `./avatars/expert.png`；
- 打包脚本强制"zip 顶层目录唯一且 == `plugin.name`"；
- 打包后**回读验证**头像条目可被命中（T-06），并对"双层嵌套"坏包做回归测试（T-07，工具正确拦截）；
- 使用说明中给出 5 项排查表（`docs/02` 第五节 Q1）。

> 说明：以上为对客户端行为的技术分析，用于提升本产品的导入健壮性；未复制客户端代码，未修改客户端。
