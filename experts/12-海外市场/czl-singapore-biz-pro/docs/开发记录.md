## 一、需求来源与功能分析

### 1.1 目标用户

| 用户 | 典型场景 | 真实诉求 |
|------|---------|---------|
| 中国制造商/设备商海外负责人 | 第一次进入新加坡，要 3 个月内看到进展 | 知道先打谁、从哪进 |
| 已设新加坡公司的中资企业 | 有公司没客户，本地团队小 | 低成本找到可触达的客户与渠道 |
| 跨境贸易与品牌方 | 要找代理/经销商/售后 | 分辨"名义代理"与真有能力的分销商 |
| 投资与产业资本 | 评估区域总部与本地合作方 | 判断合作对象的主体与履约能力 |

### 1.2 要解决的问题（按优先级）

1. **选错对象**：把集团、子公司、仓库、项目混为一谈，导致打错人。
2. **排错顺序**：按知名度或规模排序，把资源投进打不进去的账户。
3. **找不到入口**：不知道采购主体是谁，只能泛泛"找代理"。
4. **证据不可追溯**：结论看似专业，但无法核对来源，团队无法复用。
5. **交付不可执行**：给了一堆分析，没有下一步动作和停止判据。

### 1.3 输入与输出

- 输入：产品/服务描述、客单价、目标行业、买方角色、市场阶段、资源与时间窗（可缺失，缺失即登记假设）。
- 输出：ICP 卡、假设登记、候选池与排序表、进入路径、首触要点、90 天行动、待核实清单、证据台账。

### 1.4 质量要求

| 维度 | 要求 | 实现方式 |
|------|------|---------|
| 准确性 | 事实可核对 | 证据编号制 + A–D 分级 + 台账校验脚本 |
| 一致性 | 同样的输入给同样的判断口径 | 固定六段流程 + 固定评分维度与权重 |
| 可执行 | 每条建议有动作与判据 | 输出结构强制包含"下一步动作""成功判据""停止判据" |
| 稳定性 | 信息不足时不编造 | 判断门 G1–G4 + 降级四段式输出 |
| 速度 | 简单问题不套模板 | 四档模式（全流程/快速核查/决策对比/先定标） |

## 二、产品设计决策

### 2.1 为什么用"六段"而不是"能力清单"

能力清单式提示词（"你会做客户开发、伙伴发现、供应商筛选……"）在实践中会退化为通用建议。改为阶段化流程后，每一段都有明确的输入、判断门与输出，模型无法跳段直接给名单。

### 2.2 为什么把 Fit 与 Priority 分开

合成一个分数会掩盖"适配但进不去"的账户。分开后，排序依据单一（Priority），Fit 只用于解释长期价值，避免出现"评分高但打不动"的推荐。

### 2.3 为什么强制反证

单向前提下，模型总能为一棵"看起来像客户"的企业找到理由。强制三条反证并逐条回应，把"像"和"值得"分开。

### 2.4 为什么只给档位不给分值

输入是判断而非测量。给出 87.3 分会制造不存在的精度，并诱导用户跳过依据。档位 + 逐维理由更可复核。

### 2.5 为什么配四个脚本

提示词约束靠"自觉"，脚本约束靠"可验证"。四个脚本把三条最容易被违反的规则变成可执行检查：评分门禁、台账完整性、包与头像的可导入性。

## 三、原创性说明

### 3.1 工作方式

1. 阅读参考专家（`sg-biz-dev`）的目录结构、元数据格式、提示词与参考文档，用于**功能分析**：它解决什么问题、按什么顺序、有哪些约束。
2. 归纳出功能需求（见第一节），**不复制**其文本、结构编号、代码或图像。
3. 重新设计产品结构（STRAIT 六段）、重写全部提示词与文档、独立实现全部脚本、独立生成头像。

### 3.2 未使用的原专家内容

| 类别 | 处理 |
|------|------|
| 原专家提示词正文（约 470 行） | 未复制。本包 Agent 提示词按"运行契约 + 六段流程 + 判断门 + 门禁"重写，段落结构与表述均不同 |
| 原专家 19 篇参考文档 | 未复制。本包 8 篇参考文档为重新撰写，主题按六段流程重新组织 |
| 原专家数据源清单 | 未复制表格。本包数据源文档为独立检索后重写，含 2026-10-28 的实测结果（HTTP 状态、API 返回字段） |
| 原专家头像 | 未使用。本包头像为独立生成 + 二次处理 |
| 原专家品牌文案、README、分类标签 | 未复制。展示文案重新撰写 |
| 原专家代码 | 原专家无脚本。本包 4 个脚本为全新实现 |

### 3.3 属于通用方法、非专属表达的部分

以下概念属于商务咨询领域的通用方法，本包以其通用含义使用，并以自己的语言重新表述：

- 证据分级（A/B/C/D）与来源权威性排序
- "事实—推断—建议"三层分离
- 采购信号分级（招标 → 投资 → 组织 → 行业背景）
- 理想客户画像（ICP）
- 双层评分（适配度 / 优先级）

这些概念不构成任何一方的专有表达。本包对其的具体定义、维度、权重、判断门、输出格式均为自行设计，例如：

- 信号四级的具体判定边界与"可支撑结论"的对应关系为自行定义；
- 评分维度与权重（Fit 5 维、Priority 6 维）为自行设定；
- 判断门 G1–G4 的触发条件为自行设计；
- 运行契约 C1–C6、反证三条规则、档位映射表为自行设计。

### 3.4 可核验的创作痕迹

- 本文件记录了设计决策与取舍理由（第二节）。
- 脚本含完整实现与自测用例，可复现（见《功能测试报告》）。
- 数据源文档中的实测结果带日期，可重新执行验证。
- 头像保留原始生成文件（1024×1024）与处理后文件（512×512），可对比。

## 四、与参考对象的功能差异

| 维度 | 参考对象 | 本产品 |
|------|---------|--------|
| 流程形态 | 以能力与规则章节组织 | 六段流水线，每段有输入/判断门/输出/异常 |
| 评分 | 给出参考权重，未强制门禁 | Fit/Priority 双层 + 置信度 + 反证门禁，可用脚本判定 |
| 反证 | 要求"至少找一条反向理由" | 强制三条 + 逐条回应，未通过不得进前三 |
| 证据 | 要求标注来源 | 证据编号制 + 台账 CSV + 校验脚本（等级/日期/URL/陈旧/D 级误用） |
| 交付物 | 以对话输出为主 | 5 个模板 + 4 个脚本，可产出可复用的表与卡 |
| 实体识别 | 提示区分集团与本地实体 | 七类实体 + "实体四问" + 账户级/站点级排除 |
| 依赖 | 声明 SingStat MCP | 零依赖，不声明 MCP，数据源走公开网页与公开 REST 接口 |
| 数据源 | 19 篇文档的静态清单 | 8 篇文档 + 实测记录（HTTP 状态、API 字段、可查询总量） |
