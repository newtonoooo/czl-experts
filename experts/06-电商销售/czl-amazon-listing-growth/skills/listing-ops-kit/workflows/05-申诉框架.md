# G5 · 申诉框架

## 职责

Listing 被压制、被下架、账号被警告时，产出一份**四段式申诉骨架 + 证据清单**。

这一门不替用户拍板最终申诉信。事实只能由用户确认，你给结构和素材。

## 输入参数

| 参数 | 必填 | 说明 |
|---|---|---|
| 处置类型 | 是 | 搜索压制 / Listing 下架 / 账号警告 / 侵权投诉 |
| 平台通知原文 | 是 | 逐字粘贴，不要转述 |
| 涉事 ASIN | 是 | — |
| 已做动作 | 否 | 已改了什么、什么时候改的 |
| 在手材料 | 否 | 报告、发票、授权书、注册号 |

## 执行步骤

1. **读通知原文，定位政策条款**。平台通知里通常有政策名称或条款编号，先把它摘出来。没有就写"通知未指明条款，需在后台政策页比对"。
2. **判根因**：具体到"哪条政策 + 哪个动作 + 哪份材料缺失"。写不出这三要素，说明根因还没找到，不要往下写。
3. **列已采取的纠正**：带时间点和证据文件名。
4. **设计预防机制**：谁、在哪个环节、用什么检查拦住同类问题。要能落到具体动作，不是"加强管理"。
5. **出证据清单**：文件级，标"已有 / 待补"。
6. **给提交前自查表**：用户核对事实后才能提交。

## 判断条件

| 情况 | 动作 |
|---|---|
| 根因未明 | 停在根因分析，不写纠正与预防。猜根因的申诉几乎必败 |
| 用户确实违规 | 承认真实情况，写整改，不要辩解。辩解会升级处置 |
| 用户认为误判 | 走"事实澄清"路线，用材料证明，不情绪化申诉 |
| 涉及侵权投诉 | 提示需权利人侧解决（撤回/授权），平台侧申诉作用有限 |
| 涉及法律判断 | 明确建议找律师，不代替法律意见 |

## 输出格式

```markdown
## 申诉框架 · 搜索压制

### 一、根因

政策：《商品信息质量政策》中的"夸大或无法验证的宣称"条款。
动作：标题与五点使用 "Best" 与 "100% Satisfaction Guarantee" 共 4 处。
缺失材料：无（该表述本身不可举证，与材料无关）。

### 二、已采取的纠正

| 时间 | 动作 | 证据 |
|---|---|---|
| 2026-10-20 | 删除全部绝对化与保证性表述 | `asin_B0XXXX_title_v2.txt` |
| 2026-10-20 | 重写五点，每条改为可验证规格 | `asin_B0XXXX_bullets_v2.txt` |
| 2026-10-21 | 全店 12 个 ASIN 同类词扫描 | `scan_report_20261021.csv` |

### 三、预防机制

- 责任人：运营 A，每次上新前跑一次 `listing_audit.py compliance`，退出码非 0 不得提交。
- 环节：G3 合规放行，卡在提交前。
- 记录：扫描结果归档到 `compliance/` 目录，保留 12 个月。

### 四、证据清单

| 材料 | 状态 |
|---|---|
| 修改前后对照 | 已有 |
| 全店扫描报告 | 已有 |
| 产品检测报告 | 待补 |

### 提交前自查

- [ ] 通知原文已逐字核对
- [ ] 根因与平台条款对应
- [ ] 纠正动作有可查证据
- [ ] 预防机制能落到人和环节
- [ ] 所有陈述与事实一致
```

## 异常处理

- **用户给的是转述而非原文**：要求原文。转述会丢条款信息，据此写的申诉方向大概率错。
- **用户要求"帮我编个理由"**：拒绝。虚假申诉会导致处置升级甚至封号。
- **多 ASIN 同时被处置**：按根因归并，不要一个 ASIN 写一份，平台看的是系统性整改。
- **申诉被驳回**：重新读驳回理由，通常指向"证据不足"或"根因不对"，回到第 2 步重做。

## 依赖

- 平台通知原文、ASIN、已做动作。
- 无脚本依赖（这一门靠文本分析）。

## 与其他工作流的关系

- 独立入口：被处置时直接从本门进入，不必先走 G0–G4。
- 下游：整改完成后回 G2/G3 重写并复核，把新文案作为纠正证据。
