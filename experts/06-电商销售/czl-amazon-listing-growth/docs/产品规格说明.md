## 一、这份规格是怎么来的

规格不是照抄某个现有产品，而是从**功能需求**重新推导：先拆解「亚马逊 Listing 顾问」这类产品要解决的通用问题，再定义本产品自己的边界、闸门与交付物。

拆解时只提取了**通用问题域**（谁在用、解决什么问题、需要什么输入、产出什么、要什么工具），没有沿用任何现有产品的文案、提示词结构、代码或工作流定义。

## 二、目标用户

| 用户类型 | 典型场景 | 他现在怎么做 | 痛点 |
|---|---|---|---|
| 单干卖家（1–3 人） | 新品上架，自己写文案 | 抄竞品 + 机翻 + 凭感觉 | 不知道哪里会违规，被压了才知道 |
| 小团队运营 | 一次上 5–20 个 SKU | 模板套用，质量参差 | 没有统一的自查口径，返工多 |
| 代运营 / 服务商 | 给客户交付 Listing | 人工审，靠经验 | 交付无法举证，客户不认"我觉得没问题" |
| 工厂转跨境 | 第一次做亚马逊 | 让货代或朋友帮忙写 | 不懂字符限制与类目门槛，反复被拒 |

**共同点**：他们要的不是"更有文采的文案"，是**一份能提交、且知道风险在哪的文案**。

## 三、要解决的问题（按优先级）

1. **写完不知道会不会被压**——字符超限、全大写、符号、堆砌，都是可机器判定的，但卖家没有工具。
2. **不知道哪句话会违规**——绝对化、保证性、医疗功效、促销语，逐条可枚举，但没人系统查。
3. **不知道该准备什么材料**——德国要责任人、法国要 EPR、美国儿童品要 CPC，信息散落且会变。
4. **不知道文案能不能被 AI 助手引用**——结构化程度、问答覆盖、属性完整度，都是可量化的。
5. **被下架后不会写申诉**——根因说不清，纠正没证据，预防是空话。

## 四、产品边界

### 做什么

- 写：标题、五点、描述、后台搜索词、A+ 文案骨架
- 查：字符预算、格式违规、关键词堆砌
- 判：合规放行（GO / CONDITIONAL / BLOCKED）
- 评：AI 推荐就绪度 0–100
- 救：申诉四段式框架

### 不做什么（明确排除）

| 不做 | 原因 |
|---|---|
| 广告投放与 ACOS 优化 | 属另一条业务链，混进来会稀释每道门的判断标准 |
| 选品与市场容量分析 | 同上 |
| 到岸成本与定价测算 | 已有独立产品覆盖，重复建设 |
| 图片与视频制作 | 不是文本工作流能解决的 |
| 代写申诉信终稿 | 事实只能由用户确认，代写会产生虚假陈述风险 |
| 承诺排名 / 流量 / 审核通过 | 不可控，承诺即虚假宣传 |

## 五、必要的输入

最小可用输入：**站点 + 类目 + 产品本体 + 至少一个主关键词**。

完整输入见 `skills/listing-ops-kit/workflows/00-输入体检.md` 的七项清单。缺项时用显式假设继续，假设必须标注"会影响哪道门"。

机器输入（脚本用）为 JSON，字段定义见 `SKILL.md` 第三节。只有 `title` 是硬必填。

## 六、预期输出

| 输出 | 形态 | 判定依据 |
|---|---|---|
| 输入卡 | Markdown 表 | 缺失项为空 |
| 关键词分配表 | Markdown 表 | 每词唯一归属，标题不超预算 |
| 文案块 | 纯文本，可直接复制 | lint 无 BLOCK |
| 合规判定 | 三级清单 + GO/CONDITIONAL/BLOCKED | 无 BLOCK |
| 就绪度 | 0–100 + 扣分明细 + 问答缺口 | 每项扣分有改写动作 |
| 审计报告 | Markdown 文件 | `report` 子命令产出 |
| 申诉框架 | 四段式 + 证据清单 | 每段有可执行动作 |

## 七、通用处理步骤（六道闸门）

```
G0 输入体检 → G1 关键词预算 → G2 文案构建 → G3 合规放行 → G4 AI 就绪度
                                                    ↘ G5 申诉框架（独立入口）
```

每道门的职责、输入、步骤、判断、输出、异常、依赖、上下游关系，逐份写在 `skills/listing-ops-kit/workflows/` 下。汇总视图见 `docs/工作流设计.md`。

## 八、工具能力与技术接口

| 能力 | 实现 | 依赖 |
|---|---|---|
| 文案体检 | `listing_audit.py lint` | 标准库 re / json |
| 合规放行 | `listing_audit.py compliance` | 同上 + 规则包 JSON |
| 就绪度评分 | `listing_audit.py score` | 同上 |
| 关键词预算 | `listing_audit.py keywords` | 同上 |
| 报告合成 | `listing_audit.py report` | 同上 |

- **零第三方依赖**：只用 Python 标准库，不需要联网、不需要装包、不需要 API Key。
- **不需要外部服务**：不调用任何 SaaS、不依赖任何平台接口，因此不存在接口失效导致的能力中断。
- **退出码契约**：`0` 通过 / `1` 警告 / `2` 阻断，可串进 CI 或批量脚本。
- **`--json`**：输出机器可读结果，便于二次处理。

## 九、质量要求

| 维度 | 要求 | 验收方式 |
|---|---|---|
| 正确性 | 每个 BLOCK 判定都能指到具体字符位置或具体法规条目 | 测试报告逐项核对 |
| 一致性 | 文档写的评分口径与代码实现一致 | `score-rubric.md` 与 `score()` 逐维对照 |
| 可解释 | 任何结论都带原因与改法，不只给结论 | 输出模板强制四要素 |
| 稳定 | 同一输入多次运行结果一致，无随机 | 重复运行比对 |
| 速度 | 单个 Listing 全量审计 < 1 秒 | 实测 |
| 可维护 | 规则与代码分离，改规则不用改代码 | 规则包为独立 JSON |

## 十、诚实边界

本产品是**写作期自查工具**，不是：

- 法律意见；
- 亚马逊官方政策解释；
- 认证代办服务；
- 销量预测工具。

规则包中的字符上限与合规义务是**配置基线**，会随平台与法规变化。冲突时的优先级：用户后台显示 > 当地法规原文 > 本规则包。产品在每次判定后都输出这句声明，不省略。
