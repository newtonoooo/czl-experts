# 工作流设计 · 六道闸门

本文是架构层说明。每道门的操作细节在 `skills/listing-ops-kit/workflows/` 下，这里只讲**为什么这样组织**。

---

## 一、设计原则

### 原则 1：闸门，不是步骤

"步骤"可以跳过，"闸门"不能。每道门都有一个**机器可判定的通过条件**：

| 门 | 通过条件 | 判定者 |
|---|---|---|
| G0 | 缺失项为空 | 人（检查清单） |
| G1 | 标题字符预算已算且未超 | 脚本 `keywords` |
| G2 | lint 无 BLOCK | 脚本 `lint` 退出码 ≠ 2 |
| G3 | 无 BLOCK 项 | 脚本 `compliance` 判定 ≠ BLOCKED |
| G4 | 每个扣分项都有改写动作 | 人（检查输出模板） |
| G5 | 四段齐全且每段有动作 | 人（检查输出模板） |

只要有一道门的判定是脚本给的，就不能用"我觉得没问题"顶替。

### 原则 2：先算预算，再写字

绝大多数 Listing 返工来自"写完发现超字符"。所以 G1 强制先算：`站点上限 − 品牌 − 2`。预算写在分配表顶部，写的时候对照着写。

### 原则 3：合规单独成门，不塞进写作

写作时的心理状态是"想表达"，合规判定需要"想风险"。混在一起，两边都做不好。所以 G2 只管写和格式，G3 只管判。G2 写完必须停下，让 G3 判。

### 原则 4：分数必须可拆

一个总分没有用。有用的是"哪一维掉了多少、为什么掉、怎么补"。所以 G4 强制输出扣分明细，且每项都要有改写动作。

### 原则 5：申诉独立入口

被下架的用户不需要从 G0 开始。G5 可以单独进入，因为它处理的不是"写得好不好"，而是"已经出事了怎么办"。

## 二、数据流

```
用户口述
   │
   ▼
[G0] 输入卡（Markdown 表 + 缺失项）
   │  ├── attributes ──────────────────────┐
   │  ├── 类目键 ────────────────┐         │
   │  └── 主词/竞品 ──┐          │         │
   ▼                 ▼          │         │
[G1] 关键词分配表 ◄──┘          │         │
   │                            │         │
   ▼                            │         │
[G2] 文案块（title/bullets/desc/search_terms）
   │                            │         │
   ├──► lint ── 退出码 ─────────┘         │
   ▼                                      │
[G3] 合规判定 ◄── 类目键 ─────────────────┘
   │
   ├── BLOCKED ──► 回 G2 改写
   ▼
[G4] 0–100 分 + 问答缺口 ◄── attributes
   │
   ▼
交付三块：成品 / 体检结论 / 下一步
```

申诉链独立：

```
平台通知 ──► [G5] 根因 → 纠正 → 预防 → 证据 ──► 用户核对事实 ──► 提交
                                          └──► 整改后回 G2/G3
```

## 三、每道门的失败模式与处理

| 门 | 典型失败 | 处理 |
|---|---|---|
| G0 | 用户只给一句话 | 给输入卡模板让他填，不凭空生成 |
| G0 | 站点缺失 | 停止。站点决定字符与合规，不能猜 |
| G1 | 词池太小 | 用竞品与类目词扩；扩不出就说明并建议取后台搜索词报告 |
| G1 | 用户要塞同义词 | 给后果 + 给合规写法，让用户选 |
| G2 | 写不出证据 | 删掉该条，换可举证的卖点 |
| G2 | 非英语站点 | 用目标语言写，不确定标 `[待母语校对]` |
| G3 | 类目键未覆盖 | `category_known=false` → 最多 CONDITIONAL |
| G3 | 拿不准法规 | 写"需核实"+ 核实路径，不写"应该没问题" |
| G4 | 文案太短 | 说明信息量不足，退回 G2 |
| G4 | 脚本误判 | 人工改判并说明理由 |
| G5 | 根因不明 | 停在根因分析，不往下写 |

## 四、门与门之间的回退规则

允许的回退只有四条，其他情况一律往前推：

1. **G2 → G1**：写完发现关键词放不下，重排预算。
2. **G3 → G2**：BLOCK 项必须改表述才能消除。
3. **G3 → G0**：类目判错，需重判类目键。
4. **G4 → G2**：分数 < 70，结构需要重写。

不允许的回退：G3 判 BLOCKED 却回去只改标点。BLOCK 项必须实质改写或补齐材料。

## 五、脚本在架构中的位置

脚本不是"可选加速器"，是**判定来源**。三条硬规则：

1. G2 交付前必须跑 `lint`，退出码 2 不许说"可以提交"。
2. G3 判定必须来自 `compliance`，人工只能在其基础上**加严**（例如把某条 CONDITION 升级为 BLOCK），不能放宽。
3. 分数必须来自 `score`，人工改判要写明理由。

脚本零依赖、不联网，因此判定可复现：同一份 JSON 任何时候跑都得到同样结果。这是"可举证"的基础。

## 六、规则与代码分离

```
references/marketplace-rules.json   ← 站点字符基线、文案检查参数
references/compliance-matrix.json   ← 宣称规则、类目门槛、市场义务
references/score-rubric.md          ← 评分口径（文档，代码按其实现）
```

改规则不改代码。平台改了字符上限，只改 JSON。法规新增义务，只改 JSON。这样规则维护成本低，也让"规则来源"可追溯。

代价：文档与代码必须手动保持一致。所以 `score-rubric.md` 里每个维度的判定方式写得足够具体（到什么词、什么阈值），代码照抄口径，改一处必须同步另一处。这一条写进了维护纪律。

## 七、为什么不做成多专家团队

考虑过拆成"文案专家 + 合规专家 + 评分专家"并行。否决，理由：

1. **强顺序依赖**：合规判定依赖文案，评分依赖文案，并行没有收益。
2. **上下文会断**：文案专家写的证据句，合规专家不知道，容易误判。
3. **交付会碎**：用户要的是一份能提交的 Listing，不是三份报告。

单专家串行，但每道门有独立产物，既保证连续性，也保证可检查。
