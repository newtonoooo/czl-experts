### 关于第三方组件的判断

参考专家的 `marketing-skills` 由外部技能市场引入（origin 指向 clawhub，SKILL.md 自述 vendor 自第三方仓库），`market-researcher` 未标注独立许可证。两者权利链都需要单独核实，且与"单场直播操盘"这个定位关系不大。

**结论：新包不引入任何第三方技能**，改为自行编写两个与业务强相关的技能。这样做的代价是少了 23 个营销模块，收益是许可链干净、职责集中、体积从数 MB 降到 470KB 量级。

## 三、产品定位决策

### 3.1 命名

- 包名：`czl-livestream-ops-coach`（`czl-` 前缀 + 功能名 livestream-ops-coach）
- 花名：阿麦（取"麦克风"的麦，与直播场景关联，两个字好记）
- 职业头衔：专业级直播间操盘教练
- 英文：Mai / Professional Livestream Room Operations Coach
- 重名检查：对比 `my-experts` 下 25 个自建专家与 `experts` 市场 49 个已安装专家，无同名；与相近的 `czl-douyin-growth-ops`（账号增长）、`czl-ecom-profit-ops`（利润与货盘）在定位上区分：**本产品只做单场直播的操盘，不碰账号内容与供应链利润结构**。

### 3.2 为什么是 Agent 型而不是 Team 型

六段工作流是串行依赖的（排品依赖目标、脚本依赖排品、投放依赖保本），并行多角色并不能提速，反而增加信息在角色之间失真的风险。单人设 + 强流程约束更稳，也更好维护。若后续要做"主播教练 + 投手 + 选品"三角色并行，可在此基础上扩为 Team 型。

### 3.3 分类

`07-SalesCommerce`。理由：主要输出物是销售场景的执行方案（排品、话术、逼单、投放），服务对象是卖货的人，而不是做品牌营销的人。05-MarketingGrowth 更偏流量与传播，与"单场成交"不是一回事。

## 五、未采纳的方案（记录取舍理由）

| 方案 | 为什么没做 |
|---|---|
| 引入第三方营销技能库 | 许可链需单独核实，且与单场操盘关联弱；自写两个技能更聚焦 |
| 做 Team 型多角色 | 六段串行，多角色只会增加上下文丢失 |
| 内置平台 API 对接 | 各平台开放能力与授权条件差异大，且会带来账号安全与合规风险 |
| 提供 GMV 预测模型 | 单场样本量不足，任何预测都是编的，与"不承诺结果"的原则冲突 |
| 做可视化图表 | 直播操盘的使用场景是打印贴墙，表格比图更实用 |
| 直接沿用参考专家的"数据看板模板" | 属于对方的具体表达，改用自设计的六段输出 |
