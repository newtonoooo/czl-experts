# 开发说明

这份文档讲三件事：一个专家包由什么组成、为什么这么组织、以及新增或修改一个包要走哪些步骤。

---

## 一、仓库的三层结构

```
czl-experts/
├── experts/     源码层：可读、可改、可 diff 的原始包
├── skills/      源码层：从专家包里拆出来、按技能标识去重后的独立技能
├── dist/        成品层：按分类归档的 zip，下载即用
└── CATALOG.md   索引层：面向使用者的目录
```

三层分开的理由：**源码层给人看，成品层给机器装，索引层给人找**。把 zip 提交进 `experts/` 会让 diff 变成二进制噪音；只给 zip 不给源码，别人没法改也没法审。

`experts/` 与 `dist/` 由脚本从 `01-专家包` 源库生成，不要直接在这两个目录里改——下次重建会覆盖。改包请回源库。

---

## 二、一个专家包的标准结构

| 路径 | 必需 | 作用 | 缺了会怎样 |
|---|---|---|---|
| `.codebuddy-plugin/plugin.json` | 是 | 身份、挂载、展示字段 | 平台识别不到，等于没装 |
| `agents/<包标识>.md` | 是 | 系统提示词，决定角色行为 | 专家加载不出人格 |
| `skills/<技能标识>/SKILL.md` | 否 | 技能主体 | 专家只剩提示词，没有可执行流程 |
| `avatars/` | 否 | 头像 512×512，≤500KB | 用默认头像 |
| `docs/` | 强烈建议 | 规格、开发记录、测试报告、风险清单 | 上架审核缺自证材料 |
| `README.md` | 否 | 包内说明 | 使用者只能读代码 |
| `CHANGELOG.md` | 否 | 版本记录 | 无法追溯改了什么 |
| `LICENSE` / `NOTICE` | 否 | 许可与来源声明 | 商用与原创性质疑时无据 |
| `tests/` `tools/` | 否 | 回归测试与可执行脚本 | 改动后无法自动验证 |

`docs/` 不是装饰。它是审核、原创性质疑、版权争议时唯一能拿出来的东西：开发记录写清「参考了什么、哪些没抄」，风险清单写清「残余风险与处置」。

## 三、命名铁律

以下四处必须完全一致，且**上架后不可改**：

| 位置 | 示例 |
|---|---|
| 目录名 | `czl-product-decision-audit` |
| `plugin.json` 的 `name` | `czl-product-decision-audit` |
| `plugin.json` 的 `agentName` | `czl-product-decision-audit` |
| `agents/<id>.md` 的文件名 | `czl-product-decision-audit.md` |

改名等于重建包。展示名（`displayName.zh`）和职业头衔（`profession.zh`）可以随时改，只影响展示。

Team 型额外两条：

- `profession` 必须等于 `displayName`（校验脚本强制）
- 必须有 `settings.json`，内容为 `{"agent": "<主理人 agentName>"}`

## 四、技能是怎么被触发的

技能没有显式调用入口，全靠模型读 `description` 决定是否启用。所以 `description` 的写法直接决定可用性：

**好的写法**：先说做什么，再说什么时候用，最后给触发场景的同义说法。

```
Fourth gate. Attack your own conclusion before someone else does: write falsification
conditions, run a pre-mortem with six product-specific death causes... Use before any
approval meeting, or when a decision already feels obvious.
```

**坏的写法**：只有名词短语（`"合同审查工具"`），模型不知道边界在哪，该用时不用，不该用时乱用。

技能内部的写法约定：

- 一个技能只承诺一件事。朱笔从「七件事」收窄到「只做质检」就是这么来的
- 正文先写「什么时候用」，再写步骤
- 参考资料放 `references/`，不要把大段资料塞进 `SKILL.md`
- 可执行脚本放 `scripts/`，纯标准库优先，避免装依赖

## 五、校验与测试

三个层次，从松到严：

```bash
# 1. 技能级：检查 SKILL.md 的 frontmatter 是否齐备、name 与目录名是否一致
python scripts/quick_validate.py skills/<技能标识>

# 2. 包级：检查 plugin.json 字段、tags 数量、quickPrompts 数量、
#    Team 型约束、头像文件是否存在
python scripts/validate_expert.py experts/<分类>/<包标识>

# 3. 回归测试：包内自带的 tests/，覆盖可执行逻辑
python experts/<分类>/<包标识>/tests/run_tests.py
```

注意 `validate_expert.py` 内置一条位置校验：专家必须位于专家目录下，否则报「专家不在专家目录下」。对 `experts/` 这种发布目录会必然报错，属预期行为，不是内容问题。

校验口径上的几个硬指标：

- `tags` 正好 3 个
- `quickPrompts` 正好 3 个，且 `defaultInitPrompt` 等于第一条
- `displayDescription.zh` 建议 40–50 字
- `avatar` 必须是 `avatars/` 下的实际文件，不能是 base64 data URI

当前 20 个包在这几条上还有欠账，明细见 [合规报告](03-合规报告.md)。

## 七、新增一个包的流程

1. 在源库 `01-专家包/<分类>/` 下建目录，名字用 `czl-<英文短名>`，全小写连字符
2. 写 `plugin.json`：`name` / `agentName` / `displayName` / `profession` / `displayDescription` / `tags`(3) / `quickPrompts`(3) / `avatar`
3. 写 `agents/<包标识>.md`：角色定义、核心能力、工作流程、输出规范、约束
4. 拆技能到 `skills/<技能标识>/SKILL.md`：一个技能一件事，`description` 写清触发条件
5. 生成头像放 `avatars/`，512×512，≤500KB
6. 补 `docs/`：产品规格、使用说明、测试报告、风险清单、开发记录
7. 跑 `validate_expert.py`，把报错逐条清掉
8. 重建仓库：`python 00-索引/_build_github_repo.py` → `_package_skills.py` → `_package_experts.py` → `_gen_repo_catalog.py`
9. 提交推送

## 八、已知技术债

**同名技能跨包冲突**。以下技能标识在多个包里重复出现，同时安装到同一个技能目录只会保留一份：

| 技能 | 出现在 |
|---|---|
| `evidence-ledger` | 定盘、产品战略参谋、产品战略作战室、方案策划 |
| `win-theme-forge` | 中标方案专家、方案策划 |
| `family-intake` / `home-system` | 语文家教、英语家教 |
| `czl-triprism-playbook` | 三棱镜分析师、三棱镜专家团 |
| `czl-oracle-*` 系列 | 算卦台、司南 |

彻底解决需要给其中一方加前缀（如 `bid-evidence-ledger`）。当前仓库的做法是**去重后只收录一份**，取舍依据见 [重名技能取舍说明](../skills-conflicts.md)。

**两处展示名重复**：`czl-gov-presales-pro` 与 `czl-proposal-strategy-studio` 的 `displayName` 都是「标胜」，目录里并排出现时不易区分。

## 九、重新生成仓库

```bash
cd 00-索引
python _build_github_repo.py    # 源码树 + README/LICENSE/EXPERTS/SKILLS/冲突说明
python _package_skills.py       # 176 个技能 zip
python _package_experts.py      # 61 个专家 zip，按分类归档到 dist/
python _gen_repo_catalog.py     # CATALOG.md
```

四个脚本都是幂等的，可以随时重跑。`_build_github_repo.py` 只清理 `experts/`、`skills/` 两个子目录，`dist/` 与 `.git` 不受影响。
